# 第 12 章 · 扩展与复用

> 你将学会:
> - 说清 v3 扩展模型的总原则——反射抽象与发现器被移除后,"特性对自身行为负责"意味着什么,以及自定义能力的三个入口
> - 用 `dotnet new xunit3-extension` 模板起扩展工程,并解剖它自带的动态跳过示例
> - 派生 `FactAttribute` 把平台门槛、`Trait` 标签封装成 `[LinuxFact]`、`[IntegrationTest]` 这样的自定义测试特性
> - 用 `BeforeAfterTestAttribute` + `$XunitDynamicSkip$` 消息前缀做运行时依赖门槛,并分清它和特性级 `SkipUnless` 的适用差异
> - 派生 `DataAttribute` 做自定义数据源;用 `IXunitSerializer` 让不可序列化的参数类型也能逐行运行;用 `ITestPipelineStartup` 在发现与执行之前做全局初始化
> - 把以上能力打包成一个可复用的测试基础设施类库:同解决方案用项目引用,跨仓库用 `dotnet pack` 发到私有源
> - 判断"什么时候不值得扩展":四步升级路线与停在最简形态的克制

本章有两个工程。[`code/Ch12.MyExtensions`](../code/Ch12.MyExtensions) 是扩展库:自定义特性、数据源、断言助手、管道启动都放在这里;[`code/Ch12.Extensibility`](../code/Ch12.Extensibility) 是消费它的测试工程,被测代码在 [`Production/`](../code/Ch12.Extensibility/Production/):`ProductKey`(目录服务的产品键,一个普通 record)与它的文本解析。所有输出片段来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2 的真实运行;绝对路径用 `...` 省略,其余逐字保留。

## 12.1 v3 的扩展模型:特性对自身行为负责

v2 的扩展靠"发现器":`[Fact]`、`[Theory]`、数据源、`Trait` 特性本身只声明意图,真正干活的是配套的 `Xunit.Sdk` 发现器类,反射信息还要先被包成 `IAttributeInfo`/`IMethodInfo` 这层抽象。v3 把这两样都删了:`Reflector` 与所有 `ReflectionXyz` 类不复存在,`IDataDiscoverer.GetData` 搬进了 `IDataAttribute.GetData` 成为 `DataAttribute` 的抽象方法。官方迁移文档的总结是:凡是消失的"发现器",它原来负责描述的东西现在自己描述自己。

对写测试的人来说,自定义能力因此只剩三个入口:

1. **派生 `FactAttribute`**(或实现 `IFactAttribute`):你的特性就是测试的声明本身,门槛、标签都在构造函数或接口成员里自己给出;
2. **派生 `DataAttribute`**(或实现 `IDataAttribute`):自己实现 `GetData` 返回数据行,自己实现 `SupportsDiscoveryEnumeration()` 决定何时枚举;
3. **管道钩子**:测试级的 `BeforeAfterTestAttribute`、程序集级的 `ITestPipelineStartup` 与 `IXunitSerializer`,各自挂在流水线的固定位置上。

### 12.1.1 `xunit3-extension` 模板

写扩展不必从 `xunit3` 测试模板起步。官方模板包里还有一个 `xunit3-extension`:

```text
$ dotnet new xunit3-extension -o MyExtensions
```

它生成的工程只引用扩展所需的最小集合([`Ch12.MyExtensions`](../code/Ch12.MyExtensions) 就是从这里起步的):

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <ImplicitUsings>enable</ImplicitUsings>
    <LangVersion>12.0</LangVersion>
    <Nullable>enable</Nullable>
    <TargetFramework>netstandard2.0</TargetFramework>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="xunit.analyzers" Version="2.1.0" />
    <PackageReference Include="xunit.v3.extensibility.core" Version="4.0.1" />
  </ItemGroup>

</Project>
```

注意三点:目标框架是 `netstandard2.0`(纯扩展库追求被谁都能引用);除分析器包之外只引用 `xunit.v3.extensibility.core`,不碰 runner 和 MTP;模板钉的版本可能落后,应升级到当前版本(本章统一用 4.0.2)。

模板自带一个示例扩展——按操作系统动态跳过的特性,它同时演示了 `$XunitDynamicSkip$` 这个本章的主角:

```csharp
public sealed class SupportedOSAttribute(params SupportedOS[] supportedOSes) :
    BeforeAfterTestAttribute
{
    public override void Before(MethodInfo methodUnderTest, IXunitTest test)
    {
        // …逐个比对 RuntimeInformation.IsOSPlatform(略)…

        // We use the dynamic skip exception message pattern to turn this into a skipped test
        // when it's not running on one of the targeted OSes
        if (!match)
            throw new Exception($"$XunitDynamicSkip$This test is not supported on {RuntimeInformation.OSDescription}");
    }
}
```

机制在官方 v3 文档里写得很直白:任何异常,只要消息以 `$XunitDynamicSkip$` 开头,就被 runner 当作动态跳过,标记之后的文本就是跳过原因。12.3 会用同样的骨架做一个探测 TCP 依赖的版本。

### 12.1.2 本章库工程的依赖选择

`xunit3-extension` 模板适合"纯扩展"。本章的库还要提供断言助手(用到 `Assert`),所以再加一个 `xunit.v3.assert`;因为库本身就面向 .NET 10 的测试工程,直接钉 `net10.0`。这是实测可用的最小配置:

```xml
  <ItemGroup>
    <Using Include="Xunit" />
  </ItemGroup>

  <ItemGroup>
    <PackageReference Include="xunit.v3.assert" Version="4.0.2" />
    <PackageReference Include="xunit.v3.extensibility.core" Version="4.0.2" />
  </ItemGroup>
```

`PropertyGroup` 与测试工程基本同款(`net10.0` 等),只是没有 `OutputType Exe`,也不需要 MTP 的 `TestingPlatformDotnetTestSupport`——库不需要 runner 入口。

不要引用 `xunit.v3.mtp-v2`——那是测试工程(可执行 + runner 入口)的事;库只该拿到编写与扩展所需的类型。12.7 会验证消费工程的引用方式。

## 12.2 自定义测试特性:把门槛和标签封装进特性

### 12.2.1 平台门槛:`[LinuxFact]` / `[WindowsFact]`

第 7 章用特性级 `SkipUnless` + `SkipType` 做过"只在 Linux 跑",但每条测试都要重复写三件套(`Skip`、`SkipUnless`、`SkipType`)。派生一个 `FactAttribute`,把门槛搬进库里的构造函数,使用处就只剩一个特性名。门槛属性是 [`Ch12.MyExtensions/PlatformGate.cs`](../code/Ch12.MyExtensions/PlatformGate.cs) 上的三个 `public static bool` 属性(`IsLinux` / `IsWindows` / `IsMacOS`,基于 `RuntimeInformation.IsOSPlatform`),多个测试工程共用。

[`Ch12.MyExtensions/PlatformFactAttributes.cs`](../code/Ch12.MyExtensions/PlatformFactAttributes.cs):

```csharp
/// <summary>只在 Linux 上执行的 Fact;其他平台运行时动态跳过。</summary>
public sealed class LinuxFactAttribute : FactAttribute
{
    public LinuxFactAttribute()
    {
        Skip = "此测试只在 Linux 上执行";
        SkipUnless = nameof(PlatformGate.IsLinux);
        SkipType = typeof(PlatformGate);
    }
}
```

要点:`Skip` 必须同时设置(第 7 章的坑,不设置运行期直接失败);`SkipType` 让门槛属性不必长在测试类上,而是指向库里的 `PlatformGate`;用 `nameof` 写属性名,拼错在编译期就报 CS0117(`PlatformGate` 不包含该定义)——但要注意,xUnit1054 那类"属性必须存在且返回 bool"的检查只针对写在测试方法特性上的命名参数,构造函数里赋的值它不检查,写错了要到运行时才炸(实测报 `Cannot find public static property 'IsLinxu' on type 'Ch12.MyExtensions.PlatformGate' for dynamic skip on test method …`)。

使用与真实输出([`Ch12.Extensibility/PlatformFactsTests.cs`](../code/Ch12.Extensibility/PlatformFactsTests.cs) 里 `[LinuxFact]` 的测试正常执行,`[WindowsFact]` 的在 Linux 上被动态跳过):

```text
skipped Ch12.Extensibility.Tests.PlatformFactsTests.WindowsFolder_IsResolvable (0ms)
  此测试只在 Windows 上执行
```

分析器认得自定义 Fact 派生类。给 `[LinuxFact]` 加一个不引用取消令牌的 `Timeout`,警告照常触发(这是临时探针,章工程里没有留下):

```text
warning xUnit1069: Test method 'Probe_MissingToken' has a Timeout but does not reference TestContext.Current.CancellationToken. Tests with a Timeout should reference TestContext.Current.CancellationToken so they can terminate promptly when the timeout is exceeded. (https://xunit.net/xunit.analyzers/rules/xUnit1069)
```

### 12.2.2 带构造参数的 Trait 封装:`[IntegrationTest]`

v2 想把 `Trait` 封装成自定义特性要写"特性 + `ITraitDiscoverer`"两件套;v3 的 `TraitDiscoverer` 随发现器一起删了,取而代之的是:任何实现 `Xunit.v3.ITraitAttribute` 的特性自己报告 `GetTraits()`,框架在收集特性时一并扫描。一个实现 `IFactAttribute` 一侧(通过派生 `FactAttribute`)、`ITraitAttribute` 一侧的特性,就能把"Fact + Trait"合成一个特性名:

[`Ch12.MyExtensions/TestKindAttribute.cs`](../code/Ch12.MyExtensions/TestKindAttribute.cs):

```csharp
/// <summary>Fact + Trait("kind", kind):把"测试种类"这类标签封装成带构造参数的特性。</summary>
[AttributeUsage(AttributeTargets.Method, AllowMultiple = false)]
public class TestKindAttribute(string kind) : FactAttribute, ITraitAttribute
{
    public IReadOnlyCollection<KeyValuePair<string, string>> GetTraits() => [new("kind", kind)];
}

/// <summary>等价于 [TestKind("integration")]:标记为集成测试,可用 --filter-trait "kind=integration" 单独筛出。</summary>
public sealed class IntegrationTestAttribute() : TestKindAttribute("integration");
```

12.3 的 `RequiresServiceTests` 两条用例都挂着 `[IntegrationTest]`。原生 runner 列出全工程用过的 trait:

```text
$ ./bin/Debug/net10.0/Ch12.Extensibility -list traits

"kind": ["integration"]
```

按 trait 过滤运行,只有那两条进入:

```text
$ ./bin/Debug/net10.0/Ch12.Extensibility -trait "kind=integration"
=== TEST EXECUTION SUMMARY ===
   Ch12.Extensibility  Total: 2, Errors: 0, Failed: 0, Skipped: 1, Not Run: 0, Time: 0.099s
```

MTP 侧同样有效:`dotnet test --project Ch12.Extensibility -- --filter-trait "kind=integration"` 的汇总就是 `total: 2`。

### 12.2.3 类型安全与领域 Trait:枚举值 + `ITraitAttribute`

上面的 `[IntegrationTest]` 把常用的 `kind=integration` 固定成一个特性名。若调用处需要在多个值之间选择,可以让 `ITraitAttribute` 把枚举转换成 trait 字符串,也可以让类级特性统一标记功能区域:

```csharp
using Xunit.v3;
using Xunit;

public enum FailureImpact { DataLoss, UserVisible, Cosmetic }

[AttributeUsage(AttributeTargets.Method)]
public sealed class ImpactAttribute(FailureImpact impact) : Attribute, ITraitAttribute
{
    public IReadOnlyCollection<KeyValuePair<string, string>> GetTraits() =>
        [new("impact", impact.ToString())];
}

[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = true)]
public sealed class ComponentAttribute(string name) : Attribute, ITraitAttribute
{
    public IReadOnlyCollection<KeyValuePair<string, string>> GetTraits() =>
        [new("component", name)];
}

[Component("invoicing")] // 可贴在类上,让类里的测试都带 component=invoicing
public class InvoiceTests
{
    [Fact]
    [Impact(FailureImpact.DataLoss)]
    public void Export_PreservesEveryInvoice() { /* ... */ }
}
```

`[Impact(...)]` 只提供标签,因此要与 `[Fact]` / `[Theory]` 一起使用;它和 12.2.2 里派生 `FactAttribute` 的 `[IntegrationTest]` 不同,后者本身也声明了一条 Fact 测试。上例中的测试同时有 `impact=DataLoss` 与 `component=invoicing`,可用 `--filter-trait "impact=DataLoss"` 或 `--filter-trait "component=invoicing"` 筛选。枚举成员名经 `ToString()` 成为 trait 值,重命名成员也会改变过滤值;若 CI 命令或报告依赖该值,应把它视为稳定接口。

这是 v3 的 `ITraitAttribute` 形态:接口在 `Xunit.v3` 命名空间中,由 `GetTraits()` 返回 name/value 对。v2 的同名接口是标记接口,自定义特性还需要 trait discoverer 才能供过滤器识别;不要把两套实现直接互换。

## 12.3 动态跳过扩展:兑现 `$XunitDynamicSkip$`

第 7 章留过一个尾:"动态跳过的底层机制是异常消息,以 `$XunitDynamicSkip$` 开头的异常消息会被当作动态跳过,后面部分是原因。"这一章把它用作扩展的原料。

场景:一组测试依赖某个 TCP 服务,服务起没起只有到执行那一刻、真去连一次才知道——这既不是编译期能判定的,也不是"某个类上的 bool 属性"写得下的(特性级 `SkipUnless` 要求一个可静态引用的 public static bool 属性;而且第 7 章实测过,特性级条件跳过根本不进 `BeforeAfterTest` 这条流水线)。用 `BeforeAfterTestAttribute` 在 `Before` 里做运行时探测:

[`Ch12.MyExtensions/RequiresServiceAttribute.cs`](../code/Ch12.MyExtensions/RequiresServiceAttribute.cs):

```csharp
public sealed class RequiresServiceAttribute(string host, int port) : BeforeAfterTestAttribute
{
    public override void Before(MethodInfo testMethod, IXunitTest test)
    {
        if (!TcpGate.IsListening(host, port))
            throw new Exception(
                $"$XunitDynamicSkip$所需服务 {host}:{port} 未监听;" +
                "请先启动依赖(或用夹具把它带起来)再运行这条测试");
    }
}
```

`Before` 的第二个参数 `IXunitTest` 是 v3 新增的(v2 只给方法信息),从这里能拿到当前测试的完整上下文。测试侧([`Ch12.Extensibility/RequiresServiceTests.cs`](../code/Ch12.Extensibility/RequiresServiceTests.cs),静态构造里起一个进程内回环服务,`EchoServer`/`EchoAssert` 同样来自库):

```csharp
public class RequiresServiceTests
{
    public const int EchoPort = 39817;    // 进程内回环服务:静态构造里起起来
    public const int AbsentPort = 39818;  // 故意没有任何服务在监听

    static RequiresServiceTests() => EchoServer.EnsureListening(EchoPort);

    [IntegrationTest]
    [RequiresService("127.0.0.1", EchoPort)]
    public void Echo_RoundTripReceivesPayload() =>
        EchoAssert.RoundTrip("127.0.0.1", EchoPort, "hello-ch12");

    [IntegrationTest]
    [RequiresService("127.0.0.1", AbsentPort)]
    public void LegacyMirror_RoundTripReceivesPayload() =>
        EchoAssert.RoundTrip("127.0.0.1", AbsentPort, "legacy-mirror");
}
```

真实运行里,监听着的端口那条正常执行,没监听的那条被记为跳过,原因正是标记后的文本:

```text
skipped Ch12.Extensibility.Tests.RequiresServiceTests.LegacyMirror_RoundTripReceivesPayload (0ms)
  所需服务 127.0.0.1:39818 未监听;请先启动依赖(或用夹具把它带起来)再运行这条测试
```

反例同样真实:把消息前缀去掉再跑,同一条测试就从"跳过"变成"失败"——前缀是这条机制的唯一开关:

```text
failed Ch12.Extensibility.Tests.RequiresServiceTests.LegacyMirror_RoundTripReceivesPayload (12ms)
  from .../Ch12.Extensibility.dll (net10.0|x64)
  Xunit.MicrosoftTestingPlatform.XunitException: System.Exception : 所需服务 127.0.0.1:39818 未监听;请先启动依赖(或用夹具把它带起来)再运行这条测试
    at Ch12.MyExtensions.RequiresServiceAttribute.Before(MethodInfo testMethod, IXunitTest test) in .../Ch12.MyExtensions/RequiresServiceAttribute.cs:17
```

与特性级 `SkipUnless` 怎么选:条件能表达成"某类型上的 public static bool 属性"就用 `SkipUnless`(声明式、无代码);需要执行期探测(TCP、环境变量、许可证)、或条件依赖只有跑起来才有的状态,用 `Before` + 前缀。注意执行边界:这条路径会先构造测试类、跑完 `Before` 才跳过(上面监听端口的用例正是靠"类构造先于 `Before`"才连上服务的),而特性级条件跳过连类都不构造——这正是第 7 章那张计数表留下的分界线。

## 12.4 自定义数据源:派生 `DataAttribute`

v3 里数据源的最小契约就是 `DataAttribute` 的两个抽象成员:`GetData(MethodInfo, DisposalTracker)` 返回 `ValueTask<IReadOnlyCollection<ITheoryDataRow>>`,`SupportsDiscoveryEnumeration()` 返回 `bool`。`GetData` 拿到的是真实的 `MethodInfo`(不再是 v2 的 `IMethodInfo` 抽象),可以按参数类型解析数据;`DisposalTracker` 里登记的对象会在测试结束后被释放(适合打开的数据库连接)。`SupportsDiscoveryEnumeration()` 决定枚举时机:`true` 表示发现期就把每行数据变成独立测试用例;`false` 表示只产出一个测试用例,数据到执行期才枚举——数据源要连库、读文件时,这能避免"只是列一下测试"也去读一遍数据源。

最小可用的自定义数据源,把内嵌 CSV 解析成数据行([`Ch12.MyExtensions/CsvDataAttribute.cs`](../code/Ch12.MyExtensions/CsvDataAttribute.cs) 节选):

```csharp
[AttributeUsage(AttributeTargets.Method, AllowMultiple = false)]
public sealed class CsvDataAttribute(string csv) : DataAttribute
{
    public override ValueTask<IReadOnlyCollection<ITheoryDataRow>> GetData(
        MethodInfo testMethod,
        DisposalTracker disposalTracker)
    {
        var parameterTypes = testMethod.GetParameters().Select(p => p.ParameterType).ToArray();
        var rows = new List<ITheoryDataRow>();

        foreach (var rawLine in csv.Split('\n', StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries))
        {
            var line = rawLine;
            var markSkipped = line.StartsWith('!');
            if (markSkipped)
                line = line[1..].Trim();

            var cells = line.Split(',', StringSplitOptions.TrimEntries);
            if (cells.Length != parameterTypes.Length)
                throw new ArgumentException(
                    $"CSV 行 \"{line}\" 有 {cells.Length} 列,而测试方法 {testMethod.Name} 有 {parameterTypes.Length} 个参数");

            // …每一列按对应参数类型 Convert.ChangeType(先解 Nullable)成 object?…

            TheoryDataRowBase row = new TheoryDataRow(values);
            if (markSkipped)
                row = row.WithSkip("CSV 行首带 !,标记为暂不执行");
            // ConvertDataRow:行上已有的值优先,缺的从特性属性(Label/Skip/Traits/…)补齐
            rows.Add(ConvertDataRow(row));
        }

        return ValueTask.FromResult<IReadOnlyCollection<ITheoryDataRow>>(rows);
    }

    public override bool SupportsDiscoveryEnumeration() => true;
}
```

注意 `ConvertDataRow` 这一步。数据行元数据(`Label`、`Skip`、`TestDisplayName`、`Timeout`、`Traits`、`Explicit`、`SkipUnless`/`SkipWhen`/`SkipType`、`DisableParallelization`)不会由框架自动从特性属性套到行上——`DataAttribute` 提供 `ConvertDataRow` 助手,语义是"行上的值优先,缺的从特性属性补齐",内置数据源都走它,自定义数据源不调用就没有这个行为。这正是"特性对自身行为负责"落到细节里的样子。

测试侧把三种元数据都用上([`Ch12.Extensibility/CsvProductsTests.cs`](../code/Ch12.Extensibility/CsvProductsTests.cs)):

```csharp
    private const string InventoryCsv = """
        1049,Widget,19.99
        2112,Gadget,3.50
        !2600,RetiredWidget,0.00
        """;

    [Theory]
    [CsvData(InventoryCsv, Label = "inventory-csv", Traits = new[] { "source", "csv" })]
    public void InventoryRow_PriceIsPositive(int id, string name, decimal price)
    {
        output.WriteLine($"行 {id}({name})价格 {price},标签 = {TestContext.Current.Test?.TestLabel}");
        Assert.True(price > 0m, $"行 {id} 的价格必须为正");
    }
```

先看枚举时机的差别。原生 in-process runner 默认关闭"理论预枚举"(`-?` 里写明 `disabled by default`),默认运行只发现 8 个测试用例;加 `-preEnumerateTheories` 后是 15 个:

```text
$ ./bin/Debug/net10.0/Ch12.Extensibility -diagnostics | grep Discovered
  Discovered:  Ch12.Extensibility (8 test cases to be run)

$ ./bin/Debug/net10.0/Ch12.Extensibility -preEnumerateTheories -diagnostics | grep Discovered
  Discovered:  Ch12.Extensibility (15 test cases to be run)
```

预枚举打开后,每行 CSV 都是可单独列出的测试用例,`Label` 会追加到显示名(参数列表被它替代),`Traits` 进入 trait 集合:

```text

Ch12.Extensibility.Tests.CsvProductsTests.InventoryRow_PriceIsPositive [inventory-csv]
Ch12.Extensibility.Tests.CsvProductsTests.InventoryRow_PriceIsPositive [inventory-csv]
Ch12.Extensibility.Tests.CsvProductsTests.InventoryRow_PriceIsPositive [inventory-csv]

$ ./bin/Debug/net10.0/Ch12.Extensibility -preEnumerateTheories -trait "source=csv"
=== TEST EXECUTION SUMMARY ===
   Ch12.Extensibility  Total: 3, Errors: 0, Failed: 0, Skipped: 1, Not Run: 0, Time: 0.080s
```

行级 `Skip` 无论是否预枚举都在运行期生效(`!` 那行):

```text
    Ch12.Extensibility.Tests.CsvProductsTests.InventoryRow_PriceIsPositive [inventory-csv] [SKIP]
      CSV 行首带 !,标记为暂不执行
```

而 `Label` 的原始值在测试体内经 `TestContext.Current.Test.TestLabel` 读得到:

```text
        行 1049(Widget)价格 19.99,标签 = inventory-csv
        行 2112(Gadget)价格 3.50,标签 = inventory-csv
```

## 12.5 自定义序列化:让不可序列化的参数也能逐行运行

runner 要把一条 Theory 数据行"交出去、再要回来"(Test Explorer 的发现与执行跨进程跨时间;预枚举本身也要求每行可序列化,否则无法唯一标识一个用例)。内置序列化覆盖基元、`Guid`/`Uri`/`Version` 等系统类型、枚举、数组与 `null`;自定义类型不在其列。`ProductKey`([`Ch12.Extensibility/Production/Catalog/ProductKey.cs`](../code/Ch12.Extensibility/Production/Catalog/ProductKey.cs))就是这样一个生产类型(节选):

```csharp
public sealed record ProductKey(int CategoryId, string Sku)
{
    public static ProductKey Parse(string text) { /* 失败抛 FormatException */ }
    public static bool TryParse(string text, out ProductKey? key) { /* 分类ID:SKU 文本格式 */ }

    public override string ToString() => $"{CategoryId}:{Sku}";
}
```

`ProductCatalogTests` 用 `TheoryData<ProductKey, string>` 喂给 `[Theory]`。没有序列化器时,预枚举会发出诊断并退回单测试用例——这是真实输出(临时注释掉注册后跑出来的):

```text
    [D::Ch12.Extensibility] Non-serializable data (of type 'Ch12.Extensibility.Production.ProductKey') found for 'Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText'; falling back to single test case.
```

v3 的解法是外部序列化器 `Xunit.Sdk.IXunitSerializer`(v2 的 `IXunitSerializable` 仍可用,但要求把接口实现到数据类型自己身上;外部序列化器不用改生产代码,还能序列化你控制不了的类型):

[`Ch12.Extensibility/Production/Catalog/ProductKeySerializer.cs`](../code/Ch12.Extensibility/Production/Catalog/ProductKeySerializer.cs):

```csharp
public sealed class ProductKeySerializer : IXunitSerializer
{
    public bool IsSerializable(Type type, object? value, out string failureReason)
    {
        if (value is ProductKey or null)
        {
            failureReason = string.Empty;
            return true;
        }

        failureReason = $"无法序列化 {type}:值不是 {nameof(ProductKey)}";
        return false;
    }

    public string Serialize(object value) =>
        value is ProductKey key
            ? key.ToString()
            : throw new ArgumentException($"无法序列化 {value.GetType()}", nameof(value));

    public object Deserialize(Type type, string serializedValue) => ProductKey.Parse(serializedValue);
}
```

程序集级注册(特性类在 `Xunit.Sdk` 命名空间;序列化器要有公共无参构造):

```csharp
[assembly: RegisterXunitSerializer(typeof(ProductKeySerializer), typeof(ProductKey))]
```

注册之后,同一个 Theory 的三行各自成为可单独选中的用例,按显示名精确运行其中一行:

```text
$ ./bin/Debug/net10.0/Ch12.Extensibility -preEnumerateTheories -list tests -method "Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText"

Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText(key: 1049:widget24, expectedSku: "widget24")
Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText(key: 2112:tool9, expectedSku: "tool9")
Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText(key: 7:gadgetX, expectedSku: "gadgetX")

$ ./bin/Debug/net10.0/Ch12.Extensibility -preEnumerateTheories -displayName 'Ch12.Extensibility.Tests.ProductCatalogTests.ProductKey_RoundTripsThroughText(key: 2112:tool9, expectedSku: "tool9")'
=== TEST EXECUTION SUMMARY ===
   Ch12.Extensibility  Total: 1, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 0.076s
```

MTP 侧按显示名过滤,同样只跑那一行(`total: 1, succeeded: 1`)。这就是"Test Explorer 里逐行点着跑"背后的机制。

坑:内置类型的序列化不可覆盖,注册会被警告并忽略;两个序列化器注册同一类型,先注册的赢,后来的同样被警告忽略;`Serialize` 永远不会收到 `null`(`null` 由内置机制处理),所以 `Deserialize` 要返回非 `null`。

## 12.6 管道启动:发现与执行之前的全局初始化

程序集夹具(第 5 章)只在执行期存在;发现阶段(列测试、Test Explorer 刷新列表)它不跑。如果有些全局初始化是发现和执行都需要的——注册环境变量、准备诊断上下文、加载许可证——那是 `ITestPipelineStartup` 的位置:

[`Ch12.MyExtensions/RunStampPipelineStartup.cs`](../code/Ch12.MyExtensions/RunStampPipelineStartup.cs):

```csharp
public sealed class RunStampPipelineStartup : ITestPipelineStartup
{
    public const string RunIdVariable = "CH12_RUN_ID";

    private IMessageSink? diagnosticSink;
    private string? runId;

    public ValueTask StartAsync(IMessageSink diagnosticMessageSink)
    {
        diagnosticSink = diagnosticMessageSink;
        runId = Guid.NewGuid().ToString("N")[..8];
        Environment.SetEnvironmentVariable(RunIdVariable, runId);
        diagnosticMessageSink.OnMessage(
            new DiagnosticMessage($"[Ch12 管道启动] 运行号 {runId};任何发现/执行开始前就已生效"));
        return ValueTask.CompletedTask;
    }

    // StopAsync 同理:发一条 "[Ch12 管道收尾] 运行号 … 结束" 诊断
}
```

注册是程序集级的,一个程序集只允许一个:`[assembly: TestPipelineStartup(typeof(RunStampPipelineStartup))]`;4.0 起还有泛型写法 `[assembly: TestPipelineStartup<RunStampPipelineStartup>]`(仅 .NET 8+)。`StartAsync` 的参数就是诊断消息通道——别用 `TestContext.Current.SendDiagnosticMessage`,管道启动时 TestContext 还没接好诊断接收器,消息会无声丢掉(这是本章踩过的真坑,第一版代码就发不出来)。

真实输出。跑一条断言"运行号必须已经存在"的测试,加 `-diagnostics`(MTP 不显示 xUnit 诊断,看第 9 章):


## 12.7 打包成可复用的测试基础设施库

本章的库把自定义特性(`LinuxFact`/`WindowsFact`/`IntegrationTest`/`RequiresService`)、数据源(`CsvData`)、断言助手(`EchoAssert`)、共享服务(`EchoServer`/`TcpGate`)和管道启动(`RunStampPipelineStartup`)放在一起;测试工程只有一条项目引用:

```xml
  <ItemGroup>
    <ProjectReference Include="..\Ch12.MyExtensions\Ch12.MyExtensions.csproj" />
  </ItemGroup>
```

实测验证依赖的流动方式:NuGet 的 `PackageReference` 会沿项目引用传递。一个只有这条项目引用、没有任何 xunit 包引用的普通类库,照样能编译下面的代码——`[LinuxFact]`、`[CsvData]` 甚至 `Assert.True` 都解析得到:

```csharp
public class SomeTests
{
    [LinuxFact]
    public void UsesFactFromLibraryWithoutOwnXunitReference() => Assert.True(PlatformGate.IsLinux);
}
```

(全局 `using Xunit;` 不随库流动,消费方自己写一行 using 即可。)当然,要成为**可运行**的测试工程,消费方仍需 `xunit.v3.mtp-v2` 提供入口与 runner——库不该也无法替它决定运行方式。

工程化要点:

- **库引用哪些包**:扩展与测试编写类型在 `xunit.v3.extensibility.core`,断言在 `xunit.v3.assert`;runner/MTP(`xunit.v3.mtp-v2`)只进可执行测试工程。这是 `xunit3-extension` 模板与本章库共同的边界。
- **版本对齐**:库钉的 xunit 版本应与测试工程一致(都是 4.0.2)。不一致时 NuGet 会取高版本,扩展接口在 minor 之间偶有增删,对齐能省掉一类难查的 `MissingMethodException`。
- **目标框架**:纯扩展库用 `netstandard2.0`(模板默认,谁都能引用);要共享的测试基础设施常用 `net10.0`(直接用新 BCL API,消费方也都是新工程)。本章选后者。
- **命名与目录**:扩展类型按能力分文件(一个能力一个文件),命名空间跟工程名([`Ch12.MyExtensions`](../code/Ch12.MyExtensions)),门槛属性类(`PlatformGate`)与探针(`TcpGate`)保持 public——`SkipType` 与运行时反射都要求 public 可见性。

**跨仓库分发:把它变成 NuGet 包。** 项目引用只在同一个解决方案里流动;公司里其它仓库要用这套 `[LinuxFact]`/`[CsvData]`,就把库打成包。本章的库不需要任何额外配置就能打:

```text
$ dotnet pack Ch12.MyExtensions -o /tmp/ch12pkg
  Ch12.MyExtensions -> .../Ch12.MyExtensions/bin/Release/net10.0/Ch12.MyExtensions.dll
  The package Ch12.MyExtensions.1.0.0 is missing a readme. Go to https://aka.ms/nuget/authoring-best-practices/readme ...
  Successfully created package '/tmp/ch12pkg/Ch12.MyExtensions.1.0.0.nupkg'.

$ unzip -l /tmp/ch12pkg/Ch12.MyExtensions.1.0.0.nupkg | grep -E "nuspec|dll"
      665  ...  Ch12.MyExtensions.nuspec
    18944  ...  lib/net10.0/Ch12.MyExtensions.dll
```

`dotnet pack` 读 csproj 里的 `Version` 与包元数据;本章的库没写 `Version`,所以包版本默认就是上面那个 `1.0.0`。产物里 `lib/net10.0/` 的路径跟着 `TargetFramework` 走。之后 `dotnet nuget push` 到公司的私有源(或内部 feed 的目录共享),消费方 `dotnet add package Ch12.MyExtensions` 即可——上一段说的"包引用沿项目引用传递"对包形式的消费方同样成立。给库补上 csproj 元数据(`PackageReadmeFile`、`RepositoryUrl`、稳定的 `Version`)能消掉上面那条 readme 警告,也让升级可控:测试基础设施库适合 **Minor/Patch 语义化版本**,破坏性变更宁可新开包名。

**最后一条是刹车。** 扩展能力很容易过度使用:一个团队里同时存在 `WindowsFact`、`SkipOnCiFact`、`RetryFact`、`DataFromDbAttribute` 五种自定义特性,新人每个都要查一遍文档,这比它们省下的样板代码更贵。值得动手的升级路线只有四步——**发现同一个模式在三个以上地方出现 → 触发条件是可判定的一件事(环境、数据源、标签) → 先封装成特性或数据源(行为不变) → 确实跨仓库复用了再进库/包**。任何一步不满足,就停在更简单的形态上:一个私有的辅助方法、一个 `static IEnumerable<T>` 数据源,都比一个只有一个人用得懂的特性好。

## 12.8 再往前:排序器与结果写入器

本章没碰的两个扩展点,点到为止:

- **自定义排序器**:第 6 章已经实现过 `ITestMethodOrderer`(还有 `ITestCaseOrderer`/`ITestClassOrderer`/`ITestCollectionOrderer` 四级,注册特性在 `Xunit` 命名空间)。
- **自定义结果写入器**:4.0 把报告生成器开放成了扩展点——实现 `IConsoleResultWriter` / `IMicrosoftTestingPlatformResultWriter`,用程序集级 `[RegisterResultWriter]`、`[RegisterConsoleResultWriter]`、`[RegisterMicrosoftTestingPlatformResultWriter]` 注册(泛型变体同样有),详见官方 4.0 发布说明与 runner 文档。自定义 runner reporter 在 v3 的另一形态:实现 `IRunnerReporter`,用程序集级 `[RegisterRunnerReporter(typeof(…))]` 链进测试程序集,再用 `-reporter` 选择(只在直接运行测试程序集时可用);一个独立 reporter 包能否被外部 runner 自动发现,仍是未解的开放问题(xunit/xunit#1874)。

## 动手练习

1. **补齐平台门槛**:在库里加 `[MacOSFact]`(复用 `PlatformGate.IsMacOS`),在测试工程加一条用它的用例。验收:Linux 上章工程仍全绿,`dotnet test` 汇总里多一条 `skipped`,原因是你写的 `Skip` 消息。
2. **给 CSV 数据源加注释语法**:让以 `#` 开头的行整行忽略;再加一个 `skipOnError` 开关,坏行列数不符时不抛异常而是产出一条带 `Skip` 的行(原因写明列数不符)。验收:`-preEnumerateTheories -list tests` 里注释行不出现、坏行以跳过形态出现;章工程全绿。
3. **再写一个外部序列化器**:给 `ProductKeySerializer` 加一个兄弟,支持 `Money(decimal Amount, string Currency)` record(文本形式 `19.99|USD`),用它写一个 3 行的 Theory。验收:不带序列化器时 `-preEnumerateTheories` 出现 `Non-serializable data (of type '…Money')` 诊断;注册后 `-displayName` 能精确运行其中一行,`total: 1`。

## 本章小结

- v3 删掉了反射抽象与发现器:声明什么就自己实现什么——`FactAttribute` 派生类、`DataAttribute.GetData`、`ITraitAttribute.GetTraits` 都是"特性对自身行为负责"的具体化;`xunit3-extension` 模板给出 `netstandard2.0` + `xunit.v3.extensibility.core` 的最小形态。
- 自定义 Fact 可以把 `Skip + SkipUnless + SkipType` 三件套封装进构造函数;分析器照常把派生特性当测试声明(xUnit1069 等照常触发),但构造函数里赋的属性名不受 xUnit1054 检查,用 `nameof` 自保。
- `$XunitDynamicSkip$` 前缀是运行时动态跳过的开关:消息以此开头的异常 = 跳过,其余部分是原因;无前缀 = 失败。特性级条件要静态可引用的 bool 属性;`Before` 钩子能做任意运行时探测,但那时测试类已构造、`Before` 已在跑。
- 自定义数据源实现 `GetData` 与 `SupportsDiscoveryEnumeration` 两个抽象成员;数据行元数据要经 `ConvertDataRow` 才会把特性上的 Label/Skip/Traits 套到行上;预枚举让每行成为独立用例,原生 runner 默认关闭(`-preEnumerateTheories` 打开)。
- 预枚举要求每行可序列化;`IXunitSerializer` + `[assembly: RegisterXunitSerializer(typeof(序列化器), typeof(支持的类型))]` 让自定义类型逐行可运行,否则框架发诊断并退回单测试用例。
- `ITestPipelineStartup` 在命令行解析后、任何发现/执行前运行,发现-only 也运行;诊断走 `StartAsync` 给的 sink,不走尚未接好的 `TestContext`。可复用测试库:包引用(`extensibility.core` + `assert`)放库上,沿项目引用传递;runner 包只进可执行测试工程;库与框架版本对齐。
- 跨仓库分发用 `dotnet pack`(零额外配置即可打,`lib/<TFM>/` 随目标框架走)+ 私有源;同解决方案用项目引用即可。扩展的克制标准:同一模式出现三次以上、触发条件可判定、行为不变才封装;否则留在辅助方法或静态数据源。
