# 第 6 章 · 并行执行与顺序

> 你将学会:
>
> - 理解 xUnit 的默认并行模型:测试集合是什么,为什么"集合间并行、集合内串行"是默认值
> - 用真实输出(报告头部、时间窗、墙钟时间)证明某个测试组到底有没有并行
> - 用具名或强类型的测试集合把多个类合并成一个串行单元
> - 用 4.0 的 `[assembly: Parallelization(...)]` 配置并行模式、线程数与调度算法,并用命令行临时覆盖
> - 在集合、类、方法、数据源、数据行五个层级选择性退出并行,以及每一层只在哪种模式下生效
> - 理解默认执行顺序的"稳定随机"机制,用排序器(orderer)需要时钉死顺序,用唯一 ID 与过滤选项复现并行下的失败

单元测试彼此独立,所以可以安全地同时跑;而现代开发机有几十个 CPU 线程,一次只跑一个测试是把硬件浪费掉。xUnit.net 从 v2 起就把并行设为默认行为,v3 4.0 更进一步:除了默认的按集合并行(`collections`)与完全不并行(`none`),还新增了让所有测试彼此并行的 `all` 模式,并配套了从集合到数据行五个层级的"退出并行"开关。本章把这些机制全部展开,并用真实运行输出证明每一个结论;第 5 章留下的问题——"把类放进同一个集合为什么会得到串行"——在这里给出完整的解释。

本章的工程是 [`code/Ch06.Parallel`](../code/Ch06.Parallel)。所有输出片段来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2(32 线程 CPU)的真实运行;过长的类名显示与报告属性用 `…` 省略,其余逐字保留。时间窗证据里的 `HH:mm:ss.fff` 时间戳和 `thread=` 线程号,来自测试自己通过 `TestContext.Current.TestOutputHelper` 写出的输出,配合原生 runner 的 `-showLiveOutput` 按执行次序实时打印。

## 6.1 默认并行模型:测试集合

xUnit 调度的基本单位不是测试类,也不是单个测试,而是**测试集合(test collection)**。默认规则只有一条:**每个测试类自动属于一个只包含它自己的集合**。在此之上,并行模型定义三种模式:

| 模式 | 语义 |
| --- | --- |
| `none` | 整个程序集内所有测试逐个执行 |
| `collections`(默认) | 不同集合并行,同一集合内串行 |
| `all`(4.0 新增) | 所有测试与所有其它测试并行,集合不再构成边界 |

默认模式下,"两个互不相干的类"就是两个集合,它们彼此并行;同一个类里的两个测试同属一个集合,它们串行。运行任何一次测试时,runner 都会把实际采用的模式报告出来——这一行在启用诊断消息(`-diagnostics`)后出现在报告头部:

```text
Starting:    Ch06.Parallel (parallel mode = collections [32 threads], stop on fail = off, explicit = off, seed = 92831001)
```

`[32 threads]` 是并行使用的线程上限,默认等于 CPU 线程数。把两个各占住线程 1 秒的测试放进两个类([`ParallelModelTests.cs`](../code/Ch06.Parallel/ParallelModelTests.cs)),时间窗是否重叠就是并行与否的直接证据:

```csharp
public sealed class SlowWindowAlphaTests
{
    [Fact]
    public void Alpha_HoldsTheThreadForOneSecond() =>
        HoldWindow.Await("alpha", 1000);
}

public sealed class SlowWindowBetaTests
{
    [Fact]
    public void Beta_HoldsTheThreadForOneSecond() =>
        HoldWindow.Await("beta", 1000);
}
```

`HoldWindow.Await` 把开始/结束时刻与承载线程写进测试输出(完整实现见工程文件)。默认模式下只跑这两个类:

```text
    Ch06.Parallel.Tests.SlowWindowBetaTests.… [OUTPUT] [beta] start  22:58:48.348 thread=7
    Ch06.Parallel.Tests.SlowWindowAlphaTests.… [OUTPUT] [alpha] start  22:58:48.348 thread=4
    Ch06.Parallel.Tests.SlowWindowAlphaTests.… [OUTPUT] [alpha] end    22:58:49.354 after 1006ms thread=4
    Ch06.Parallel.Tests.SlowWindowBetaTests.… [OUTPUT] [beta] end    22:58:49.354 after 1006ms thread=7
   Ch06.Parallel  Total: 2, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 1.092s
```

两个测试同一毫秒开始、在不同线程上重叠,总耗时约 1 秒——并行。同一个命令加 `-parallelMode none`:

```text
Starting:    Ch06.Parallel (parallel mode = none, stop on fail = off, explicit = off, seed = 92831001)
    Ch06.Parallel.Tests.SlowWindowBetaTests.… [OUTPUT] [beta] start  22:58:49.579 thread=6
    Ch06.Parallel.Tests.SlowWindowBetaTests.… [OUTPUT] [beta] end    22:58:50.586 after 1007ms thread=6
    Ch06.Parallel.Tests.SlowWindowAlphaTests.… [OUTPUT] [alpha] start  22:58:50.599 thread=6
    Ch06.Parallel.Tests.SlowWindowAlphaTests.… [OUTPUT] [alpha] end    22:58:51.599 after 1000ms thread=6
   Ch06.Parallel  Total: 2, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 2.087s
```

时间窗首尾相接、全程同一个线程,总耗时约 2 秒——串行。注意这两个演示类**没有任何关于并发的断言**:并行是调度决策,"有没有真的同时跑"受机器负载影响,写成断言就会带来不稳定;并行的证据用输出和时间找,断言只用来证明"确定不会发生"的事(6.2 节)。

## 6.2 把多个类合并进同一个集合

默认"一类一集合"意味着类与类之间默认并行。当几个类共享可变资源(同一份缓存、同一个临时目录、一个非线程安全的静态注册表),就把它们放进**同一个具名集合**——它们与彼此串行,与其它集合仍然并行([`SharedCollectionTests.cs`](../code/Ch06.Parallel/SharedCollectionTests.cs)):

```csharp
[Collection("billing")]
public sealed class BillingWindowOneTests
{
    [Fact]
    public void WindowOne_RunsSeriallyWithinBilling()
    {
        using (Probes.Shared.Enter("billing"))
            HoldWindow.Await("billing-1", 1000);
        Assert.Equal(1, Probes.Shared.MaxActive("billing"));
    }
}

[Collection("billing")]
public sealed class BillingWindowTwoTests
{
    [Fact]
    public void WindowTwo_RunsSeriallyWithinBilling()
    {
        using (Probes.Shared.Enter("billing"))
            HoldWindow.Await("billing-2", 1000);
        Assert.Equal(1, Probes.Shared.MaxActive("billing"));
    }
}
```

这里有两层互补的证据。断言层:`Probes.Shared` 是一个线程安全的并发观测器([`Production/ConcurrencyProbe.cs`](../code/Ch06.Parallel/Production/ConcurrencyProbe.cs),用 `ConcurrentDictionary` 上的原子更新记录每个作用域的峰值并发),两个类共用作用域 `"billing"`,`MaxActive("billing") == 1` 断言"这个作用域里从未同时存在两个测试"——这是**确定性的**,因为同集合串行是框架承诺,不管两个测试谁先跑都成立。时间层,完整运行中的真实时间窗:

```text
    Ch06.Parallel.Tests.BillingWindowOneTests.… [OUTPUT] [billing-1] start  22:58:01.813 thread=14
    Ch06.Parallel.Tests.BillingWindowOneTests.… [OUTPUT] [billing-1] end    22:58:02.818 after 1005ms thread=14
    Ch06.Parallel.Tests.BillingWindowTwoTests.… [OUTPUT] [billing-2] start  22:58:02.819 thread=14
    Ch06.Parallel.Tests.BillingWindowTwoTests.… [OUTPUT] [billing-2] end    22:58:03.819 after 1000ms thread=14
```

`billing-2` 在 `billing-1` 结束后 1 毫秒才开始——集合内串行;而同一时刻 `alpha`/`beta` 正在别的线程上跑(本章代码里那条 `-diagnostics -showLiveOutput` 全量运行的输出)——集合间并行不受影响。

**强类型集合**是同一机制的编译安全写法:定义类不带名字,测试类用泛型特性直接指向它:

```csharp
[CollectionDefinition]
public sealed class AuditTrailCollection;

[Collection<AuditTrailCollection>]
public sealed class AuditWindowOneTests { /* 与 AuditWindowTwoTests 同集合,串行 */ }
```

字符串名字的问题在于拼错不会报错:`[Collection("billng")]` 会悄悄挂出一个只有自己的新集合,串行保证消失,要到某次偶发竞态才暴露;指向类型则拼错就编译不过。第 5 章的集合夹具用的正是这套机制——`[CollectionDefinition]` + `ICollectionFixture<T>` 定义共享夹具,`[Collection<TDef>]` 同时带来夹具共享与集合内串行。并行模型与共享范围是同一枚硬币的两面:**要共享可变状态,就先声明它属于同一个集合**。

## 6.3 程序集级配置:模式、线程数与算法

4.0 用 `Xunit.v3` 命名空间下的 `ParallelizationAttribute` 统一了程序集级并行配置(枚举 `ParallelMode`、`ParallelAlgorithm` 在 `Xunit.Sdk` 命名空间);v2 与 v3 早期分散在 `CollectionBehaviorAttribute` 上的 `DisableTestParallelization` / `MaxParallelThreads` / `ParallelAlgorithm` 属性已全部过时:

```csharp
using Xunit.Sdk;
using Xunit.v3;

// …(文件头部注释解释了它与旧 CollectionBehavior 的取代关系,此处省略)…
[assembly: Parallelization(Mode = ParallelMode.Collections)]
```

三个属性都可省略,省略即保持默认:

| 属性 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `Mode` | `ParallelMode` | `Collections` | `None` / `Collections` / `All`,语义见 6.1 |
| `MaxThreads` | `int` | CPU 线程数 | 并行线程上限;`-1` 表示不限 |
| `Algorithm` | `ParallelAlgorithm` | `Conservative` | 调度算法,见下 |

**算法取舍。** `conservative`(默认)一次只*启动*不超过 `MaxThreads` 个测试,等一个结束才启动下一个:时间测量准确,`Timeout` 在并行下仍然可靠,对任务调度系统压力小;代价是大量时间在 `await` 上挂起的异步重测试会吃不满 CPU。`aggressive` 是旧算法:不管上限先尽量启动,靠 `SynchronizationContext` 限制同时在跑的数量——异步重测试的吞吐更好,但被挂起再恢复的测试计时不准,`Timeout` 不可靠。官方建议:默认用 `conservative`,只有当测试明显偏慢时才考虑换。算法只在模式不是 `none` 且线程数有限时参与调度(不限线程时无从"限制")。

配置可以被 runner 在更高层覆盖,优先级从低到高:

| 层级 | 写法 |
| --- | --- |
| 代码 | `[assembly: Parallelization(Mode = ParallelMode.None)]` |
| `xunit.runner.json`(所有 runner) | `"parallelMode": "none"`、`"maxParallelThreads": 2`、`"parallelAlgorithm": "aggressive"`(旧配置里的 `parallelizeTestCollections: false` 在 4.0 自动映射为 `parallelMode: "none"`) |
| `testconfig.json`(仅 MTP) | `"xUnit": { "parallelMode": … }` 同名键 |
| 命令行 | 最高,见下 |

**从早期版本迁移。** 较早版本通过 `CollectionBehavior` 配置程序集级并行;4.0.2 把这些设置集中到 `ParallelizationAttribute`。关闭程序集并行可写成 `Mode = ParallelMode.None`;如果旧项目依赖特定的集合划分方式,升级时应检查每个测试类所属的集合,确保共享状态仍有预期的串行边界。

`xunit.runner.json` 中的线程上限仍可通过 `maxParallelThreads` 配置。项目迁移时应以实际引用的框架版本为准;本章当前写法见 [`ParallelAssemblyConfig.cs`](../code/Ch06.Parallel/ParallelAssemblyConfig.cs)。

原生 runner(`dotnet run` / 直接跑产物)的开关:

```shell
$ ./Ch06.Parallel -parallelMode none          # none | collections | all
$ ./Ch06.Parallel -maxThreads 2 -diagnostics   # 头部变为 … collections [2 threads] …
$ ./Ch06.Parallel -parallelAlgorithm aggressive
# 头部变为 … collections [32 threads/aggressive] …
```

`dotnet test`(MTP 模式)对应 `--parallel none|collections|all`、`--max-threads`、`--parallel-algorithm`。同一程序集在两种命令行下的墙钟对比,只跑 6.1 的两个慢类:

```shell
$ dotnet test --project Ch06.Parallel -- --filter-class "Ch06.Parallel.Tests.SlowWindow*"
  …/Ch06.Parallel.dll (net10.0|x64) passed (4s 227ms)
  duration: 4s 348ms
$ dotnet test --project Ch06.Parallel -- --parallel none --filter-class "Ch06.Parallel.Tests.SlowWindow*"
  …/Ch06.Parallel.dll (net10.0|x64) passed (5s 073ms)
  duration: 5s 191ms
```

(`duration` 含固定的进程启动开销,所以绝对值比原生 runner 的 `Time:` 大;两次差出的约 0.8 秒正是并行被关掉后两个 1 秒睡眠不再重叠。)

一个诚实的提醒:`all` 模式会打破"集合内串行"的默认保证。本章项目里 `billing`/`audit` 集合的 `MaxActive == 1` 断言依赖这条保证,用 `-parallelMode all` 跑全项目它们会失败(实测 4 个)。这不是 bug,是语义:要评估 `all` 模式的影响,先用 `--filter-class` 圈出与共享状态无关的类试跑。

## 6.4 选择性退出并行(4.0)

`all` 模式把"哪些东西不与我并行"的控制权交给了每个测试自己。4.0 提供五个层级的退出开关,共同规则:**一旦在某层退出并行,不能在更低层再进入**;每一层只在对应模式下有意义:

| 层级 | 写法 | 生效模式 |
| --- | --- | --- |
| 测试集合 | `[CollectionDefinition("name", DisableParallelization = true)]` | `collections`、`all` |
| 测试类 | `[TestClass(DisableParallelization = true)]` | 仅 `all`(`collections` 下类即集合,本就串行) |
| 测试方法 | `[Fact(DisableParallelization = true)]`、`[Theory(…)]` 同理 | 仅 `all` |
| 数据源 | `[InlineData(…, DisableParallelization = true)]`(作用于该特性产出的所有行;其它数据特性同理) | 仅 `all` |
| 数据行 | `new TheoryDataRow<string>("…") { DisableParallelization = true }`(第 4 章预告的兑现) | 仅 `all` |

退出并行的含义是强保证:**该测试与任何其它测试都不会同时运行**,不是"和某些东西排队"。

**集合级。** 定义类上开 `DisableParallelization`(注意属性名是 `DisableParallelization`,官方文档个别处写作 `DisableParallelism`,以编译为准):

```csharp
[CollectionDefinition("nightly-window", DisableParallelization = true)]
public sealed class NightlyWindowCollection;
```

默认模式下,`nightly` 集合的两个测试被调度到整场运行的末尾,逐个独占执行——`nightly-1` 的开始时刻(03.822)晚于全场最后一个其它测试的结束(`billing-2` 的 03.819):

```text
    Ch06.Parallel.Tests.NightlyWindowOneTests.… [OUTPUT] [nightly-1] start  22:58:03.822 thread=14
    Ch06.Parallel.Tests.NightlyWindowOneTests.… [OUTPUT] [nightly-1] end    22:58:04.422 after 600ms thread=14
    Ch06.Parallel.Tests.NightlyWindowTwoTests.… [OUTPUT] [nightly-2] start  22:58:04.424 thread=14
    Ch06.Parallel.Tests.NightlyWindowTwoTests.… [OUTPUT] [nightly-2] end    22:58:05.024 after 600ms thread=14
```

(排在末尾是这次调度器的安排,不是承诺;承诺是"绝不与任何其它测试重叠"。)

**类级与方法级。** 用 `-parallelMode all` 只跑相关类,时间窗把语义展示得清清楚楚:

**数据源与数据行级。** 数据特性与数据行的元数据上都有同名开关,粒度是"这一行数据与别的测试不并行":

```csharp
[Theory]
[InlineData("runs-in-parallel")]
[InlineData("isolated-by-attribute", DisableParallelization = true)]
public void Rows(string expectation) =>
    HoldWindow.Await($"data-source:{expectation}", 300);

// ── 另一个测试类(DataRowOptOutTests)里的数据源方法 ──
public static IEnumerable<TheoryDataRow<string>> IsolatedAndParallelRows()
{
    yield return new TheoryDataRow<string>("runs-in-parallel");
    yield return new TheoryDataRow<string>("isolated-by-row") { DisableParallelization = true };
}
```

某一行需要独占(比如它会重启一个共享服务),其它行照常并行,就写行级;整个数据特性产出的行都要独占,就写数据源级。默认 `collections` 模式下这些开关一律被忽略——同一 Theory 的所有行本来就同属一个集合(跑一次本章代码里的 `./Ch06.Parallel -diagnostics -showLiveOutput`,输出里 `data-row:runs-in-parallel → data-row:isolated-by-row` 正是背靠背同线程)。

## 6.5 共享状态与并行的安全准则

并行不是需要对抗的敌人,而是"测试互不相干"这条纪律的放大器。按优先级排序的安全准则:

1. **能不共享就不共享。** xUnit 每个测试新建一个测试类实例(第 5 章),构造器里的状态天然私有;测试类字段不需要任何线程安全考虑。
2. **要共享,先选对范围,再进集合并行边界。** 类内共享用 `IClassFixture<T>`,跨类共享用集合夹具,全局共享用程序集夹具(第 5 章)。类夹具与集合夹具都落在某个集合边界内,集合边界同时就是串行边界;程序集夹具跨所有集合,必须自己线程安全。
3. **需要串行时用集合,不用锁。** 给共享资源的所有使用者打上同一个 `[Collection(...)]`,串行由框架保证,没有死锁、没有锁粒度问题,也不拖慢其它集合。测试体里的 `lock` 只能保护单个测试进程内的代码,保护不了"另一个集合的测试正在改数据库"这种局面。
4. **必须跨集合共享可变状态时,共享对象自己线程安全。** 本章的 `ConcurrencyProbe` 就是示范:`ConcurrentDictionary` + 原子更新,按作用域键隔离计数,所以它可以安全地是一个 `static readonly` 单例——第 5 章警告的是"普通 static 字段被并行的测试互相踩",线程安全 + 键隔离是它合法的两种解法。
5. **断言方向选对。** "不会并发"是框架承诺,可以用计数断言(6.2 的 `MaxActive == 1`);"会并发"是调度事实,只能用时间窗和墙钟观察(6.1),写成断言就是不稳定。

## 6.6 执行顺序:默认的"稳定随机"

顺序没有任何保证——这是设计,不是缺陷。`RandomOrderDemoTests` 里六个方法按 `DeclaredFirst`…`DeclaredSixth` 声明,该类不做任何顺序断言,只把"我何时执行"写进输出;`-showLiveOutput` 下真实次序:

```text
    …RandomOrderDemoTests.DeclaredFifth [OUTPUT] executed: DeclaredFifth
    …RandomOrderDemoTests.DeclaredSixth [OUTPUT] executed: DeclaredSixth
    …RandomOrderDemoTests.DeclaredFourth [OUTPUT] executed: DeclaredFourth
    …RandomOrderDemoTests.DeclaredFirst [OUTPUT] executed: DeclaredFirst
    …RandomOrderDemoTests.DeclaredSecond [OUTPUT] executed: DeclaredSecond
    …RandomOrderDemoTests.DeclaredThird [OUTPUT] executed: DeclaredThird
```

与声明顺序无关,像随机。但它**稳定**:同一台机器、同一路径下重复运行,次序逐次一致(上面的次序在多次运行中一字不差地复现)。v3 从 3.0.1 起不再用伪随机数决定顺序,而是按测试与测试集合的**唯一 ID** 排序——ID 由程序集磁盘路径等元数据派生,报告尾部能看到程序集 ID:

```text
  Finished:    Ch06.Parallel (ID = '6df949c2080c4c0289a824b5bd72a983602e61f056893c643bc1637e9a50fe62')
```

好处是顺序对本地开发者"看起来随机"(能暴露顺序耦合),又跨运行可复现;代价是**换环境可能换顺序**——本地全绿、CI 上偶发红,常常是这条引起的。配置项里剩下的 `seed` 是旧机制的遗留,官方文档明说"现在基本不使用",只在第三方自定义测试用例等回退场景参与。

由此得出设计原则(第 5 章已见过两个反例):测试之间不传递状态、不依赖前后跑;需要前后关系(状态机演示、迁移链)就把它们写进**同一个测试方法**,或者用 6.7 的排序器显式声明。

## 6.7 排序器:需要顺序时显式声明

4.0 的排序分四级,依次生效:**集合 → 类 → 方法 → 用例**。四个接口都在 `Xunit.v3` 命名空间,方法为泛型方法(元素类型约束到 `Xunit.Sdk` 的标记接口,运行时实例总同时实现 `Xunit.v3.IXunitTest*` 模型接口,元数据从后者读取):

| 接口 | 方法 | 排序特性 | 可作用位置 |
| --- | --- | --- | --- |
| `ITestCollectionOrderer` | `OrderTestCollections` | `[assembly: TestCollectionOrderer(typeof(…))]` | 仅程序集 |
| `ITestClassOrderer` | `OrderTestClasses` | `[TestClassOrderer(typeof(…))]` | 程序集、类 |
| `ITestMethodOrderer` | `OrderTestMethods` | `[TestMethodOrderer(typeof(…))]` | 程序集、类 |
| `ITestCaseOrderer` | `OrderTestCases` | `[TestCaseOrderer(typeof(…))]` | 程序集、类、方法 |

(特性类在 `Xunit` 命名空间,4.0 另有等价的泛型形式 `TestCollectionOrdererAttribute<T>` 等,.NET 8+ 可用。)

最小实现:`OrderTestMethods` 按 `MetadataToken`(与编译顺序一致,即源码声明顺序)返回方法([`Orderers/DeclarationOrderMethodOrderer.cs`](../code/Ch06.Parallel/Orderers/DeclarationOrderMethodOrderer.cs)):

```csharp
public sealed class DeclarationOrderMethodOrderer : ITestMethodOrderer
{
    public IReadOnlyCollection<TTestMethod?> OrderTestMethods<TTestMethod>(
        IReadOnlyCollection<TTestMethod?> testMethods)
        where TTestMethod : ITestMethod =>
        [.. testMethods.OrderBy(m => ((IXunitTestMethod)m!).MetadataToken)];
}
```

打在类上只影响该类([`OrderedExecutionTests.cs`](../code/Ch06.Parallel/OrderedExecutionTests.cs)),其余测试仍保持默认随机:

```csharp
[TestMethodOrderer(typeof(DeclarationOrderMethodOrderer))]
public sealed class DeclarationOrderDemoTests
{
    // 声明顺序即期望执行顺序;排序器负责把默认的随机顺序"扶正"为声明顺序。
    [Fact]
    public void Alpha_RunsFirst() => Record("alpha");
    [Fact]
    public void Bravo_RunsSecond() => Record("bravo");
    [Fact]
    public void Charlie_RunsThird() => Record("charlie");
    // …Record:登记次序、输出 order #N、断言位置…
}
```

真实运行:

```text
    …DeclarationOrderDemoTests.Alpha_RunsFirst [OUTPUT] order #1: alpha
    …DeclarationOrderDemoTests.Bravo_RunsSecond [OUTPUT] order #2: bravo
    …DeclarationOrderDemoTests.Charlie_RunsThird [OUTPUT] order #3: charlie
   Ch06.Parallel  Total: 3, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 0.083s
```

与 6.6 相反,这些顺序断言在重复运行下是稳定的——排序器把顺序钉死了。对照实验:临时注释掉类上的特性再跑,`charlie` 第一个执行,三条位置断言全红:

```text
    …DeclarationOrderDemoTests.Charlie_RunsThird [OUTPUT] order #1: charlie
    …DeclarationOrderDemoTests.Charlie_RunsThird [FAIL]
   Ch06.Parallel  Total: 3, Errors: 0, Failed: 3, …
```

分析器 xUnit3004 会检查特性里的类型确实实现了对应接口,写错接口立刻编译报错。

## 6.8 并行下的调试:复现顺序与定位失败

并行 + 随机顺序下调试偶发失败,按这个顺序来:

**1. 先判断是否与顺序/并行有关。** 用 `-parallelMode none` 再跑一遍:仍然失败,是普通 bug,与并发无关;不失败了,继续往下。

**2. 复现顺序:锁定唯一 ID。** 顺序由程序集 ID 派生,而 ID 默认来自磁盘路径——本地与 CI 路径不同,顺序就可能不同。把失败环境的 ID 写进测试程序集旁边的同名 `.uniqueid` 文件,即可在另一台机器上复现同一顺序(实测):

```shell
$ cat bin/Debug/net10.0/Ch06.Parallel.uniqueid
abc123
$ ./Ch06.Parallel -class "Ch06.Parallel.Tests.RandomOrderDemoTests" -showLiveOutput
    …RandomOrderDemoTests.DeclaredFourth [OUTPUT] executed: DeclaredFourth
    …RandomOrderDemoTests.DeclaredFirst [OUTPUT] executed: DeclaredFirst
    …RandomOrderDemoTests.DeclaredThird [OUTPUT] executed: DeclaredThird
    …
  Finished:    Ch06.Parallel (ID = 'abc123')
```

ID 变了(来自文件内容),这组测试的次序也随之改变——这就是"用 ID 控制顺序"的开关。

**3. 缩小到单个测试。** 原生 runner 用 `-method "全名"` / `-class "前缀*"`,MTP 用 `--filter-method` / `--filter-class`(实测 `Total: 1` / `total: 1`):

```shell
$ ./Ch06.Parallel -method "Ch06.Parallel.Tests.RandomOrderDemoTests.DeclaredFifth"
$ dotnet test --project Ch06.Parallel -- --filter-method "Ch06.Parallel.Tests.RandomOrderDemoTests.DeclaredFifth"
```

单个测试稳定失败而全量偶发失败,多半是共享状态;用 `-diagnostics` 看头部确认实际生效的模式与线程数,用 `-showLiveOutput` 的时间窗找重叠的对手。

**4. 修它。** 让测试真正独立(首选),或者把共享它状态的所有类合并进同一集合(6.2),或者给肇事者加退出并行开关(6.4)。

## 动手练习

1. **计时对比。** 写两个测试类,各含一个占住线程 2 秒的测试。先用默认模式、再用 `-parallelMode none` 各跑一次,记录两次 `Time:` 与两个测试的时间窗。验收:两次 `Time:` 相差约 2 秒,前者的时间窗重叠、后者首尾相接。
2. **一个类内的并行。** 给练习 1 的两个类都加 `[Collection("pair")]`,不加任何模式开关再跑。验收:时间窗重新变成首尾相接,而 `SlowWindow` 演示类仍然与它们并行(时间窗与其它类重叠)。
3. **字母序类排序器。** 实现 `ITestClassOrderer`,按 `TestClassName` 对类排序,程序集级启用,造两个类(`Zebra…`、`Alpha…`)各输出自己的类名。验收:`-showLiveOutput` 中 `Alpha…` 的输出总是先于 `Zebra…`,重复运行三次不变;注释掉排序器后至少出现一次相反次序(或说明为何这次没有)。

## 本章小结

- xUnit 的并行单位是测试集合;默认"一类一集合",`collections` 模式下集合间并行、集合内串行;`none` 全串行;`all`(4.0)所有测试彼此并行。实际生效的模式、线程数、seed 在报告头部可见(需 `-diagnostics`)。
- 把多个类放进同一个具名或强类型集合即得到串行保证;强类型写法把拼错名字从"偶发竞态"变成"编译错误"。集合是共享可变状态的正确边界——要串行用集合,不用锁。
- 程序集级配置 4.0 起用 `[assembly: Parallelization(Mode, MaxThreads, Algorithm)]`(`Xunit.v3` / `Xunit.Sdk`),取代旧 `CollectionBehavior` 的并行属性;`xunit.runner.json`、`testconfig.json`、命令行逐级覆盖。算法默认 `conservative`(计时准确),异步重负载才考虑 `aggressive`。
- 五个层级的 `DisableParallelization`(集合定义、类、方法、数据源、数据行)只在对应模式生效:集合级对 `collections` 与 `all` 有效,其余仅 `all`;退出并行的测试与任何其它测试绝不重叠,且不能在更低层再进入并行。
- 默认执行顺序是"稳定随机":按测试唯一 ID 排序,同路径下重复可复现,换环境可能改变;`seed` 基本不再参与。测试不要依赖顺序,依赖顺序的结构要么合并,要么用排序器声明。
- 四级排序链 collection → class → method → case,四个接口在 `Xunit.v3`,特性在 `Xunit`(程序集级,部分可打到类/方法);实现一个 `ITestMethodOrderer` 只需一个 `OrderBy(MetadataToken)`。
- 调试并行失败:`-parallelMode none` 定性质,`.uniqueid` 复现顺序,`-method`/`--filter-*` 定位测试,然后用独立性、集合或退出开关修复。
