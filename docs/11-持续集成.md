# 第 11 章 · 持续集成

> 你将学会:
> - 说清 `dotnet test` 在 .NET 10 SDK 下为什么走 MTP 模式、[`global.json`](../code/global.json) 是按什么规则被找到的,以及找不到时你会看到什么
> - 分清一次 `dotnet test` 命令行里哪些是构建选项(`--no-restore`、`--configuration`)、哪些是测试运行器选项(`--filter-trait`、`--report-xunit-junit`),以及两种传法在 SDK 10 上的实测差别
> - 用一份可直接复制的 GitHub Actions 工作流模板,把还原缓存、分层测试、报告与覆盖率产物上传接成一条流水线
> - 用 traits 把 unit / smoke / integration 拆进不同 job,并用 `--fail-skips on`、`--minimum-expected-tests`、`--ignore-exit-code` 把"假绿"变成红灯
> - 用 `--results-directory` 固定报告落点,让 `upload-artifact` 的路径永远匹配
> - 排查"本地全绿、CI 偶发红":先定性(并发还是顺序),再定位(过滤器重跑),最后修独立性

本章的工程是 [`code/Ch11.Ci`](../code/Ch11.Ci)。被测代码在 [`Production/`](../code/Ch11.Ci/Production/):`RunEnvironment`(环境判定)、`DeploymentInventory`(构建产物清单)、`GatePolicy`(构建门禁)、`ArtifactStore`(把清单写到真实磁盘)。工作流模板在 [`Ch11.Ci/ci/github-actions-example.yml`](../code/Ch11.Ci/ci/github-actions-example.yml)。所有输出片段来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2 的真实运行,绝对路径以 `...` 缩写。

一个环境细节(与第 7 章相同):我本机 shell 里恰好带着 `CI=true`,所以下文"本地场景"的命令写成 `env -u CI ...`,CI 场景写成 `CI=1 ...`。GitHub Actions 的每个 job 都自动带有 `CI=true`(GitHub 文档的默认环境变量),所以 `CI=1` 就是 CI 上的真实情形。本章命令除特别说明外都在 `code/` 目录下执行。

## 11.1 CI 里的测试工程运行模型

### 11.1.1 global.json 决定 dotnet test 走哪条路

第 1 章说过:[`code/global.json`](../code/global.json) 里的这一段让 `dotnet test` 走 MTP 模式——它是整个测试工具链(过滤器、报告、覆盖率、退出码)的开关,必须随仓库提交:

```json
{
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

CI 上最容易踩的坑:**SDK 是从当前工作目录向上查找 [`global.json`](../code/global.json) 的,不是从 `--project` 指向的目录**。本教程的 [`global.json`](../code/global.json) 在 `code/` 下,同一条命令换个目录跑,结果完全不同。在 `code/` 下:

```console
$ dotnet test --project Ch11.Ci --filter-trait kind=smoke
...
Test run summary: Passed!
  total: 4
  succeeded: 4
```

退到仓库根目录(那里没有 [`global.json`](../code/global.json)),`dotnet test` 退回 VSTest 模式,报的是一句莫名其妙的 MSBuild 错误:

```console
$ cd ..
$ dotnet test --project code/Ch11.Ci --filter-trait kind=smoke
MSBUILD : error MSB1001: Unknown switch.
    Full command line: '/usr/share/dotnet/sdk/10.0.113/MSBuild.dll ... --property:VSTestArtifactsProcessingMode=collect ... --target:VSTest ... --project code/Ch11.Ci --filter-trait kind=smoke -restore ...'
Switch: --project
```

命令行里出现 `--target:VSTest` 就是证据:根本没进 MTP。结论到 CI 上只有一句话:**工作流里所有 `dotnet` 命令的工作目录,必须是能向上找到 [`global.json`](../code/global.json) 的目录**。本章的模板用 `defaults.run.working-directory: code` 解决;你自己的仓库把 [`global.json`](../code/global.json) 放仓库根目录,这个问题就不存在。

### 11.1.2 一条命令,两层选项

`dotnet test` 的命令行里混着两类选项:

| 类别 | 例子 | 谁消费 |
| --- | --- | --- |
| 构建/SDK 选项 | `--no-restore`、`--configuration Release`、`--project` | dotnet CLI / MSBuild |
| 测试运行器选项 | `--filter-trait`、`--report-xunit-junit`、`--fail-skips`、`--coverage` | MTP(第 7、9、10 章) |

官方文档在 .NET SDK 8/9 那一节要求把测试选项写在 `--` 之后(`dotnet test -- --filter-class ClassName`),SDK 10 那一节的示例则直接写 `dotnet test --filter-class ClassName`。实测在 SDK 10 上,不加 `--` 直接写 MTP 选项也能透传:

```console
$ dotnet test --project Ch11.Ci --filter-trait kind=unit
  total: 9        # 不加 -- 也生效
```

两种写法都实测可用,但建议 CI 脚本里统一用 `--` 分隔:构建选项和运行器选项的命名空间是各自演化的,今天不冲突不代表以后不冲突(`--results-directory` 在 VSTest 时代就有自己的含义),`--` 把边界写死,读的人不用猜。

`--no-restore` 与 `--configuration Release` 是 CI 脚本的标配:还原单独一步(缓存命中与否在日志里看得见),测试跑 Release(和被部署的产物一致)。本章工作流里的完整命令 11.2 逐段解释。

### 11.1.3 退出码决定构建成败

CI 判定成败的依据只有一条:进程退出码。非 0,步骤失败,job 失败。MTP 的退出码表在第 10 章(0 成功、2 至少一条失败、8 零命中、9 少于 `--minimum-expected-tests`……),本章会用到其中的 2、8、9,并且每个都有真实输出。原生 runner 没有这套细分码:实测有失败一律返回 1(失败 1 条和 3 条都是 1),零命中和全跳过都返回 0,命令行参数写错返回 3(第 10 章 10.6)。所以 CI 上必须保证走的是 MTP(11.1.1)。

## 11.2 一份可直接使用的工作流模板

模板文件在 [`Ch11.Ci/ci/github-actions-example.yml`](../code/Ch11.Ci/ci/github-actions-example.yml),把它复制到你仓库的 `.github/workflows/ci.yml`(本教程示例工程在 [`code/Ch11.Ci`](../code/Ch11.Ci),自己项目里去掉路径里的 `code/` 前缀即可)。模板里每一条 `run` 命令都在本机真实执行过,下文引用的输出就是执行结果。

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: "30 18 * * *" # nightly 层:每天 UTC 18:30

# 所有 run 步骤都在 code/ 下执行:dotnet CLI 从当前工作目录向上查找 global.json,
# 找不到就退回 VSTest 模式——xUnit v3 的 MTP 集成(报告、覆盖率、--filter-trait)全部消失。
defaults:
  run:
    working-directory: code

jobs:
  unit-smoke:
    name: unit + smoke(每次 push / PR 必跑)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      # 仓库里提交了 packages.lock.json(dotnet restore --use-lock-file 生成),
      # setup-dotnet 的 NuGet 全局包缓存以它作缓存键;restore 用 --locked-mode 校验一致性。
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: "10.0.x"
          cache: true
          cache-dependency-path: "**/packages.lock.json"

      - name: Restore(锁定模式,校验 packages.lock.json)
        run: dotnet restore Ch11.Ci --locked-mode

      # 分层过滤:这个 job 只跑 unit 与 smoke 两层;
      # 报告写进固定的 TestResults 目录(相对当前工作目录,即 code/TestResults),
      # 便于下一步 upload-artifact 用固定路径收集。
      - name: Test(unit + smoke)
        run: >
          dotnet test --project Ch11.Ci --no-restore --configuration Release
          --filter-trait kind=unit --filter-trait kind=smoke
          --report-xunit-junit --report-xunit-ctrf
          --results-directory TestResults

      # if: always() —— 测试红了也要上传报告,红了没报告等于白跑
      - name: Upload test reports
        if: ${{ always() }}
        uses: actions/upload-artifact@v4
        with:
          name: unit-smoke-reports
          path: code/TestResults/

  integration:
    name: integration(覆盖率;不允许跳过)
    runs-on: ubuntu-latest
    env:
      # 集成层的前提:一个可写目录。测试代码只认 CH11_STORE_DIR 这一个入口(11.4)。
      CH11_STORE_DIR: ${{ runner.temp }}/ch11-store
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: "10.0.x"
          cache: true
          cache-dependency-path: "**/packages.lock.json"

      - name: Restore(锁定模式)
        run: dotnet restore Ch11.Ci --locked-mode

      # --fail-skips on:这一层的测试若被跳过(前提没配好)直接判失败——
      # "集成 job 绿但什么都没跑"是最危险的假绿。
      # --coverage-settings 只认绝对路径,用 ${{ github.workspace }} 拼。
      - name: Test(integration,skips fail the job)
        run: >
          dotnet test --project Ch11.Ci --no-restore --configuration Release
          --filter-trait kind=integration --fail-skips on
          --coverage --coverage-output-format cobertura
          --coverage-settings "${{ github.workspace }}/code/Ch11.Ci/coverage.runsettings"
          --report-xunit-junit
          --results-directory TestResults

      - name: Upload coverage and reports
        if: ${{ always() }}
        uses: actions/upload-artifact@v4
        with:
          name: integration-results
          path: code/TestResults/

  nightly:
    name: nightly 层(仅定时触发;允许零命中)
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: "10.0.x"
          cache: true
          cache-dependency-path: "**/packages.lock.json"

      - name: Restore(锁定模式)
        run: dotnet restore Ch11.Ci --locked-mode

      # kind=nightly 这一层目前一条都没有:过滤器合法落空,退出码 8
      # 被 --ignore-exit-code 8 豁免成 0(11.6)。
      - name: Test(nightly layer, zero hits allowed)
        run: >
          dotnet test --project Ch11.Ci --no-restore --configuration Release
          --filter-trait kind=nightly --ignore-exit-code 8
```

逐段说明:

- **触发器。** push/PR 跑 unit+smoke,integration 也每次跑(本章的集成层只有三条,测试步骤本机 5 秒上下);nightly 用 `schedule` 定时,`if: github.event_name == 'schedule'` 让它在 push/PR 下直接判 skipped——不参与,也不空跑。`schedule` 有两个 GitHub 文档写明的前提:它只在默认分支上生效(所以 nightly 跑的永远是默认分支的最新提交),并且负载高时会被推迟(整点附近尤其明显)。nightly 的结论适合看趋势,不适合当合并门禁。
- **`working-directory: code`。** 11.1.1 的坑在这里修:所有 `run` 步骤在 `code/` 下执行,[`global.json`](../code/global.json) 能被找到,`dotnet test` 走 MTP。
- **setup-dotnet@v4 + 缓存。** `dotnet-version: "10.0.x"` 显式钉 SDK(GitHub 的 ubuntu-latest 镜像预装了 .NET 10,但显式声明不依赖镜像更新节奏)。`cache: true` 开启 NuGet 全局包缓存,**它要求仓库里有 `packages.lock.json` 作缓存键**,没有匹配的锁文件这个 action 会直接失败。生成方法(本机已执行):`cd code && dotnet restore Ch11.Ci --use-lock-file`,然后把 [`Ch11.Ci/packages.lock.json`](../code/Ch11.Ci/packages.lock.json) 提交进仓库;之后的还原用 `--locked-mode`,锁文件与 csproj 不一致时还原直接报错——依赖漂移从"偶发的红"变成"还原期就红"。
- **`--no-restore`。** 还原已经单独一步,测试步骤不再重复还原;还原失败会在自己的步骤里失败,日志归日志、测试归测试。
- **`--configuration Release`。** 测的就是要部署的产物。注意输出目录随之变成 [`bin/Release/net10.0/`](../code/Ch11.Ci/bin/Release/net10.0/),下文报告路径同理。
- **`--results-directory TestResults`。** 固定落点,11.5 展开。
- **`upload-artifact` + `if: always()`。** 默认步骤在测试失败时被跳过——恰恰是最需要报告的时候。`always()` 保证红构建也带着 JUnit/覆盖率下车。`path` 不吃 `defaults.run.working-directory`(那个默认值只作用于 `run` 步骤),action 步骤按运行器给它的当前目录解析,也就是仓库根(`GITHUB_WORKSPACE`),所以写 `code/TestResults/`。

## 11.3 测试分层:unit / smoke / integration 各跑各的

第 7 章用 `kind` trait 给测试分层,本章把它接到 CI job 上。工程里的分层(类级 `[Trait("kind", "...")]`,见各测试文件):

| 层 | 类 | 数量 | 边界 |
| --- | --- | --- | --- |
| unit | `UnitDeploymentTests`、`GateEnvironmentTests` | 9 | 纯内存,不碰磁盘/网络/环境 |
| smoke | `SmokeDeploymentTests`、`OrderCoupledTests` | 4 | 毫秒级,只验证形状与默认配置 |
| integration | `IntegrationStoreTests` | 3 | 真的写磁盘读回来 |

每层的过滤器与真实计数(本机运行,`CI=1` 即 CI 场景):

```console
$ CI=1 dotnet test --project Ch11.Ci --no-restore --configuration Release --filter-trait kind=unit
  total: 9
  succeeded: 8
  skipped: 1

$ dotnet test --project Ch11.Ci --no-restore --configuration Release --filter-trait kind=smoke
  total: 4
  succeeded: 4

$ CI=1 CH11_STORE_DIR=/tmp/gh-runner-temp/ch11-store dotnet test --project Ch11.Ci \
    --no-restore --configuration Release --filter-trait kind=integration --fail-skips on
  total: 3
  succeeded: 3
  skipped: 0
```

同一个 trait 键重复传是 OR(第 7 章),所以 `--filter-trait kind=unit --filter-trait kind=smoke` 恰好命中 13 条——就是工作流 unit-smoke job 的那条命令,它的真实摘要:

```console
Test run summary: Passed!
  total: 13
  failed: 0
  succeeded: 12
  skipped: 1
```

这个分层在 CI 上换来三件事:unit+smoke job 最先给出 PR 初判(这 13 条的测试步骤本机 4 秒内跑完,慢的是 checkout/还原这些公共步骤);integration job 独占覆盖率收集(覆盖率只统计"真实执行过的代码",分层跑时把 `--coverage` 放在跑得最全的那个 job 里,或者每个 job 各出一份再合并;11.5.2 有两个真实数字对比);某层的失败不掩盖另一层的结论——job 名就是分类。

注意 unit 那次的 `skipped: 1`:那是 11.4 的环境分支对——unit job 里它是合法的,所以 unit job 不加 `--fail-skips`;哪些 job 该加,11.4 说。

## 11.4 环境与条件执行:本地跳过,CI 必须跑

### 11.4.1 CI 判定集中在一个类里

第 7 章的模式原样沿用:判定集中一处,测试只读结论([`Production/RunEnvironment.cs`](../code/Ch11.Ci/Production/RunEnvironment.cs)):

```csharp
public static bool IsCi => !string.IsNullOrEmpty(Environment.GetEnvironmentVariable("CI"));

public static string? StoreDirectory =>
    Environment.GetEnvironmentVariable("CH11_STORE_DIR") is { Length: > 0 } value ? value : null;
```

`GatePolicy.FromEnvironment()` 把"CI 更严格"编进生产代码:CI 上不允许任何跳过,本地允许。这个判定本身也有测试——按第 7 章的模式,两个分支各一条,每条只守自己的分支([`GateEnvironmentTests.cs`](../code/Ch11.Ci/GateEnvironmentTests.cs)):

```csharp
[Fact]
public void GatePolicy_FromEnvironment_FailsSkipsOnCi()
{
    Assert.SkipUnless(RunEnvironment.IsCi, "本次运行没有 CI 环境变量,CI 分支由另一条用例守");

    Assert.True(GatePolicy.FromEnvironment().FailSkips);
}

[Fact]
public void GatePolicy_FromEnvironment_AllowsSkipsLocally()
{
    Assert.SkipWhen(RunEnvironment.IsCi, "本次运行是 CI,本地分支由另一条用例守");

    Assert.False(GatePolicy.FromEnvironment().FailSkips);
}
```

同一条命令(11.3 那条 unit+smoke 的 `--filter-trait kind=unit --filter-trait kind=smoke`),两种环境各绿各的(真实输出,只看摘要):`CI=1` 下跳过的是 `AllowsSkipsLocally`(原因"本次运行是 CI,……"),`env -u CI` 下跳过的是 `FailsSkipsOnCi`(原因"本次运行没有 CI 环境变量,……"),两次都是 `total: 13, succeeded: 12, skipped: 1`——被跳过的永远是"这次不该判断"的那一条。GitHub Actions 自动给每个 job 设 `CI=true`,所以 CI 上永远走第一分支——这正是第 7 章"两个分支各留一条用例"比"本地整个跳过"强的地方:CI 分支的行为也被测到了。

### 11.4.2 集成层:前提由环境提供,跳过必须可解释

集成测试不自己发明前提,只消费 `CH11_STORE_DIR`(工作流的 integration job 用 `${{ runner.temp }}` 下的一次性目录配好它):

```csharp
private const string SkipReason =
    "集成层未配置:设置 CH11_STORE_DIR=<可写目录> 后再运行这一层(CI 的集成 job 会自动设置)";

[Fact]
public void Store_SaveThenLoad_RoundTripsAllArtifacts()
{
    Assert.SkipUnless(RunEnvironment.StoreDirectory is not null, SkipReason);
    ...
}
```

本地默认没有这个变量,三条集成测试跳过,原因里写清了怎么让它们跑起来。真配上目录,它们真的在磁盘上留下东西(本机运行后的真实文件树):

```console
$ CI=1 CH11_STORE_DIR=/tmp/ch11-store dotnet test --project Ch11.Ci --filter-trait kind=integration
  total: 3
  succeeded: 3

$ find /tmp/ch11-store -type f
/tmp/ch11-store/Store_ManifestIsPlainJson_OnDisk/inventory.json
/tmp/ch11-store/Store_SaveThenLoad_RoundTripsAllArtifacts/inventory.json
/tmp/ch11-store/Store_SecondSave_ReplacesManifest/inventory.json
```

### 11.4.3 `--fail-skips on`:集成 job 不允许"假绿"

集成 job 最怕的不是红,是"绿得可疑":前提没配好,三条全跳过,摘要 `skipped: 3`,job 照样绿。`--fail-skips on`(第 7、10 章)把这种绿判成红。没配变量时(模拟工作流里 `env:` 被删掉的坏情形):

```console
$ CI=1 dotnet test --project Ch11.Ci --no-restore --configuration Release \
    --filter-trait kind=integration --fail-skips on
failed Ch11.Ci.Tests.IntegrationStoreTests.Store_SaveThenLoad_RoundTripsAllArtifacts (0ms)
  Xunit.MicrosoftTestingPlatform.XunitException: FAIL_SKIP : 集成层未配置:设置 CH11_STORE_DIR=<可写目录> 后再运行这一层(CI 的集成 job 会自动设置)
...
Exit code: 2
Test run summary: Failed!
  total: 3
  failed: 3
```

配上变量就全绿(11.3 第三条命令)。规则:**`--fail-skips on` 只加在"这一层的测试必须真的跑起来"的 job 上**——集成 job 加;unit job 不加,因为它里面合法地住着环境分支对(11.4.1),加了就把正确行为判成错误。

## 11.5 报告与产物:固定落点,红构建也要能下车

### 11.5.1 `--results-directory` 的相对路径按当前工作目录解析

第 10 章的默认落点是 `bin/<配置>/<tfm>/TestResults/`——路径随配置(Release/Debug)变,`upload-artifact` 的 `path` 就得跟着猜。CI 上把它钉死:

```console
$ # 在 code/ 下执行
$ dotnet test --project Ch11.Ci --no-restore --configuration Release \
    --filter-trait kind=unit --filter-trait kind=smoke \
    --report-xunit-junit --report-xunit-ctrf --results-directory TestResults
...
  In process file artifacts produced:
    - .../code/TestResults/lindesty_homearch_2026-10-23_04_42_37.666701.ctrf
    - .../code/TestResults/lindesty_homearch_2026-10-23_04_42_37.666701.junit.xml

$ find TestResults -type f
TestResults/lindesty_homearch_2026-10-23_04_42_37.666701.ctrf
TestResults/lindesty_homearch_2026-10-23_04_42_37.666701.junit.xml
```

关键事实(实测):`--results-directory TestResults` 的相对路径按**当前工作目录**解析,落进了 `code/TestResults/`,不是工程目录也不是输出目录。所以工作流里"在 `code/` 下运行 + `--results-directory TestResults` + `path: code/TestResults/`"三者是同一条路径链。文件名保持自动命名(`用户_机器_日期_时间`),多 job/多工程不互相覆盖(第 10 章的告诫)。

### 11.5.2 各格式接进 CI 的方式

格式选型第 10 章已做,这里只接管线:

JUnit——给测试报告器/聚合工具消费,计数在头部,跳过带原因:

```xml
<testsuites name="Test results" tests="13" failures="0" errors="0" disabled="0" ...>
  <testsuite name=".../bin/Release/net10.0/Ch11.Ci.dll" tests="13" ... skipped="1" ...>
    <testcase name="Ch11.Ci.Tests.GateEnvironmentTests.GatePolicy_FromEnvironment_AllowsSkipsLocally"
              time="0.000000" classname="Ch11.Ci.Tests.GateEnvironmentTests">
      <skipped>本次运行是 CI,本地分支由另一条用例守</skipped>
    </testcase>
```

CTRF——给仪表盘消费,**测试的 trait 会进 `labels`**(第 10 章),所以仪表盘上能直接按 `kind` 切片:

```json
"summary": {"tests": 13, "passed": 12, "failed": 0, "skipped": 1, ...}
{"name": "Ch11.Ci.Tests.UnitDeploymentTests.Inventory_TotalBytes_SumsAllArtifacts",
 "status": "passed", "labels": {"kind": "unit"}}
```

覆盖率——`--coverage --coverage-output-format cobertura` 生成 `.cobertura.xml`,配 `coverage.runsettings`(`IncludeTestAssembly` + 只统计 `Ch11.Ci.Production`,原因见第 10 章)。`--coverage-settings` 只认绝对路径,工作流里用 `${{ github.workspace }}` 拼;写成相对路径不会得到"文件找不到",而是整个运行崩掉(摘要 `Zero tests ran`、退出码 1,SDK 里一句 `KeyNotFoundException`)——和第 10 章 10.5 那个形状一样。下面这份报告来自"所有层都跑上"的一次运行(配好 `CH11_STORE_DIR`、不加过滤器,命令见"本章代码"):

```xml
<coverage line-rate="1" ...>
  <packages>
    <package name="Ch11.Ci" line-rate="1" ...>
      <classes>
        <class name="Ch11.Ci.Production.GatePolicy" ...>
```

只跑 integration 层时,同一个位置是 `line-rate="0.634"`:`ArtifactStore` 和清单是 1,而 `GatePolicy`、`RunCounts`、`GateDecision` 整类 0,`RunEnvironment` 只有 `StoreDirectory` 那半条被调用(`0.5`)——集成层根本没碰门禁。这就是 11.3 那句"把 `--coverage` 放在跑得最全的那个 job 里"的具体含义:报出一个覆盖率数字之前,先说清它是哪次运行、跑了哪些层算出来的。

三种文件都落在同一个固定目录,一次 `upload-artifact` 全部带走。

## 11.6 失败排查:本地全绿,CI 偶发红

### 11.6.1 先判断是否与顺序/并发有关

第 6 章的排查流程在 CI 语境下的完整版。本章工程里住着一个故意保留的反面教材([`OrderCoupledTests.cs`](../code/Ch11.Ci/OrderCoupledTests.cs)):两条测试通过静态字段传递状态,类上加了方法排序器把声明顺序钉死,所以完整运行永远全绿:

```csharp
[TestMethodOrdererAttribute(typeof(DeclarationOrderMethodOrderer))]
[Trait("kind", "smoke")]
public class OrderCoupledTests
{
    private static string? deploymentMarker;

    [Fact]
    public void A_WritesDeploymentMarker() => deploymentMarker = "deployed";

    [Fact]
    public void B_ReadsDeploymentMarker() => Assert.Equal("deployed", deploymentMarker);
}
```

CI 上最常见的触发点是"只重跑失败用例"式的过滤器——它把 B 单独选中,前面的 A 不再执行,本地怎么跑都绿的测试在 CI 上红了:

```console
$ dotnet test --project Ch11.Ci --filter-method "Ch11.Ci.Tests.OrderCoupledTests.B_ReadsDeploymentMarker"
failed Ch11.Ci.Tests.OrderCoupledTests.B_ReadsDeploymentMarker (7ms)
  Assert.Equal() Failure: Strings differ
  Expected: "deployed"
  Actual:   null
    at Ch11.Ci.Tests.OrderCoupledTests.B_ReadsDeploymentMarker() in .../OrderCoupledTests.cs:21
...
Test run summary: Failed!
  total: 1
  failed: 1
```

第一步定性(第 6 章):用原生 runner 加 `-parallelMode none` 再跑。仍然红,说明不是并发竞态,而是顺序/状态耦合:

```console
$ ./Ch11.Ci/bin/Debug/net10.0/Ch11.Ci -method "Ch11.Ci.Tests.OrderCoupledTests.B_ReadsDeploymentMarker" -parallelMode none
    Ch11.Ci.Tests.OrderCoupledTests.B_ReadsDeploymentMarker [FAIL]
      Assert.Equal() Failure: Strings differ
      Expected: "deployed"
      Actual:   null
```

第二步复现顺序:如果红与"哪条先跑"有关,用第 6 章实测过的 `.uniqueid` 文件把失败环境的顺序钉到本地复现(顺序由程序集 ID 派生,ID 默认来自磁盘路径——CI 与本地路径不同,顺序就可能不同;`.uniqueid` 放在测试程序集旁边即可覆盖)。第 6 章还实测了 `-diagnostics` 报告头部里的 `seed` 与并行配置。

第三步修根:让 B 自己准备状态,不读别人留下的东西。排序器只是把反面教材钉在原地,不是修复。

### 11.6.2 分层过滤的零命中:exit 8 的两种处理

nightly job 的过滤器命中零条测试时(本工程的 `kind=nightly` 一条都没有),MTP 以退出码 8 结束:

```console
$ dotnet test --project Ch11.Ci --no-restore --configuration Release --filter-trait kind=nightly
...
Test run completed with non-success exit code: 8 (see: https://aka.ms/testingplatform/exitcodes)
$ echo $?
8
```

"这个过滤器允许落空"就用 `--ignore-exit-code 8` 表达——nightly job 的那条命令,同一个过滤器,退出码 0:

```console
$ dotnet test --project Ch11.Ci --no-restore --configuration Release --filter-trait kind=nightly --ignore-exit-code 8
Test run summary: Zero tests ran
  total: 0
$ echo $?
0
```

反过来,如果零命中一定是配错了(trait 名拼错、测试被误删),不要用 `--ignore-exit-code` 掩盖,用 `--minimum-expected-tests` 把下限写进命令。它和零命中检查是叠加的:命中太少,即使全过也红:

```console
$ dotnet test --project Ch11.Ci --no-restore --configuration Release --filter-trait kind=smoke --minimum-expected-tests 5
Test run summary: Minimum expected tests policy violation, tests ran 4, minimum expected 5
  total: 4
  failed: 0
  succeeded: 4
  skipped: 0
Test run completed with non-success exit code: 9 (see: https://aka.ms/testingplatform/exitcodes)
$ echo $?
9
```

退出码 9(少于要求的最小值)在第 10 章的表里。两个开关的选择标准只有一条:**这次落空是合法状态,还是配错了。**

## 11.7 工程实践:什么进版本库,什么留在命令行

第 10 章 10.7 的划分在 CI 语境下补全:

| 进版本库 | 本章里的文件 | 理由 |
| --- | --- | --- |
| [`global.json`](../code/global.json) | [`code/global.json`](../code/global.json) | 没有它,CI 上的 `dotnet test` 连 MTP 都进不去(11.1.1) |
| `xunit.runner.json` / `testconfig.json` | 工程根目录 | 项目恒定的行为,本地与 CI 一致 |
| `coverage.runsettings` | 工程根目录 | 覆盖率口径必须全团队一致 |
| `packages.lock.json` | `dotnet restore --use-lock-file` 生成 | setup-dotnet 缓存的键;依赖漂移在还原期暴露 |
| 工作流文件 | `.github/workflows/` | 流水线的结构也是代码 |

留在 CI 命令行的:报告开哪几种、覆盖率开不开、门禁(`--fail-skips`、`--minimum-expected-tests`、`--ignore-exit-code`)、过滤(`--filter-trait`)——都是"这次运行"的决定,不是项目的属性(第 10 章)。

两个 CI 特有的默认值要心里有数:

- **并行线程数默认等于 CPU 逻辑核数。** 第 6 章实测本机(32 核)报告头部是 `parallel mode = collections [32 threads]`;GitHub 标准 ubuntu runner 只有 4 核(公开仓库;私有仓库 2 核),同一套测试在 CI 上的并行度只有本机的零头。依赖计时的测试(第 8 章)在共享 runner 上天然更脆:同样的 `Timeout`,在争抢 CPU 的 runner 上更容易踩线。解法是按第 8 章把 token 传全、把计时断言改成事件断言,而不是把超时调大——调大只是把偶发红推远到下次。
- **跳过与零命中的默认值都不拦人。** 默认 `skipped` 不算失败、零命中 exit 8 也只在 MTP 侧存在(原生 runner 对零命中返回 0,摘要里 `Total: 0`)。CI 的严格是配出来的:`--fail-skips on`、`--minimum-expected-tests`,按 job 的语义逐个加,别全局一刀切(11.4.3)。

## 动手练习

1. **复现一次"假绿"再把它变红。** 不带 `CH11_STORE_DIR` 跑 `--filter-trait kind=integration`:验收摘要是 `total: 3, skipped: 3` 且退出码 0("绿得可疑");再加 `--fail-skips on`:验收是 `failed: 3`、退出码 2、失败消息里有 `FAIL_SKIP :` 和你写的跳过原因;最后配上变量:验收是 `succeeded: 3`、退出码 0,`/tmp` 下出现三条 `inventory.json`。
2. **修掉反面教材。** 用 `--filter-method` 单独运行 `B_ReadsDeploymentMarker`,确认它红(11.6.1 的输出)。然后修改 `OrderCoupledTests`:让 B 自己写入再读回(不再依赖 A),并删掉排序器。验收:单独运行 B 变绿;`dotnet test --project Ch11.Ci` 仍然全绿;`--filter-trait kind=smoke` 的 `total` 不变。
3. **让 nightly job 真的跑东西。** 给 `Store_ManifestIsPlainJson_OnDisk` 再打一个 `[Trait("kind", "nightly")]`(同名方法级 Trait 叠加,第 7 章),然后不带 `--ignore-exit-code` 跑 nightly 的过滤命令(配好 `CH11_STORE_DIR`)。验收:它不再是零命中,退出码 0;说明这时 `--ignore-exit-code 8` 还该不该留在命令里。

## 本章小结

- `dotnet test` 走 MTP 靠的是从**当前工作目录**向上找到的 [`global.json`](../code/global.json);CI 上工作目录不对,就退回 VSTest 模式并报出莫名其妙的 MSBuild 错误——`working-directory` 或把 [`global.json`](../code/global.json) 放仓库根。
- 命令行分两层:构建选项归 SDK,测试选项归 MTP,用 `--` 划界(SDK 10 实测不加也能透传,但 `--` 把边界写死)。退出码就是构建成败,MTP 的细分退出码见第 10 章的表。
- 工作流模板的骨架:checkout → setup-dotnet(锁文件缓存)→ `restore --locked-mode` → 分层 `dotnet test` → `upload-artifact`(`if: always()`)。每条命令本机可复跑。
- traits 分层 + `--filter-trait` 让 job 与测试层一一对应;同键多值是 OR。`--fail-skips on` 只加在"必须真跑"的 job 上;环境分支对的合法跳过提醒我们:门禁是按 job 语义配的。
- CI 判定(`CI` 变量)与前提开关(`CH11_STORE_DIR`)集中在 `RunEnvironment`;两个分支各一条用例,CI 分支的行为也被测到。
- `--results-directory` 的相对路径按当前工作目录解析——固定它,`upload-artifact` 的 `path` 才永远匹配;JUnit 给报告器、CTRF 的 `labels` 给仪表盘、cobertura 给覆盖率平台,红构建也要上传。
- 排查顺序:先 `-parallelMode none` 定性(竞态还是顺序),再 `.uniqueid`/seed 复现顺序(第 6 章),最后修独立性;"只重跑失败用例"的过滤器是顺序耦合最常见的触发点。
- 零命中 exit 8:合法落空用 `--ignore-exit-code 8`,配错了用 `--minimum-expected-tests`(exit 9)。并行默认线程数 = CPU 核数,共享 runner 下计时测试更脆——修测试,不调大超时。
