# 第 13 章 · 结语与进阶路线

> 你将收获:一张全书能力地图、一份日常工程速查清单、继续深入 xUnit.net 的四条路线与权威资料入口。

本章没有新的示例工程。它做三件事:把前十二章串成一张可检索的地图;把全书实测过的关键结论压缩成速查清单;指出离开本教程后值得继续学习的内容。

## 13.1 能力地图:你在这十二章里学到了什么

| 能力 | 对应章节 | 核心手段 |
| --- | --- | --- |
| 建立正确的测试观 | 第 1–2 章 | AAA、命名即文档、Fact/Theory 判定、测试与生产代码的组织 |
| 精确地验证行为 | 第 3 章 | `Equal`/`Equivalent`/`StrictEqual` 的分工、集合与异常断言、`Assert.Multiple`、自定义断言 |
| 用数据覆盖输入空间 | 第 4 章 | `InlineData`/`MemberData`/`ClassData`、`TheoryData` 强类型、数据行元数据、`MatrixTheoryData` |
| 管理测试的共享状态 | 第 5 章 | 每测试新实例的模型、`IDisposable`/`IAsyncLifetime`、类/集合/程序集三级夹具与选型 |
| 掌控执行方式 | 第 6 章 | 测试集合模型、`Parallelization` 三模式、五层级退出并行、四个排序器、稳定随机与复现 |
| 控制哪些测试该跑 | 第 7 章 | 静态/动态/异常驱动跳过、Explicit、Traits、简单过滤器与查询过滤语言 |
| 控制测试跑多久 | 第 8 章 | `Timeout` 的真实语义、`CancellationToken` 透传链、`CancelCurrentTest`、挂起检测 |
| 让失败可诊断 | 第 9 章 | `ITestOutputHelper`、诊断消息、警告与附件、`KeyValueStorage`、调试手法 |
| 把测试接入工程 | 第 10 章 | `xunit.runner.json`/`testconfig.json`、六种报告格式、覆盖率与门禁 |
| 把测试接入 CI | 第 11 章 | GitHub Actions 工作流、分层过滤、产物上传、退出码语义 |
| 扩展框架本身 | 第 12 章 | 自定义 Fact/Data 特性、`$XunitDynamicSkip$`、序列化器、管道启动、可复用测试库 |

一个健康的测试工程,这十一类能力通常以同一个顺序相互支撑:先有可读的单个测试(1–3),再有数据与共享状态管理(4–5),然后才轮到执行策略(6–8)与工程化(9–11),最后才是框架扩展(12)。倒序建设(先搭宏大夹具与并行基建,再抱怨测试难读)是常见的弯路。

## 13.2 速查清单:全书实测过的关键结论

以下每一条都在本教程的工程里真实运行过,可直接作为 code review 检查项:

**编写**
- `Assert.Equal` 对集合做序列比较;跨 CLR 类型的按值比较用 `Assert.Equivalent`;lambda 里直接 throw(表达式体、或只含 throw 的块体)都会绑到已过时重载(CS0619),先把代码存进 `Action` 变量再交给 `Throws<T>`。
- 数据行的显示名属性是 `TestDisplayName`,不是 `DisplayName`;`Assert.All` 空集合默认放行,需要 `throwIfEmpty: true`。
- 特性级 `SkipUnless/SkipWhen` 必须同时设置 `Skip` 作为跳过消息,否则测试直接失败。

**生命周期与并行**
- 每个测试都新建测试类实例:构造器/`Dispose` 是类级 setup/teardown;跨类共享状态用夹具,不要静态可变字段。
- `IAsyncLifetime` 在 v3 继承 `IAsyncDisposable`,方法是 `ValueTask`;同时实现两种 Dispose 时框架只调 `DisposeAsync`。
- 并行退出特性拼写是 `DisableParallelization`(不是 `DisableParallelism`);除集合级(对 `collections` 与 `all` 都有效)之外,类级/方法级/数据源级/数据行级的退出只在 `ParallelMode.All` 下生效。
- 顺序不是资产:默认随机且稳定;需要顺序就实现排序器,怀疑顺序引发偶发失败就用 `.uniqueid` 文件钉住运行。

**执行控制**
- `Timeout` 不会强杀测试:它只把 `TestContext.Current.CancellationToken` 置为已取消。失败在时限那一刻判定;没接令牌的代码继续在进程里跑,而 runner 不保证等它,它后来抛的异常以 `[Test Cleanup Failure]` 单独报告(分析器 xUnit1069/1051 会提醒透传令牌)。
- Explicit 用于"手动验证"的测试;自动生成的跳过要留可搜索的原因。
- 零命中过滤器在 MTP 下退出码 8;CI 分层过滤时用 `--ignore-exit-code 8` 或保证每层非空。

**工程化**
- 报告选项用 4.0 的新名字(`--report-xunit-xml`/`--report-xunit-junit`…):MTP 下旧名被判成无效参数(测试模块 exit 5,日志里是 `Handshake failures`),原生 runner 的旧名(`-junit`/`-xml`)只是弃用警告,改用 `-result-*`;JUnit 报告不含附件,xUnit XML 报告含 `<warnings>`/`<attachments>`。
- [`global.json`](../code/global.json) 按当前工作目录向上查找:CI 工作流要在跑测试的步骤里定位到含 [`global.json`](../code/global.json) 的目录,否则退回已不被 .NET 10 SDK 支持的 VSTest 路径。
- 被测代码在测试程序集内时,覆盖率需要 `IncludeTestAssembly=True`;`--coverage-settings` 只认绝对路径。
- 配置进版本库(`xunit.runner.json`/`testconfig.json`),环境相关的开关留在命令行。

## 13.3 进阶路线

离开本教程后,四条路线按常见需求排序:

### 1. Native AOT:让测试也进入 AOT 发布链路

xUnit.net v3 从 4.0 起支持 Native AOT(只支持 C#,最低目标框架 .NET 9):用 `xunit.v3.aot.*` 包族(`xunit.v3` → `xunit.v3.aot`、`xunit.v3.assert` → `xunit.v3.assert.aot` 等),测试用例由源生成器登记,不依赖反射。代价是部分反射型 API 在 AOT 模式下不可用(会被条件性标记为过时),自定义扩展需要配套源生成器。适合关注启动时间、产物体积或在 AOT 流水线里跑测试的读者:见官方 [Testing with Native AOT](https://xunit.net/docs/getting-started/v3/native-aot)。

### 2. Microsoft Testing Platform 扩展生态

本教程用了 MTP 的测试运行与覆盖率扩展,但它是一个开放平台:报告、遥测、平台集成都可以以 NuGet 扩展形式接入(`Microsoft.Testing.Extensions.*`)。你的测试工程本身就是一个 MTP 应用,也可以对外提供自定义命令行选项。入口:[MTP 扩展文档](https://learn.microsoft.com/dotnet/core/testing/unit-testing-platform-extensions)。顺带一提:MTP 默认遥测可用环境变量 `TESTINGPLATFORM_TELEMETRY_OPTOUT=1` 关闭。

### 3. 更深的框架扩展

第 12 章停在"特性与数据"这一层。再往下有:自定义结果写入器(`IConsoleResultWriter`/`IMicrosoftTestingPlatformResultWriter` + `RegisterResultWriterAttribute`,4.0 起可完全脱离 XSL-T)、自定义 runner reporter(`[assembly: RegisterRunnerReporter]` 把它链进测试程序集,再用 `-reporter` 选择)。这类 reporter 目前仅由测试程序集内的 in-process console runner 支持;多程序集 console/MSBuild runner 与 VSTest adapter(`dotnet test`、Test Explorer)不支持自定义 reporter,见官方[自定义 runner reporter 文档](https://xunit.net/docs/getting-started/v3/custom-runner-reporter)。再往下还有替换整个测试框架的 `ITestFramework`。这类扩展会直接接触 v3 的对象模型与消息管道,动手前先读 [Migrating Extensibility](https://xunit.net/docs/getting-started/v3/migration-extensibility) 与 [API 文档](https://api.xunit.net/)。

### 4. 存量 v2 工程的迁移

维护中的旧工程升 v3 的路径:包名换 `xunit.v3.*`、`OutputType` 改 `Exe`、目标框架升到 v3 支持的下限(`net8.0` 或 `net472`,见第 1 章)、再按断言与命名空间的差异逐项修。完整清单在官方 [迁移指南](https://xunit.net/docs/getting-started/v3/migration)。官方 [2.9.3 发布说明](https://xunit.net/releases/v2/2.9.3)称该版预计是 v2 Core Framework 的最后一版,[发布索引](https://xunit.net/releases/)也将 v2 标为维护状态;新项目或需要 v3 新能力的项目可优先评估 v3,存量工程是否及何时迁移则按兼容性与升级风险决定。

## 13.5 把知识落到项目里

学习完各章后,可以选一个小型业务改动,把测试技能接入日常开发流程:

1. 选一个可观察的行为,为正常值、边界值和失败路径写测试,再按需要选择 `Fact` 或 `Theory`。
2. 把测试命令加入持续集成,失败时保存测试报告,让每次改动都有可追踪的结果。
3. 当测试之间出现重复的设置逻辑时,先确认共享范围和隔离要求,再决定是否引入 fixture 或抽出测试支持库。

## 本章小结

- 本教程的十二章可以在日常工作中当"检查表"使用:写测试看 1–5,调执行看 6–8,做工程看 9–11,写扩展看 12。
- 所有关键结论(包括官方文档与实现不一致的几处)都以真实运行输出为准——这也是本教程最重要的方法论:对工具的行为保持怀疑,用最小实验取得事实。
- 进阶方向按需求选择:性能与 AOT、MTP 扩展生态、框架深水区、v2 迁移;每一条都有官方文档作为起点。
