# 第 8 章 · 超时与取消

> 你将学会:
> - 用 `[Fact(Timeout = ms)]` / `[Theory(Timeout = ms)]` 给测试设毫秒级时限,并读懂超时失败在两个 runner 里的形态(含 `FailureCause` 分类的概念)

## 8.1 Timeout:毫秒级时限,同步测试也生效

`Timeout` 是 `FactAttribute` / `TheoryAttribute` 上的 `int` 属性,单位毫秒。v2 里它只允许用在 async 测试上;v3 取消了这个限制——同步测试同样可以设时限(官方 v3 变更说明明确写了这一点,本节下面就用一条纯同步测试实测)。数据行级的 `Timeout`(单行一个时限)第 4 章已经演示过(`TheoryDataRow.WithTimeout(...)`);本章讲特性级和它背后的语义。

[`TimeoutSemanticsTests.cs`](../code/Ch08.Timeouts/TimeoutSemanticsTests.cs) 里,一条纯同步测试把时限交给生产代码去"接":

```csharp
/// <summary>8.1:v3 的 Timeout 对同步测试同样生效;生产代码每轮检查令牌,200ms 处被截停。</summary>
[Fact(Timeout = 200, Skip = "演示:去掉 Skip 复现同步测试的超时失败(见 8.1)")]
public void AuditLoop_ObservesToken_StopsAtTimeout()
{
    var snapshot = Enumerable.Range(0, 200).Select(i => new LedgerEntry($"SKU-{i}", i)).ToList();
    StocktakeAggregator.AuditLedger(snapshot, rounds: 50_000_000, TestContext.Current.CancellationToken);
}
```

[`Production/StocktakeAggregator.cs`](../code/Ch08.Timeouts/Production/StocktakeAggregator.cs) 没有任何 `await`,取消只能靠主动检查令牌:

```csharp
/// <summary>做 rounds 轮全表扫描;每轮开头检查一次令牌,取消一到就抛 OperationCanceledException。</summary>
public static int AuditLedger(
    IReadOnlyList<LedgerEntry> snapshot, int rounds, CancellationToken cancellationToken)
{
    var discrepancies = 0;

    for (var round = 0; round < rounds; round++)
    {
        cancellationToken.ThrowIfCancellationRequested();

        foreach (var entry in snapshot)
            if (entry.Quantity < 0)
                discrepancies++;
    }

    return discrepancies;
}
```

### 8.1.2 FailureCause:失败会被分类

v3 的测试结果消息(`ITestFailed`)里有一个 `FailureCause` 字段,把失败分成 `Assertion` / `Timeout` / `Exception`(外加 `Other` / `Unknown` 两个兜底)。分类靠运行时检查异常实现的接口名:实现了名为 `IAssertionException` 的接口算断言失败,实现了 `ITestTimeoutException` 的算超时失败——只认接口名,不要求命名空间,第三方断言库不需要引用 xUnit 就能参与分类。控制台里你看到的对应物就是 8.1 那个 `failed (canceled)` 标记和 `Test execution timed out after N milliseconds` 消息;写报告解析器或第三方集成时,读的是消息对象里的这个字段。

## 8.2 超时的真实语义:不强杀,只发信号

官方 v3 变更说明里最重要的一句:**超时的测试不会被强行停止**;框架做的事是把 `TestContext.Current.CancellationToken` 置为已取消。这个令牌同时承载两种取消:超时,以及用户请求取消测试运行。所以"设了 Timeout 的测试"的正确写法,是让测试体能观察这个信号:

- 把令牌**透传**给所有可取消的 API:`Task.Delay(ms, token)`、`HttpClient.SendAsync(request, token)`、`CancellationTokenSource.CreateLinkedTokenSource(token)`;
- CPU 循环里主动 `token.ThrowIfCancellationRequested()`;
- 调用自己写的生产方法时,把令牌作为参数一路传下去,而不是让生产代码"自己想办法"。

把这些观察合起来,超时语义的完整图景是:

1. **失败在时限到的那一刻判定**,不用等测试跑完(两条反例正例都 ~(100ms) 报出)。
2. **测试本身没有被中止**。传了令牌的测试会在信号处主动结束(正例);没传令牌的测试继续占用执行资源,直到自然结束或进程退出——原生 runner 基本在判定后立刻退出(实测 0.18s 上下),MTP 有时等到被放弃的测试自然结束(实测 3s 多),有时提前退出(实测 0.6s~1.6s)。哪种情况都不改变"失败已经判定"这个事实。
3. 被放弃的测试后来如果抛异常,会以 `[Test Cleanup Failure ...]` 单独出现(8.1 里那条 `OperationCanceledException` 就是);如果它正常跑完,则什么也不会追加。

**坑:超时失败不是断言失败。** 它的消息是 `Test execution timed out after N milliseconds`,不是任何 `Assert.*` 的输出。排查时别去翻断言,直接看测试里哪个等待没有接令牌。

上面的反例不用等到运行才暴露——编译期就有两条分析器盯着。把 8.2 反例代码的 `#pragma` 去掉再编译,真实警告:


### 8.4.1 把令牌设计成参数链:可取消的生产代码

超时和取消能不能生效,取决于生产代码有没有给令牌留通道。[`Production/StockFeedClient.cs`](../code/Ch08.Timeouts/Production/StockFeedClient.cs) 的约定是:**会等待的公开方法一律带 `CancellationToken` 参数,并把它传到真正等待的地方**(这里是 `Task.Delay`,真实项目里是 `HttpClient`/`Socket`)。类里唯一不守这条约定的是 `FetchSnapshotBlocking`,它是故意留下来的反例:遗留的同步方法不接受令牌,`Thread.Sleep` 卡住之后外部无从取消——这种代码一旦出现在测试调用链上,`Timeout` 就只能"判定失败",拿不回执行权。

```csharp
/// <summary>分页拉取快照:每页等待 pageDelayMs,令牌透传给 Task.Delay,取消立即生效。</summary>
public async Task<IReadOnlyList<LedgerEntry>> FetchSnapshotAsync(
    int pages = 3, CancellationToken cancellationToken = default)
{
    var entries = new List<LedgerEntry>();

    for (var page = 0; page < pages; page++)
    {
        await Task.Delay(pageDelayMs, cancellationToken);

        for (var sku = 0; sku < 4; sku++)
            entries.Add(new LedgerEntry($"SKU-{page}{sku}", (page + 1) * (sku + 1) * 10));
    }

    return entries;
}

/// <summary>
/// 每次调用自带截止时间:把调用方的令牌与本地 CancelAfter 链接成同一个令牌,
/// 两种取消(调用方放弃 / 本次调用超时)都会取消进行中的抓取。
/// </summary>
public async Task<IReadOnlyList<LedgerEntry>> FetchSnapshotWithDeadlineAsync(
    TimeSpan perCallDeadline, CancellationToken callerToken)
{
    using var deadlineCts = CancellationTokenSource.CreateLinkedTokenSource(callerToken);
    deadlineCts.CancelAfter(perCallDeadline);

    return await FetchSnapshotAsync(3, deadlineCts.Token);
}
```

两条绿测试分别验证链的两端。测试令牌一路传进去,测试一请求取消,进行中的抓取就被取消,异常由测试自己接住:

```csharp
[Fact]
public async Task StockFeedClient_TestTokenRequested_CancelsInFlightFetch()
{
    var client = new StockFeedClient(pageDelayMs: 400);
    var fetch = client.FetchSnapshotAsync(3, TestContext.Current.CancellationToken);

    TestContext.Current.CancelCurrentTest();

    var ex = await Record.ExceptionAsync(() => fetch);
    Assert.IsAssignableFrom<OperationCanceledException>(ex);
}
```

客户端自己的截止时间(不依赖测试超时)同样能取消进行中的调用——这是 8.7 会用的模式:调用级 deadline 用链接令牌实现,而不是给测试加 `Timeout`:

```csharp
[Fact]
public async Task StockFeedClient_PerCallDeadline_CancelsInFlightFetch()
{
    var client = new StockFeedClient(pageDelayMs: 400); // 全量要 1.2s
    var watch = Stopwatch.StartNew();

    var ex = await Record.ExceptionAsync(() =>
        client.FetchSnapshotWithDeadlineAsync(TimeSpan.FromMilliseconds(500), CancellationToken.None));

    watch.Stop();
    Assert.IsAssignableFrom<OperationCanceledException>(ex);
    Assert.True(watch.ElapsedMilliseconds < 1_000,
        $"应在 500ms 截止处被取消,实际让调用方等了 {watch.ElapsedMilliseconds}ms");
}
```

设计要点:`TestContext.Current` 是快照语义,令牌**按参数往下传**,不要把它缓存到字段或静态里;夹具(第 5 章)跨多条测试,更不能持有某条测试的令牌——夹具自己的释放走 `IAsyncLifetime.DisposeAsync`,不受单条测试超时影响。

## 8.5 长时运行检测:-long-running

`Timeout` 是判定,`-longRunning <秒>` / `--long-running <秒>` 只是**报告**:测试超过 N 秒还没结束,runner 在它还跑着的时候周期性打一条诊断,不改变测试结果。[`LongRunningTests.cs`](../code/Ch08.Timeouts/LongRunningTests.cs) 是一条慢但合法的测试(3 秒):

```csharp
/// <summary>慢但合法的测试:挂起检测只是把它报告出来,结果仍是通过。</summary>
[Fact]
public async Task FeedFetch_SlowRound_IsReportedWhileStillRunning()
{
    var snapshot = await new StockFeedClient(pageDelayMs: 1_000)
        .FetchSnapshotAsync(3, TestContext.Current.CancellationToken);

    Assert.Equal(12, snapshot.Count);
}
```

## 8.6 调试器下超时被禁用

官方 4.0.0 发布说明里有一条 bug 修复:调试器检测从发现期移到了执行期;修复前的症状是"在 Visual Studio Test Explorer(VSTest)里跑带超时的测试时超时仍然生效,而**这个行为在调试器下本来是被禁用的**"。也就是说:xUnit 检测到调试器附加时不会让 `Timeout` 参战——否则你在断点上停两分钟,测试就被判超时了,调试没法做。4.0 起这个判断发生在执行期,Test Explorer 里也正常了。

实测边界:本机命令行环境没有能把调试器附加到已启动进程的工具链(`dotnet attach` 在 10.0.113 SDK 里不存在,`dotnet-attach` 也不在 NuGet 源上;本机有 `/usr/bin/gdb`,但 `ptrace_scope = 1` 且没有 root,`gdb -p <pid>` 直接报 `ptrace: Operation not permitted`),所以"调试器下超时不生效"这个行为本身我没能用真实输出复现,以上结论来自官方 4.0.0 发布说明。我能实测的是反面:无调试器的所有运行里超时都如期生效(本章全部输出)。对本地调试的实际含义:在 IDE 里调试带 `Timeout` 的测试,断点挂住不会被判超时;但 CI 里没有调试器,超时照常参战——别把"调试时没超时"当成"这个超时没生效"的证据。

## 8.7 设计建议:超时值怎么定

**超时不是把慢测试变绿的工具。** 一条测试经常贴着时限跑,先问它为什么慢:数据太大就拆(按场景拆成多条小测试),逻辑太慢就参数化(第 4 章把用例搬进数据表,每条各给时限),依赖太慢就把依赖换掉或降级(假时钟、假服务)。把 `Timeout` 从 5 秒改到 50 秒,只是把红灯推迟。

**值从哪来:正常耗时的上界乘一个安全系数。** 拿一条测试在健康环境下的 P99 耗时,乘 3~10 倍,就是它该声明的上限——上限表达的是"超过这个值就不再是慢,而是坏了"。没有测量就拍脑袋写的 30000,和没有 `Timeout` 没有区别。

**网络与 IO 测试:真实超时 + 可取消的客户端,两层都要。** 测试的 `Timeout` 是最后防线;先让客户端自己可取消、有调用级 deadline(8.4 的 `CreateLinkedTokenSource` + `CancelAfter` 就是 `HttpClient` 每次调用该做的事)。这样卡死的调用会在自己的 deadline 处抛异常,失败信息是"哪个请求、什么异常",而不是干巴巴一条 `Test execution timed out`。

**慢环境用跳过,不用超时硬等。** 第 7 章的原则在这里同样成立:如果已知某些环境就是慢(慢机器、跨地域网络),条件跳过(带原因的 `Assert.SkipWhen`)比让超时必然爆红诚实——超时表达"这个行为不能超过这个时间",跳过表达"这次运行不具备判断条件"。两者别混用:给慢环境加超大 `Timeout` 是把两者搅在一起,既测不出行为,也盖住了环境差异。

**并行下超时依赖计时。** 第 6 章讲过:`aggressive` 并行算法会把挂起的测试恢复得不及时,计时不准,`Timeout` 不可靠。在意超时的工程用默认的 `conservative`。

## 动手练习

1. **复现并对比两种超时形态。** 把 `FeedFetch_PassesToken_StopsAtTimeout` 的 `Skip` 去掉,分别用 `dotnet test --project Ch08.Timeouts --filter-method "Ch08.Timeouts.Tests.TimeoutSemanticsTests.FeedFetch_PassesToken_StopsAtTimeout"` 和原生 `./bin/Debug/net10.0/Ch08.Timeouts -method "..."` 各跑一次。验收:两种输出都含 `Test execution timed out after 100 milliseconds`,MTP 形态是 `failed (canceled)` 带 `(约100ms)`,原生形态是 `[FAIL]` 无标记;把 `Skip` 加回去后 `dotnet test --project Ch08.Timeouts` 回到全绿(12 条,0 失败)。

2. **亲手触发一次 xUnit1051。** 在 `AnalyzerEvidenceTests` 的 `FeedFetch_AfterXUnit1051Fix_PassesTokenToCancellableCall` 里,把 `Task.Delay(50, TestContext.Current.CancellationToken)` 改成 `Task.Delay(50)`,编译,记下警告原文;再改回来。验收:警告文本与 8.3 一字不差;改回后 `dotnet build Ch08.Timeouts` 零警告。

3. **给一行单独设时限。** 给 `FeedFetch_RowExceedsTheoryTimeout` 增加一个 `TheoryDataRow` 数据源(第 4 章的写法),其中一行用 `.WithTimeout(100)` 配一个约 300ms 的等待,其余行保持原样。验收:新行出现在 `failed (canceled)`,其余行的结果与 8.1.1 一致;对照失败输出里的毫秒数,说明特性级 `Timeout = 200` 与行级 `Timeout = 100` 哪个实际生效了;工程最终全绿、零警告。

## 本章小结

- `[Fact(Timeout = ms)]` / `[Theory(Timeout = ms)]` 给测试(特性级:每一行)设毫秒级时限;v3 对同步测试同样生效。数据行级 `Timeout` 见第 4 章。超时失败的消息是 `Test execution timed out after N milliseconds`,MTP 里带 `failed (canceled)` 标记,原生里是 `[FAIL]`;结果消息里有 `FailureCause` 分类(`Assertion` / `Timeout` / `Exception`,靠 `IAssertionException` / `ITestTimeoutException` 这类名字标记接口识别)。
- 超时不强杀测试:框架只把 `TestContext.Current.CancellationToken` 置为已取消。失败在时限处判定,但没接令牌的测试继续跑,而 runner 不保证等它(实测:原生 runner 判定后 0.18s 就退出;MTP 的整次运行 0.6s~3.7s 不等,有时等到被放弃的测试自然结束,有时提前退出);被放弃的测试后来抛的异常以 `[Test Cleanup Failure]` 单独出现。
- 正确写法只有一条:让信号能被观察——令牌透传给可取消的 API,循环里 `ThrowIfCancellationRequested()`,生产方法的令牌按参数往下传、不缓存。
- xUnit1069 警告"设了 Timeout 却没引用令牌"的测试,xUnit1051 警告"调用可接收令牌的方法却没传"的调用;两者都是编译期警告,修复形态就是上一条。
- `TestContext.Current.CancelCurrentTest()` 无参数,与超时共用同一个令牌信号。观察到的测试以被取消 API 抛出的异常失败(没有 `(canceled)` 标记);没观察的照常跑完、仍然通过——取消是请求,不是强杀。调用级 deadline 用 `CreateLinkedTokenSource` + `CancelAfter` 实现,这是生产客户端该有的一层,不是测试 `Timeout` 的职责。
- `-longRunning <秒>`(原生)在测试超过 N 秒时打 `[Long Running Test]` 诊断,不改变结果;MTP 的 `--long-running` 在 4.0.2 里控制台看不到这些行,要用原生 runner。`--fail-skips` / `--fail-warns` 这类结果门禁与它无关(第 10、11 章)。
- 调试器附加时超时不参战(官方 4.0.0 行为,本机未能实测);CI 无调试器,超时照常生效。
- 超时值来自测量:P99 × 安全系数;慢测试拆或参数化,不无限加时;网络/IO 用可取消客户端 + 调用级 deadline 打底,测试 `Timeout` 兜底;慢环境用带原因的跳过,不用超大超时;在意超时的工程用 `conservative` 并行算法。
