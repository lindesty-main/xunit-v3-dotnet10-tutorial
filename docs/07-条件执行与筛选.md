# 第 7 章 · 条件执行与筛选

> 你将学会:
> - 用 `Skip` 静态跳过整条测试或单条数据行,并在报告里读回原因
> - 用 `Assert.Skip` / `SkipUnless` / `SkipWhen` 与特性级 `SkipUnless` / `SkipWhen`(+ `SkipType`)在执行期决定跳过,并说清这三种跳过的执行边界
> - 用 `Explicit` 把"只有手动触发才该跑"的用例排除在默认运行之外,并看懂 `Not Run` 计数
> - 用 `[Trait]` 给测试分层(方法级、类级、程序集级、多值),再用简单过滤器与查询过滤语言精确选中它们
> - 让同一套用例在 CI 与本地都全绿,只是跳过的是不同那几条
> - 判断一个场景该跳过、该失败,还是该显式

本章的工程是 [`code/Ch07.Conditional`](../code/Ch07.Conditional),被测代码在 [`Production/`](../code/Ch07.Conditional/Production/):`RefundCalculator`(退款)、`TaxRules`(区域税则表)、`InvoiceWriter`(写出发票)、`LegacyRateClient`(遗留计费 API 的裸 TCP 客户端)、`ProcessProbe`(`/proc` 探针)、`ReportFormatter`(CI 与本地两种告警格式)、`RunEnvironment` 与 `DependencyProbe`(环境判定)、`PipelineRecorder`(执行痕迹计数)。所有输出片段来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2 的真实运行;绝对路径用 `...` 省略,其余逐字保留。

一个环境细节:我本机 shell 里恰好带着 `CI=true`,所以下文"本地场景"的命令都写成 `env -u CI ...`(去掉该变量再跑),CI 场景写成 `CI=1 ...`。这个变量本身就是 7.2.5 的开关。

## 7.1 静态跳过:原因写在特性上

`Skip = "原因"` 是最直白的一种:决定在发现阶段就做完,测试体一行都不会执行。

[`StaticSkipTests.cs`](../code/Ch07.Conditional/StaticSkipTests.cs) 里三种状态并存——正常执行、特性级跳过、数据行级跳过:

```csharp
[Trait("kind", "unit")]
[Trait("speed", "fast")]
public class StaticSkipTests
{
    [Fact]
    public void Refund_CapsAtPaid() =>
        Assert.Equal(30.00m, RefundCalculator.Refund(30.00m, 12.00m, 5));

    /// <summary>特性级 Skip:整条测试不参与执行,原因原样进报告。</summary>
    [Fact(Skip = "部分退货的退款上限规则未定,见需求 #1427")]
    public void Refund_PartialShipment_PendingRule() =>
        Assert.Equal(6.00m, RefundCalculator.Refund(30.00m, 12.00m, 1));

    /// <summary>数据行级 Skip:同一个 Theory 里别的行照常跑。</summary>
    [Theory]
    [InlineData(12.00, 1, 12.00)]
    [InlineData(12.00, 3, 36.00)]
    [InlineData(12.00, 9, 100.00, Skip = "实付封顶的边界用例,与 #1427 一起再启用")]
    public void Refund_QuantityTable(double unitPrice, int quantity, double expected) =>
        Assert.Equal((decimal)expected, RefundCalculator.Refund(100.00m, (decimal)unitPrice, quantity));
}
```

数据行上的 `Skip` 属于数据源特性(`DataAttribute`)一族的元数据,和第 4 章里 `TheoryDataRow { Skip = ... }` / `.WithSkip(...)` 是同一件事;`InlineData` 上能直接写的还有 `Skip`、`TestDisplayName`、`Timeout`、`Traits`、`Explicit`、`Label`。

### 7.1.1 报告里的形态

原生 runner(`[SKIP]` + 缩进的原因行):

```text
$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -class "Ch07.Conditional.Tests.StaticSkipTests"
    Ch07.Conditional.Tests.StaticSkipTests.Refund_PartialShipment_PendingRule [SKIP]
      部分退货的退款上限规则未定,见需求 #1427
    Ch07.Conditional.Tests.StaticSkipTests.Refund_QuantityTable(unitPrice: 12, quantity: 9, expected: 100) [SKIP]
      实付封顶的边界用例,与 #1427 一起再启用
=== TEST EXECUTION SUMMARY ===
   Ch07.Conditional  Total: 5, Errors: 0, Failed: 0, Skipped: 2, Not Run: 0, Time: 0.084s
```

`dotnet test` 走 MTP,形态是 `skipped` + 原因行,汇总里累计成 `skipped`:

```text
$ env -u CI dotnet test --project Ch07.Conditional
...
Test run summary: Passed!
  total: 29
  failed: 0
  succeeded: 12
  skipped: 17
```

两个 runner 的汇总口径不同,这一点要记住:原生 runner 把"跳过"和"没运行"分开计数(`Skipped: 13, Not Run: 4`,后 4 条是 7.3 的 Explicit 用例);MTP 的汇总里没有 `Not Run` 这一项,Explicit 未运行被并入 `skipped`。同一份工程,原生 runner 的完整汇总:

```text
   Ch07.Conditional  Total: 29, Errors: 0, Failed: 0, Skipped: 13, Not Run: 4, Time: 0.084s
```

**坑:跳过的字符串就是报告内容。** 它不是注释,是搜索关键字:CI 日志里 `grep "需求 #1427"` 就能把所有相关跳过找出来。写"先挂起"、"待定"这类没有检索价值的消息,等于没有写。

**注意:`skipped` 默认不算失败,但可以让它算。** `--fail-skips on`(原生 `-failSkips`)把跳过按失败处理:

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --fail-skips on --filter-trait kind=integration
  total: 11
  failed: 7
  succeeded: 3
  skipped: 1
```

只有 1 条没被转成失败,因为它是 Explicit 未运行(7.3),不是跳过。对"集成层必须真的跑起来"的流水线,这是把环境缺失暴露成红灯的最省事的做法。

## 7.2 执行期决定:动态跳过

前提条件往往要到运行时才知道:这台机器是不是 Windows、这次是不是 CI 触发、依赖的服务在不在。v3 提供两条路:测试体里的 `Assert.Skip*`,和特性上的 `SkipUnless` / `SkipWhen`。

### 7.2.1 断言式:`Assert.Skip` / `SkipUnless` / `SkipWhen`

[`DynamicSkipTests.cs`](../code/Ch07.Conditional/DynamicSkipTests.cs):

```csharp
[Fact]
public void LegacyApi_RateRoundTrip()
{
    if (!DependencyProbe.LegacyApiAvailable)
        Assert.Skip(
            $"遗留计费 API 未监听 {DependencyProbe.LegacyApiHost}:{DependencyProbe.LegacyApiPort};" +
            "用 CH07_LEGACY_API=1 可以强制进入断言");

    var (zone, rate) = LegacyRateClient.FetchRate("EU");
    Assert.Equal("EU", zone);
    Assert.Equal(0.19m, rate);
}

[Fact]
public void LegacyApi_BatchImportMatchesRate()
{
    Assert.SkipUnless(DependencyProbe.LegacyApiAvailable,
        "遗留计费 API 不可用,批量导入无从比对");

    var (zone, rate) = LegacyRateClient.FetchRate("NO");
    Assert.Equal(0.25m, rate);
    Assert.Equal("NO", zone);
}
```

三个断言的语义:`Assert.Skip(reason)` 无条件跳过;`Assert.SkipUnless(condition, reason)` 在 `condition` 为 `false` 时跳过;`Assert.SkipWhen(condition, reason)` 在 `condition` 为 `true` 时跳过。它们和别的断言一样是"抛异常终止本条测试",所以写在中间的跳过会截断后面的代码。

同一张数据表里按数据决定跳过,是这类断言最有用的形态——用例留在表里当哨兵,只有真正没有规则的区域不参与断言:

```csharp
/// <summary>同一张表里,有规则的区参与断言,没规则的区只留哨兵。</summary>
[Theory]
[InlineData("DE", "EU")]
[InlineData("NO", "NO")]
[InlineData("SG", "SG")]
public void TaxRule_OnlyCheckedWhereRuleExists(string region, string expectedZone)
{
    Assert.SkipWhen(!TaxRules.HasRule(region), $"{region} 不在税则表内,保留用例但不参与断言");
    Assert.Equal(expectedZone, TaxRules.ZoneOf(region));
}
```

真实输出里,被跳过的那一行单独列出(另外两行照常通过,不出现在输出里):

```text
skipped Ch07.Conditional.Tests.DynamicSkipTests.TaxRule_OnlyCheckedWhereRuleExists(region: "SG", expectedZone: "SG") (0ms)
  SG 不在税则表内,保留用例但不参与断言
```

### 7.2.2 特性级:`SkipUnless` / `SkipWhen`(+ `SkipType`)

不想让判断混进测试体,就把门写成属性:

```csharp
/// <summary>供特性级 SkipUnless 使用:必须是指向 bool 的 public static 属性。</summary>
public static bool LegacyApiReady => DependencyProbe.LegacyApiAvailable;

/// <summary>属性级 SkipUnless:跳过消息仍来自 Skip。</summary>
[Fact(Skip = "遗留 API 不在,批量导入用例挂起", SkipUnless = nameof(LegacyApiReady))]
public void LegacyApi_ImportContract()
{
    var (zone, _) = LegacyRateClient.FetchRate("EU");
    Assert.Equal("EU", zone);
}
```

- `SkipUnless = nameof(属性)`:属性为 `false` 时跳过;`SkipWhen`:属性为 `true` 时跳过。两者只能设一个。
- 属性必须是 `public static`,`bool` 返回值,默认在测试类上找;放别处就配 `SkipType = typeof(别的类)`。本章用 `RunEnvironment.IsLinux` 演示跨类门:

```csharp
/// <summary>
/// SkipUnless + SkipType:门属性可以放在别的类上。非 Linux 时跳过;本机是 Linux,所以这条真的执行。
/// </summary>
[Fact(Skip = "非 Linux 没有 /proc,进程探针无从校验",
    SkipUnless = nameof(RunEnvironment.IsLinux), SkipType = typeof(RunEnvironment))]
public void ProcessProbe_SelfStatusReadable()
{
    var status = ProcessProbe.ReadSelfStatus();
    Assert.Contains("Name:", status);
    Assert.Contains("Pid:", status);
}
```

**最大的坑:`SkipUnless` / `SkipWhen` 必须同时写 `Skip`,否则这条测试直接失败。** 属性决定要不要跳,`Skip` 的字符串才是跳过时显示的消息——框架不会替你编。工程里留了一条故意漏掉 `Skip` 的反例(`Probe_MissingSkipMessage`,标成 `Explicit` 所以默认运行不参与,见 7.3),单独跑它:

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --explicit on --filter-method "Ch07.Conditional.Tests.DynamicSkipTests.Probe_MissingSkipMessage"
failed Ch07.Conditional.Tests.DynamicSkipTests.Probe_MissingSkipMessage (0ms)
  from .../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64)
  Xunit.MicrosoftTestingPlatform.XunitException: You must set 'Skip' when you set 'SkipUnless' or 'SkipWhen' on test method 'Ch07.Conditional.Tests.DynamicSkipTests.Probe_MissingSkipMessage' to set the message for conditional skips
```

另外两个错误停在编译期,不用等到运行。把门属性名写错就是 xUnit1054——下面是把上面那条用例的 `SkipUnless = nameof(LegacyApiReady)` 改成 `SkipUnless = "Ready"` 之后的真实编译输出(用 `nameof` 写一个不存在的名字则是 CS0103,同样编译不过):

```text
error xUnit1054: To be used for conditional skipping, type 'Ch07.Conditional.Tests.DynamicSkipTests' must include a public static property named 'Ready' returning 'bool'. (https://xunit.net/xunit.analyzers/rules/xUnit1054)
```

`SkipUnless` 与 `SkipWhen` 同时设是 xUnit1055:

```text

```

### 7.2.3 三种跳过的执行边界:计数证据

"跳过"这个词盖住了三种完全不同的执行边界。[`PipelineEvidenceTests.cs`](../code/Ch07.Conditional/PipelineEvidenceTests.cs) 用计数把它们量出来:测试类的构造器记"类构造",一个类级 `BeforeAfterTestAttribute` 记 `Before` / `After`,最后一条见证用例把计数断言出来并打印成表。

```csharp
[RecordPipeline]
[TestMethodOrdererAttribute(typeof(DeclarationOrderMethodOrderer))]
[Trait("kind", "unit")]
[Trait("speed", "fast")]
public class PipelineEvidenceTests
{
    private readonly ITestOutputHelper output;

    public PipelineEvidenceTests(ITestOutputHelper output)
    {
        this.output = output;
        PipelineRecorder.Record(TestContext.Current.TestMethod!.MethodName, "类构造");
    }

    /// <summary>供特性级 SkipWhen 使用。</summary>
    public static bool AlwaysTrue => true;

    [Fact(Skip = "静态跳过:发现阶段就不参与执行")]
    public void A_StaticSkip() => Assert.Equal(1, 1);

    [Fact(Skip = "特性级跳过:执行期读属性", SkipWhen = nameof(AlwaysTrue))]
    public void B_AttributeDynamicSkip() => Assert.Equal(1, 1);

    [Fact]
    public void C_AssertDynamicSkip()
    {
        PipelineRecorder.Record(nameof(C_AssertDynamicSkip), "测试体");
        Assert.Skip("断言式跳过:决定发生在测试体里");
    }

    [Fact]
    public void D_WitnessCounts()
    {
        var names = new[] { nameof(A_StaticSkip), nameof(B_AttributeDynamicSkip), nameof(C_AssertDynamicSkip) };
        output.WriteLine(PipelineRecorder.Describe(names));

        // 静态跳过:什么都没发生
        Assert.Equal(0, PipelineRecorder.Count(nameof(A_StaticSkip), "类构造"));
        Assert.Equal(0, PipelineRecorder.Count(nameof(A_StaticSkip), "Before"));
        // 特性级跳过:实测同样没有构造测试类,BeforeAfterTest 也没执行
        Assert.Equal(0, PipelineRecorder.Count(nameof(B_AttributeDynamicSkip), "类构造"));
        Assert.Equal(0, PipelineRecorder.Count(nameof(B_AttributeDynamicSkip), "Before"));
        // 断言式跳过:整条流水线跑到 Assert.Skip 那一刻,After 仍然执行
        Assert.Equal(1, PipelineRecorder.Count(nameof(C_AssertDynamicSkip), "类构造"));
        Assert.Equal(1, PipelineRecorder.Count(nameof(C_AssertDynamicSkip), "Before"));
        Assert.Equal(1, PipelineRecorder.Count(nameof(C_AssertDynamicSkip), "测试体"));
        Assert.Equal(1, PipelineRecorder.Count(nameof(C_AssertDynamicSkip), "After"));
    }
}

/// <summary>把测试方法到达过的 Before / After 阶段记进 <see cref="PipelineRecorder"/>。</summary>
public sealed class RecordPipelineAttribute : BeforeAfterTestAttribute
{
    public override void Before(MethodInfo testMethod, IXunitTest test) =>
        PipelineRecorder.Record(testMethod.Name, "Before");

    public override void After(MethodInfo testMethod, IXunitTest test) =>
        PipelineRecorder.Record(testMethod.Name, "After");
}
```

见证用例必须读到前面三条测试留下的计数,所以这个类用第 6 章的方法排序器按声明顺序执行——这是全书里少数"确实需要顺序"的地方之一。真实输出:

```text
$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -diagnostics
    Ch07.Conditional.Tests.PipelineEvidenceTests.D_WitnessCounts [PASS]
      Output:
        测试方法                               类构造    Before       测试体     After
        A_StaticSkip                         0         0         0         0
        B_AttributeDynamicSkip               0         0         0         0
        C_AssertDynamicSkip                  1         1         1         1
```

结论(4.0.2 实测,值得记牢):

- **静态跳过**(`Skip`):测试类不构造,`BeforeAfterTest` 不执行,测试体不执行。报告里它仍然出现,因为它是被"发现"出来的。
- **特性级动态跳过**(`Skip` + `SkipUnless` / `SkipWhen`):属性在执行期读取,报告形态与静态跳过一样;但实测 4.0.2 里判定发生在创建测试类之前,类构造与 `BeforeAfterTest` 同样不执行。官方 v3 变更说明里"这类测试会跑完整条流水线(含 `BeforeAfterTest`、测试类创建与释放)"的说法在这版已经不成立——别按它设计夹具副作用。
- **断言式跳过**(`Assert.Skip*`):整条流水线跑到那句断言为止——类已构造、`Before` 已执行、测试体执行到断言处,而且 `After` 仍然执行。这是唯一会真正消耗夹具与 `BeforeAfterTest` 预算的跳过,也是唯一能在跳过前做真实判断的形态。

差别在钱上:夹具(第 5 章)启动一次可能要几秒,断言式跳过照付不误;特性级与静态跳过不付。

### 7.2.4 `SkipExceptions`:把已知异常变成跳过

`SkipExceptions` 接受一组异常类型:测试抛出其中任何一个,结果就是跳过,跳过原因取异常消息。`InvoiceWriter.WriteToConfiguredDirectory` 在未配置 `CH07_EXPORT_DIR` 时抛 `ExportUnavailableException`,测试照直调用它:

```csharp
[Fact(SkipExceptions = [typeof(ExportUnavailableException)])]
public void InvoiceWriter_WritesToConfiguredDirectory()
{
    var path = InvoiceWriter.WriteToConfiguredDirectory(
        "invoice-1.csv", "id,amount\n1,12.00\n");
    Assert.Equal("invoice-1.csv", Path.GetFileName(path));
    Assert.Contains("1,12.00", File.ReadAllText(path));
}
```

```text
skipped Ch07.Conditional.Tests.DynamicSkipTests.InvoiceWriter_WritesToConfiguredDirectory (0ms)
  未配置 CH07_EXPORT_DIR,发票无处可写
```

配上环境变量,同一条用例真的跑起来并通过:

```text
$ env -u CI CH07_EXPORT_DIR=/tmp/ch07-out dotnet test --project Ch07.Conditional -- --filter-query "/[(kind=integration)&(project=ch07)]"
  total: 11
  failed: 0
  succeeded: 5     # 比不设时多 2 条:两条写出用例真的执行了
  skipped: 6
```

只把它当"环境探测的兜底"用:接住的异常类型要窄(这里是自定义的 `ExportUnavailableException`),接 `InvalidOperationException` 这种宽类型会把真 bug 一起吞掉。

### 7.2.5 场景矩阵:操作系统 / CI / 外部依赖

| 前提 | 判定手段 | 推荐写法 |
| --- | --- | --- |
| 操作系统、CPU 架构 | `OperatingSystem.IsWindows()` 等 | 特性级 `SkipUnless` + `SkipType`(判定与测试体无关) |
| CI 与本地 | `Environment.GetEnvironmentVariable("CI")` | 断言式,两个分支各一条用例(见下) |
| 外部服务、端口、目录是否配置 | 真实探测 + 环境变量开关 | 断言式(要能打印"怎么让它跑起来"),必要时 `SkipExceptions` |
| 规则/需求未定 | 无 | 静态 `Skip`,原因里写需求号 |
| 只有人来看 | 无 | `Explicit`(7.3) |

CI 与本地最容易写坏。与其"本地跳过",不如两个分支各一条用例,每条只守自己的分支:

```csharp
[Trait("kind", "unit")]
[Trait("speed", "fast")]
public class EnvironmentGateTests
{
    [Fact]
    public void ReportFormatter_UsesGithubActionsOnCi()
    {
        Assert.SkipUnless(RunEnvironment.IsCi, "本次运行没有 CI 环境变量,CI 分支由另一条用例守");
        Assert.Equal("github-actions", ReportFormatter.Select());
        Assert.Equal("::warning title=退款::30 元已受理", ReportFormatter.Warning("退款", "30 元已受理"));
    }

    [Fact]
    public void ReportFormatter_UsesConsoleLocally()
    {
        Assert.SkipWhen(RunEnvironment.IsCi, "本次运行是 CI,本地分支由另一条用例守");
        Assert.Equal("console", ReportFormatter.Select());
        Assert.Equal("WARN 退款: 30 元已受理", ReportFormatter.Warning("退款", "30 元已受理"));
    }
}
```

判定集中在 [`Production/RunEnvironment.cs`](../code/Ch07.Conditional/Production/RunEnvironment.cs) 一处:

```csharp
public static bool IsCi => !string.IsNullOrEmpty(Environment.GetEnvironmentVariable("CI"));
```

各 CI 系统给的值不一样(`true` / `1` / …),所以只判断"存在且非空"。同一套用例在两种环境下的真实结果:

```text

  本次运行没有 CI 环境变量,CI 分支由另一条用例守
  from .../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64)
Test run summary: Passed!
  total: 2
  failed: 0
  succeeded: 1
  skipped: 1

$ CI=1 dotnet test --project Ch07.Conditional -- --filter-class "Ch07.Conditional.Tests.EnvironmentGateTests"

  本次运行是 CI,本地分支由另一条用例守
  from .../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64)
Test run summary: Passed!
```

两边都是绿的,只是跳过的那条换了个方向——这正是"跳过"该有的样子:它说明的是环境,不是代码。

**开关只跳过前提检查,不制造依赖。** 本章的 `DependencyProbe.Available` 先读环境变量开关,再落到真实 TCP 探测;把 `CH07_LEGACY_API=1` 强行打开而没有真的起服务,7.2.1 那条用例就会进入断言并失败:

```text

    …
```

顺带一提:动态跳过的底层机制是异常消息——以 `$XunitDynamicSkip$` 开头的异常消息会被 runner 当作动态跳过,后面部分是原因(第 12 章做扩展时会用到)。日常写法不必自己拼这个前缀。

## 7.3 Explicit:默认不参与运行

`Explicit = true` 的用例不参与默认运行:它不执行,也不算跳过——原生 runner 把它计成 `Not Run`,MTP 把它并入 `skipped` 并给出固定原因 `Not run (due to explicit test filtering)`。

[`ManualCheckTests.cs`](../code/Ch07.Conditional/ManualCheckTests.cs):

```csharp
[Trait("kind", "manual")]
public class ManualCheckTests
{
    [Fact(Explicit = true, DisplayName = "手工:重建演示数据并读回")]
    public void DemoDatabase_ReseedAndRead()
    {
        var directory = Path.Combine(Path.GetTempPath(), "ch07-demo", Guid.NewGuid().ToString("N"));
        try
        {
            var path = InvoiceWriter.Write(directory, "invoice-9.csv", "id,amount\n9,99.00\n");
            Assert.Contains("9,99.00", File.ReadAllText(path));
        }
        finally
        {
            Directory.Delete(directory, recursive: true);
        }
    }

    [Theory]
    [MemberData(nameof(HandCheckedRowCounts))]
    public void DemoDatabase_HandCheckedRowCount(int invoiceCount, int expectedLines)
    {
        var directory = Path.Combine(Path.GetTempPath(), "ch07-demo", Guid.NewGuid().ToString("N"));
        try
        {
            var csv = string.Join('\n', Enumerable.Range(1, invoiceCount).Select(i => $"{i},{i}.00"));
            var path = InvoiceWriter.Write(directory, "bulk.csv", csv);
            Assert.Equal(expectedLines, File.ReadAllLines(path).Length);
        }
        finally
        {
            Directory.Delete(directory, recursive: true);
        }
    }

    /// <summary>数据行级 Explicit:整条 Theory 照常跑,只有这些行等手动触发。</summary>
    public static TheoryData<int, int> HandCheckedRowCounts => new()
    {
        new TheoryDataRow<int, int>(3, 3) { Explicit = true, TestDisplayName = "手工:3 张发票" },
        new TheoryDataRow<int, int>(5, 5) { Explicit = true, TestDisplayName = "手工:5 张发票" },
    };
}
```

默认运行里,MTP 把它们按显示名列成 `skipped`,原因固定是那句 `Not run (due to explicit test filtering)`;原生 runner 不列它们,只在汇总里计 `Not Run: 4`(上面 3 条 + 7.2.2 那条探针):

```text
$ env -u CI dotnet test --project Ch07.Conditional
skipped 手工:重建演示数据并读回 (0ms)
  Not run (due to explicit test filtering)
  from .../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64)

$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -explicit off
...
   Ch07.Conditional  Total: 29, Errors: 0, Failed: 0, Skipped: 13, Not Run: 4
```

选项的取值两种 runner 一致:`on`(全部跑)、`off`(只跑非 Explicit,默认)、`only`(只跑 Explicit)。

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --explicit on
  total: 29
  failed: 1        # 7.2.2 那条故意漏掉 Skip 的探针
  succeeded: 15    # 12 + 3 条手工用例
  skipped: 13

$ env -u CI dotnet test --project Ch07.Conditional -- --explicit only
  total: 29
  failed: 1
  succeeded: 3
  skipped: 25
```

原生 runner 对应 `-explicit on|off|only`,汇总里能看到 `Not Run` 怎么被消掉:

```text
$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -explicit on
   Ch07.Conditional  Total: 29, Errors: 0, Failed: 1, Skipped: 13, Not Run: 0
```

在 IDE / Test Explorer 里单独点某条 Explicit 测试,等价于只对它请求"运行",不需要整个流水线开 `--explicit on`。

**什么时候用 Explicit,什么时候用 Skip:**

| 情况 | 用法 |
| --- | --- |
| 现在该跑,但前提不满足(缺服务、缺环境变量、非目标 OS) | `Skip` / `Assert.Skip*`,原因写清"怎么让它跑起来" |
| 本来就不属于自动流水线:重建演示数据、要看眼色的视觉比对、上线前人工核对 | `Explicit` |
| 规则未定、代码待写 | 静态 `Skip` + 需求号;长期不办就删掉 |
| 已知会失败,想让流水线继续 | 都不是:用 `Skip` 等于把失败藏起来,见 7.6 |

区别在责任归属:`Skip` 是"这条本该跑,现在跑不了",`Explicit` 是"这条本来就不该自动跑"。把后者写成前者,汇总里就会长出没人认领的跳过。

## 7.4 Traits:给测试打标签

`[Trait(名字, 值)]` 是任意键值对,可以打在方法、类、程序集上;同一个名字打多次就是多值。[`TraitLayerTests.cs`](../code/Ch07.Conditional/TraitLayerTests.cs) 用两个维度分层:`kind` 说明"这层的边界在哪",`speed` 说明"提交前值不值得等它"。

```csharp
[Trait("kind", "unit")]
[Trait("speed", "fast")]
public class UnitLayerTests
{
    [Fact]
    public void Refund_NegativeQuantityRejected() =>
        Assert.Throws<ArgumentOutOfRangeException>(
            () => RefundCalculator.Refund(30.00m, 12.00m, -1));

    /// <summary>同一个 trait 名的多个值:这条同时属于 unit 与 smoke 两层。</summary>
    [Trait("kind", "smoke")]
    [Fact]
    public void TaxRules_UnknownRegionHasNoRule() =>
        Assert.False(TaxRules.HasRule("SG"));
}
```

程序集级标签写在单独的文件里,给整章测试一个可筛选的共同键:

```csharp
// AssemblyTraits.cs
// 程序集级 Trait:本章所有测试都带 project=ch07,
// 需要"整章测试"这个集合时,用它而不是靠命名空间前缀碰运气。
[assembly: Trait("project", "ch07")]
```

多值的语义是"属于多个集合",不是"覆盖":上面那条同时带 `kind=unit` 和 `kind=smoke`,所以两个过滤器都会命中它——`-trait "kind=smoke"` 得到 2 条(`SmokeLayerTests` 1 条 + 这条),而 `kind=unit` 得到 14 条。分层规则:

- `kind` 一个测试可以有多个(一条冒烟同时是单元),但每个值的边界要能一句话说清。
- `speed` 只放两个值(`fast` / `slow`)就够;标签越多,漏标的越多。
- 标签名和值是检索接口,大小写不敏感(7.5),所以别靠大小写区分含义。

标签打完先看清单再写过滤器:原生 runner 会打印这个程序集里实际出现过的标签。

```text
$ cd Ch07.Conditional && ./bin/Debug/net10.0/Ch07.Conditional -list traits

"kind": ["integration", "manual", "smoke", "unit"]
"project": ["ch07"]
"speed": ["fast", "slow"]
```

漏标的、拼错的、凭空造出来的第二个维度,在这张表里一眼可见——它比"我以为我们打了哪些标签"可靠。

标签的另一个用途发生在 IDE 里:支持 traits 的测试视图(典型如 Visual Studio 测试资源管理器的分组)可以按标签把测试分组浏览,"集成测试"和"单元测试"各归各堆。这条用途只到"看"为止:各 IDE/版本对 traits 的支持程度不一样,v3 在 MTP 下的显示也在演进——**别把 IDE 视图当真相源**,打完标签先跑上面那张 `-list traits` 清单,要"只跑这一堆"用 7.5 的过滤器。

## 7.5 筛选

标签和结构(程序集 / 命名空间 / 类 / 方法)都是选择器的输入。本章用两套筛选器:**简单过滤器**(按名字与标签)与**查询过滤语言**(按结构组合);此外还有第三种 VSTest 过滤器(原生 runner 的 `-filterVSTest`),本书不用。它们之间不能混用:

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-trait kind=unit --filter-query "/[kind=unit]"
  Error output: Unhandled exception. System.ArgumentException: Cannot add simple filter or VSTest filter; query filters already exist (Parameter 'query')
```

### 7.5.1 简单过滤器

MTP(`dotnet test -- ...` 或 `dotnet run -- ...`)与原生 runner(直接跑 exe)的对应项:

| 目的 | MTP | 原生 |
| --- | --- | --- |
| 按类 | `--filter-class "名字"` | `-class "名字"` |
| 按方法 | `--filter-method "名字"` | `-method "名字"` |
| 按命名空间 | `--filter-namespace "名字"` | `-namespace "名字"` |
| 按标签 | `--filter-trait "k=v"` | `-trait "k=v"` |
| 排除上述任一项 | `--filter-not-class/-method/-namespace/-trait` | `-class- / -method- / -namespace- / -trait-` |
| 按显示名 | `--filter-display-name "名字"` | `-displayName "名字"` |
| 排除显示名 | `--filter-not-display-name "名字"` | `-displayName- "名字"` |

同一项给多次是 OR;不同项之间是 AND(实测:标签 + 类 = `total: 3`,即两者的交集)。`--filter-not-*` / `-…-` 这些排除项给多次是 AND。名字支持开头/结尾的 `*`,**中间不行**——写错不报错,只是一个都不选(实测 `--filter-class "Ch07.Conditional.Tests.*LayerTests"` → `total: 0`)。真实计数:

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-trait "kind=unit"
  total: 14
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-trait "kind=unit" --filter-trait "kind=smoke"
  total: 15
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-class "Ch07.Conditional.Tests.IntegrationLayerTests"
  total: 2
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-class "*LayerTests"
  total: 6
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-method "*KnownRegions*"
  total: 1
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-display-name "*Refund_QuantityTable*"
  total: 3
  succeeded: 2
  skipped: 1
```

最后一条是第 4 章那招的延续:用显示名通配把一整个 Theory 的 3 行都选中,包括被跳过的那行。原生 runner 同样支持:

```text
$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -trait "kind=smoke"
   Ch07.Conditional  Total: 2, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0
```

### 7.5.2 查询过滤语言

简单过滤器只能"按某一项",查询过滤器能表达结构组合。MTP 用 `--filter-query`,原生用 `-filter`。语法要点:

- 查询以 `/` 开头,最多四段:`/<程序集>/<命名空间>/<类>/<方法>`;省略的段等于 `*`。
- 段内支持开头/结尾的 `*`;`!` 否定(`!*foo` 表示"不以 foo 结尾");一个段内可以用 `(A)|(B)` 或 `(A)&(B)` 组合,括号不可省;多段组合不能跨越段边界。
- 标签写在查询末尾:`[name=value]` / `[name!=value]`;多个标签用 `/[(a=1)&(b=2)]`,值也可以带开头/结尾通配。
- 字符串比较一律不区分大小写;特殊字符用 HTML 十六进制实体转义(`&#x28;` 是 `(`)。

本章工程上的真实例子:

```text
# 只要 unit 层
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/[kind=unit]"
  total: 14

# unit 且 fast(两个标签的交集)
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/[(kind=unit)&(speed=fast)]"
  total: 14

# 排除 integration 层
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/[kind!=integration]"
  total: 18

# 命名空间段用通配,类名精确
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/*/Ch07.Conditional.Tests*/UnitLayerTests/"
  total: 3
  succeeded: 3

# 一个段内 OR:两个类
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/*/*/(UnitLayerTests)|(SmokeLayerTests)"
  total: 4

# 段内否定:除 *LayerTests 之外的全部
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/*/*/!*LayerTests/"
  total: 23

# 程序集级标签:整章
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/[project=ch07]"
  total: 29
```

比较不区分大小写(`/[KIND=UNIT]` 同样是 14);给多个查询过滤器是 OR:`/[kind=smoke]` 与 `/[kind=manual]` 同时给,得到 5(2 + 3)。

原生 runner 写法相同:

```text
$ env -u CI ./bin/Debug/net10.0/Ch07.Conditional -filter "/[(kind=unit)&(speed=fast)]"
   Ch07.Conditional  Total: 14, Errors: 0, Failed: 0, Skipped: 6, Not Run: 0
```

**坑:过滤器一个都没命中时,MTP 判这次运行失败**(空测试集算失败,退出码 8)。脚本里加上 `--ignore-exit-code 8` 之后,同样的零命中只是报告"零条测试",进程退出码变回 0:

```text
$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/nothing/nope"
.../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64) Zero tests ran (2s 115ms)
Exit code: 8

Test run summary: Zero tests ran
  error: 1
  total: 0

$ env -u CI dotnet test --project Ch07.Conditional -- --filter-query "/nothing/nope" --ignore-exit-code 8
.../bin/Debug/net10.0/Ch07.Conditional.dll (net10.0|x64) passed (2s 218ms)

Test run summary: Zero tests ran
  total: 0
```

### 7.5.3 三种常用组合

```bash
# 提交前只跑带 speed=fast 标签的(unit 与 smoke 两层)
dotnet test --project Ch07.Conditional -- --filter-query "/[speed=fast]"
#   total: 15  succeeded: 9  skipped: 6

# 只跑集成层,并且要求它真的跑起来:缺环境就红,不绿
dotnet test --project Ch07.Conditional -- --filter-trait "kind=integration" --fail-skips on
#   total: 11  failed: 7  succeeded: 3  skipped: 1

# 本地跳过慢的那层,但标签仍然可检索
dotnet test --project Ch07.Conditional -- --filter-not-trait "speed=slow"
#   total: 18
```

三条都是实测计数。第二条里唯一没被转成失败的 `skipped` 是 7.3 那条 Explicit 用例——它没运行,也不算跳过。这条命令把"集成层缺环境"从绿色变成红色,是标签用于策略(而不是用于逃避)的典型用法;再配上 7.2.4 里那个 `CH07_EXPORT_DIR`,它就成了 CI 上集成层的正确跑法(同一过滤器下,设与不设的计数差就是那两条被环境挡住的用例)。

## 7.6 设计原则

**跳过不是失败的另一种写法。** 失败说"代码有问题",跳过说"这次运行不具备判断的条件"。如果一条测试经常失败但你不想修,那要么给它补上前提检查(变成有原因的跳过),要么删掉它;把它标成 `Explicit` 或塞进 `--filter-not-trait` 里,只是让红灯换个地方亮。

**跳过必须留下能被检索的原因。** 本章所有跳过都带具体信息:需求号(`#1427`)、缺什么(`未配置 CH07_EXPORT_DIR`)、怎么让它跑起来(`设 CH07_EXPORT_DIR=/tmp/ch07-out 再跑`)。有了这些,`grep` 和 `--filter-query "/[kind=integration]"` 才能回答"我们到底在逃避什么"。原因里没有具体信息的跳过,半年后没人能负责。

**跳过要会过期。** 静态跳过挂着需求号,集成跳过挂着环境变量名,定期用 `--explicit on` / `--fail-skips on` 审一遍。长期没人处理的静态跳过应该删掉,不是留着。

**CI 与本地的差异用最小的实现:一个环境变量判断,集中在一个类里。** 本章的 `RunEnvironment` 只有几行,但它决定了三件事:哪些分支跑、哪些分支跳过、报告里写什么。别把 `if (Environment.GetEnvironmentVariable(...))` 散落在几十个测试里——那样每个测试自己决定策略,策略就不存在了。两个分支各一条测试(7.2.5),比"本地整个跳过"多保住一半覆盖。

**别用顺序或并行来制造跳过条件。** 需要"前面的测试跑过"才决定跳不跳,通常意味着测试之间有了共享状态;先按第 5、6 章处理状态,再考虑条件。

## 本章小结

- `Skip = "原因"` 是静态跳过:发现阶段决定,测试类不构造,`BeforeAfterTest` 不执行;特性级和数据行(`InlineData` / `TheoryDataRow`)都能写。
- 运行时决定有两条路:测试体里的 `Assert.Skip` / `SkipUnless` / `SkipWhen`,和特性上的 `SkipUnless` / `SkipWhen`(+ `SkipType`,属性须 `public static bool`)。特性级必须同时写 `Skip` 作为跳过消息,否则该测试直接失败;属性名写错或两个都设会在编译期报 xUnit1054 / xUnit1055。
- 实测边界(4.0.2):静态跳过与特性级动态跳过都不构造测试类;只有断言式跳过会跑完整条流水线到那句断言,`After` 仍会执行。夹具开销只由后者产生。
- `SkipExceptions` 把指定异常变成跳过,原因取异常消息;接住的类型要窄。
- `Explicit = true` 的用例默认不运行:原生 runner 计 `Not Run`,MTP 计成 `skipped` 并写 `Not run (due to explicit test filtering)`。`--explicit on|off|only`(原生同名)决定处理方式。该自动跑但缺前提的用例用 `Skip`;本来就不该自动跑的用例用 `Explicit`。
- `[Trait(名字, 值)]` 可打在方法、类、程序集上;同名多次即多值,该测试同时属于多个集合。`kind` / `speed` 这类维度是筛选器的输入;`-list traits` 打印程序集里真实用过的标签清单,先核对再写过滤器。
- 简单过滤器(`--filter-class/-method/-namespace/-trait/-display-name`、`--filter-not-*`,原生 `-class/-method/-namespace/-trait/-displayName` 及 `-…-`):同类多次为 OR,异类之间为 AND;名字只支持开头/结尾的 `*`。查询过滤语言(`--filter-query` / `-filter`):四段结构 + 开头/结尾 `*` + `!` 否定 + 段内 `()` 里的 `|`/`&` + 末尾 `[k=v]` / `[k!=v]`,多个查询之间是 OR,比较不区分大小写。简单过滤器与查询过滤器不能混用;零命中时 MTP 判失败(退出码 8),用 `--ignore-exit-code 8` 豁免。
- `--fail-skips on`(原生 `-failSkips`)把跳过当失败,用来强制"这一层必须真的跑起来"。
- 条件跳过的价值在于它说清"这次为什么不能判断";原因要具体、可检索、会过期;CI 与本地的差异集中在一个环境判定类里,两个分支各留一条用例。
