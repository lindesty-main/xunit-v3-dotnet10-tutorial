# 第 5 章 · 夹具与生命周期

> 你将学会:
>
> - 理解 xUnit 的实例模型:每个测试都新建一个测试类实例;构造器是每个测试的 setup,`IDisposable.Dispose` 是它的 teardown
> - 用 `IAsyncLifetime` / `IAsyncDisposable` 做异步的初始化与清理,并知道同时实现 `IDisposable` 时哪个 Dispose 会被调用
> - 用 `IClassFixture<T>` 把一个昂贵对象共享给一个测试类,用集合夹具共享给多个测试类,用程序集夹具共享给整个程序集
> - 按"共享范围、隔离性、代价"给三种夹具选型,识别滥用长生命周期夹具带来的耦合
> - 用 `TestContext.Current.GetFixture<T>()` 免去构造注入,用 4.0 的管道通知接口让夹具感知每个测试的开始与结束
> - 读懂夹具初始化/清理失败在报告里的三种形态,并能用真实输出区分它们

测试应当互不影响:一个测试改了什么,不该让另一个测试变红或变绿。xUnit.net 把这条原则做成了机制——**每个测试都拿到一个全新的测试类实例**;而"多个测试共用一个昂贵对象"(数据库连接、已装载的目录、测试容器)是另一回事,它需要显式声明共享范围,这正是夹具(fixture)的职责。本章把两件事放在一起讲:实例模型是默认世界,夹具是对它有意识、有范围的偏离。

本章的工程是 [`code/Ch05.Lifecycle`](../code/Ch05.Lifecycle),被测代码在 [`Production/`](../code/Ch05.Lifecycle/Production/):`ProductStore`(库存台账,预占不允许部分满足)、`Catalog`(构造即"加载"数千 SKU 的只读价格目录)、`OrderLedger`(线程安全的订单台账)、`AuditSink`(追加式审计日志)。所有输出片段来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2 的真实运行;过长的绝对路径与报告属性值用 `...` 省略,其余逐字保留。

## 5.1 实例模型:每个测试一个新实例

xUnit.net 为每个测试新建一个测试类实例:构造器在每个测试体之前运行,`IDisposable.Dispose`(若实现)在该测试体之后运行。这就是"每测例干净上下文"的实现方式——**setup 代码写在类的构造器里,但它每个测试都跑一遍**,共享的是代码,不是对象。

[`NewInstancePerTestTests.cs`](../code/Ch05.Lifecycle/NewInstancePerTestTests.cs) 用三个计数把这件事变成可断言的事实:

```csharp
public sealed class NewInstancePerTestTests : IDisposable
{
    private static int ctorCount;
    private static int disposeCount;
    private static readonly ConcurrentDictionary<int, byte> SeenInstanceNumbers = new();

    private readonly int instanceNumber;
    private readonly ProductStore store = new();

    public NewInstancePerTestTests() =>
        instanceNumber = Interlocked.Increment(ref ctorCount);

    public void Dispose() => Interlocked.Increment(ref disposeCount);

    [Fact]
    public void Ctor_RunsBeforeEveryTest_EachTestSeesItsOwnInstance()
    {
        // …TestContext.Current.TestOutputHelper.WriteLine(…):把实例编号写进测试输出,此处省略…
        // 本实例是最新构造的那个:构造器与测试体之间没有别的测试类实例被构造
        Assert.Equal(ctorCount, instanceNumber);

        // 此前每个测试实例都已经被 Dispose:此刻未释放的恰好只有当前这一个
        Assert.Equal(ctorCount - 1, disposeCount);

        // 如果实例被跨测试共享,两个测试会报出同一个实例编号,TryAdd 失败
        Assert.True(SeenInstanceNumbers.TryAdd(instanceNumber, 0),
            $"instance #{instanceNumber} was reused by another test");
    }
}
```

三条断言合起来就是实例模型的完整证明:每个测试体运行时,它是最新构造的实例(`ctorCount == instanceNumber`)、前面每个实例都已释放(`disposeCount == ctorCount - 1`)、没有任何两个测试拿到过同一个实例(编号去重)。这些断言与执行顺序无关——不管测试以什么顺序跑,它们都成立;而在"一个实例跑所有测试"的模型里,第三条必红。

两个测试还把各自的实例编号写进测试输出(`--report-xunit-xml` 生成的报告里,逐字):

```text
<test name="Ch05.Lifecycle.Tests.NewInstancePerTestTests.Ctor_RunsBeforeEveryTest_EachTestSeesItsOwnInstance" result="Pass" …>
<output>instance #1 (ctorCount=1, disposeCount=0)
</output></test><test name="Ch05.Lifecycle.Tests.NewInstancePerTestTests.BusinessState_IsFresh_ForEveryTest" result="Pass" …>
<output>instance #2 (ctorCount=2, disposeCount=1)
</output></test>
```

第二个测试运行时,第一个实例已经被释放——构造、执行、释放,周而复始。所以测试类里的实例字段天然是"每个测试一份全新的":第二个测试在自己的构造器里 `new` 出的 `ProductStore`,永远只有种子状态,哪怕别的测试已经预占过库存。

这个模型有个必须直面的推论:**实例隔离只保护实例状态,不保护 `static` 状态**。`StaticStateCouplingDemoTests` 是一个故意 `Skip` 的反例——同一个 Theory 的两行数据,每行都先断言 static 列表为空、再往里写一条:

```csharp
public static class SharedRegistry
{
    public static readonly List<string> Entries = [];
}

public sealed class StaticStateCouplingDemoTests
{
    // …源码里此处还有一段解释演示的注释,省略…
    [Theory(Skip = "演示 static 状态耦合:去掉 Skip 运行,真实失败输出见文档 5.1")]
    [InlineData("row-1")]
    [InlineData("row-2")]
    public void SameTheory_SharedStaticState_BreaksCleanContextAssumption(string row)
    {
        Assert.Empty(SharedRegistry.Entries);
        SharedRegistry.Entries.Add(row);
    }
}
```

两行数据必有一行先跑(先后顺序不保证)。临时去掉 `Skip` 运行,失败必然发生——两次运行都落在 `row-1` 上(先跑的那行把记录留了下来):

```text

  from …/Ch05.Lifecycle/bin/Debug/net10.0/Ch05.Lifecycle.dll (net10.0|x64)
```

哪一行红看运气,但一定会红——"有时绿有时红"就是状态耦合的味道。把业务状态放进 `static`(或任何跨实例的共享可变状态),等于主动放弃实例模型给你的隔离。需要共享时,用下面有范围、有生命周期的夹具,别用 `static`。

## 5.2 IAsyncLifetime:异步初始化与清理

构造器里不能 `await`,而真实的初始化常常是异步的(连数据库、起容器、预热缓存)。`IAsyncLifetime` 补上这段时间:

```csharp
public interface IAsyncLifetime : IAsyncDisposable
{
    ValueTask InitializeAsync();   // 在测试类构造器之后、测试体之前
    // DisposeAsync 来自 IAsyncDisposable:测试体之后调用
}
```

签名的两个要点:返回类型是 `ValueTask`,不是 `Task`——这两个方法几乎总是同步完成或轻量异步,别为它们装箱 `Task`。

`AsyncCacheClientTests.cs` 同时实现 `IAsyncLifetime` 和 `IDisposable`,用计数回答"到底调用了谁":

```csharp
public sealed class AsyncCacheClientTests : IAsyncLifetime, IDisposable
{
    private static int ctorCount;
    private static int initializeCalls;
    private static int syncDisposeCalls;
    private static int asyncDisposeCalls;

    private readonly int instanceNumber;
    private bool connectionReady;

    public AsyncCacheClientTests() => instanceNumber = Interlocked.Increment(ref ctorCount);

    public async ValueTask InitializeAsync()
    {
        // 模拟异步建立连接、预热缓存:这些代码写不进构造器
        await Task.Delay(50, TestContext.Current.CancellationToken);
        connectionReady = true;
        Interlocked.Increment(ref initializeCalls);
    }

    public ValueTask DisposeAsync()
    {
        Interlocked.Increment(ref asyncDisposeCalls);
        return ValueTask.CompletedTask;
    }

    public void Dispose() => Interlocked.Increment(ref syncDisposeCalls);
}
```

对应的断言(同样是顺序无关的计数):

```csharp
[Fact]
public void InitializeAsync_CompletesBeforeTestBody_RunsForEveryTest()
{
    Assert.True(connectionReady, $"instance #{instanceNumber} saw no InitializeAsync");
    Assert.Equal(ctorCount, initializeCalls);
    Assert.Equal(ctorCount - 1, asyncDisposeCalls);
}

[Fact]
public void SyncDispose_IsNeverCalled_WhenDisposeAsyncIsAvailable()
{
    // 同时实现 IDisposable + IAsyncDisposable:只有 DisposeAsync 被调用
    Assert.Equal(0, syncDisposeCalls);
    Assert.Equal(ctorCount - 1, asyncDisposeCalls);
}
```

第二条是实测行为:**测试类同时实现 `IDisposable` 和 `IAsyncDisposable` 时,框架只调 `DisposeAsync`,`Dispose` 一次都不会被调**(`syncDisposeCalls` 恒为 0)。生命周期顺序是:构造器 → `InitializeAsync` → 测试体 → `DisposeAsync`;`Dispose` 不在任何环节。

同文件里还有第二个演示:`AsyncDisposeOnlyTests` 只实现 `IAsyncDisposable`(不实现 `IAsyncLifetime`)——只要异步清理、不要异步初始化时,v3 允许这么做(v2 不支持,必须实现完整的 `IAsyncLifetime`)。

适用场景的界线:构造器里放**同步、便宜**的初始化;`InitializeAsync` 放**异步**的初始化;两者都是每测试一次。要跨测试共享且初始化是异步的,给夹具类型自己实现 `IAsyncLifetime`(下一节)。

## 5.3 类夹具:一个测试类共享一个实例

`IClassFixture<T>` 把"一个昂贵对象"共享给一个测试类的所有测试:框架在**该类的任何测试之前**构造夹具,在**该类全部测试结束后**调用它的 `Dispose`。[`ClassFixtureTests.cs`](../code/Ch05.Lifecycle/ClassFixtureTests.cs) 里,加载 5000 个 SKU 的 `Catalog` 只加载一次:

```csharp
public sealed class WarmCatalogFixture : IDisposable, INotifyTestLifecycle
{
    public static int InstancesCreated;
    public static int TestsFinished;

    public Guid Id { get; } = Guid.NewGuid();
    public Catalog Catalog { get; }
    public bool IsDisposed { get; private set; }

    public WarmCatalogFixture()
    {
        InstancesCreated++;
        Catalog = new Catalog(skuCount: 5_000);
    }

    // 框架在每个测试的开始/结束时回调这里(INotifyTestLifecycle,见 5.7)。
    public void OnTestStarting(IXunitTest test)
    {
    }

    public void OnTestFinished(IXunitTest test) => Interlocked.Increment(ref TestsFinished);

    public void Dispose()
    {
        // 时机守卫:若 Dispose 先于全部测试结束运行,这里会抛错,
        // 报告里出现独立的 [Test Class Cleanup Failure ...] 条目(文档 5.8)。
        // 本类共有 3 个执行中的测试。
        if (TestsFinished < 3)
            throw new InvalidOperationException(
                $"fixture disposed too early: only {TestsFinished} test(s) finished");

        IsDisposed = true;
    }
}
```

测试类实现 `IClassFixture<WarmCatalogFixture>` 即声明需求,构造参数只是取用方式:

```csharp
public sealed class CatalogWithClassFixtureTests : IClassFixture<WarmCatalogFixture>
{
    private static readonly ConcurrentDictionary<Guid, byte> SeenFixtureIds = new();

    private readonly WarmCatalogFixture fixture;

    public CatalogWithClassFixtureTests(WarmCatalogFixture fixture)
    {
        this.fixture = fixture;
        SeenFixtureIds.TryAdd(fixture.Id, 0);
    }

    [Fact]
    public void Fixture_IsConstructedExactlyOnce_BeforeAnyTest()
    {
        Assert.Equal(1, WarmCatalogFixture.InstancesCreated);

        // 类内测试还在进行时,夹具不会被 Dispose
        Assert.False(fixture.IsDisposed);
    }

    [Fact]
    public void SameFixtureInstance_IsSharedByEveryTestInClass()
    {
        // SeenFixtureIds 由每个测试类实例的构造器登记:出现第二个 Id 就说明夹具不止一个
        Assert.Equal(1, WarmCatalogFixture.InstancesCreated);
        Assert.Single(SeenFixtureIds);
        Assert.False(fixture.IsDisposed);
    }

    // …第三个测试 TryGetPrice_SeededSku_ReturnsGeneratedPrice 省略…
}
```

注意这里两个计数各自证明的方向:`InstancesCreated == 1` 证明"构造一次、在任何测试之前"(测试自己从没 new 过它);每个测试类实例的构造器登记的 `Id` 只有一个,证明"所有测试拿到的是同一个实例";`IsDisposed == false` 证明"类内测试进行到一半时不会被释放";而夹具 `Dispose` 里的时机守卫(依赖 `INotifyTestLifecycle`,5.7 展开)证明"释放发生在全部测试结束之后"——四个时点合起来就是类夹具的完整生命周期。

三个容易踩的点:

**范围是"每类一个",不是"每类型一个"。** 两个测试类都写 `IClassFixture<WarmCatalogFixture>`,会得到两个独立实例。跨类共享属于下一节的集合夹具。

**构造约束在运行期才暴露(类夹具实测)。** 夹具类型可以不是 `public`,但 `internal` 夹具只能用 `TestContext.Current.GetFixture<T>()` 取用:把它写成公开测试类的构造参数会撞上 CS0051(构造参数类型的可访问性低于方法),而测试类本身必须是 `public`(xUnit1000)。构造器必须可构造——无参是基线;程序集夹具的构造签名另有编译期检查(5.5)。写一个 `BadCtorProbeFixture(int x)`,失败出现在测试头上:

```text
Xunit.MicrosoftTestingPlatform.XunitException: Class fixture type 'Ch05.Lifecycle.Tests.BadCtorProbeFixture' had one or more unresolved constructor arguments: Int32 x
```

**Skip 不豁免夹具。** `SkippedTestStillBuildsFixtureTests` 里一个 `[Fact(Skip=...)]` 加一条计数断言:

```csharp
[Fact]
public void ClassFixture_IsConstructed_EvenThoughAnotherTestIsSkipped()
{
    Assert.Equal(1, CountingFixture.CtorCount);
}
```

类夹具是在测试类**启动**时创建的:只要这个类真的会启动(至少有一个要执行的测试),夹具就在所有测试之前被构造——单个测试被 `Skip`(或 `Explicit`)豁免不了它,上面那条断言实测 `CtorCount` 就是 1。反过来,整类测试都被跳过时类不会启动,夹具也不构造不释放:给一个全 `Skip` 的类挂一个构造即抛错的夹具,运行不会变红。

## 5.4 集合夹具:多个测试类共享一个实例

数据库测试的典型形态:初始化一次数据,多个测试类都用它。这就是集合夹具——共享范围从"一个类"扩到"一个测试集合",生命周期贯穿整个集合。

**具名集合**([`NamedCollectionFixtureTests.cs`](../code/Ch05.Lifecycle/NamedCollectionFixtureTests.cs)):定义类带 `[CollectionDefinition("名字")]` 和 `ICollectionFixture<T>`,测试类用同名 `[Collection("名字")]` 挂进来:

```csharp
/// <summary>
/// 集合定义类:从不被实例化,只承载 [CollectionDefinition] 与 ICollectionFixture&lt;T&gt;。
/// </summary>
[CollectionDefinition("orders-shared")]
public class OrdersCollection : ICollectionFixture<SharedOrdersFixture>
{
}

[Collection("orders-shared")]
public class OrderCreationTests
{
    private readonly SharedOrdersFixture fixture;

    public OrderCreationTests(SharedOrdersFixture fixture)
    {
        this.fixture = fixture;
        SharedOrdersFixture.SeenIds.TryAdd(fixture.Id, 0);
    }
    // …测试省略…
}

[Collection("orders-shared")]
public class OrderFulfillmentTests
{
    // 同样的构造注入,测试省略
}
```

报告里的集合结构证明两个类确实合并成了一个集合(默认才是每类一个集合):

```text
<collection name="orders-shared" … total="4">
    Ch05.Lifecycle.Tests.OrderFulfillmentTests.Fulfill_CreatedOrder_StateIsFulfilled
    Ch05.Lifecycle.Tests.OrderFulfillmentTests.Ledger_IsTheSameInstance_AcrossClassesOfTheCollection
    Ch05.Lifecycle.Tests.OrderCreationTests.Fixture_IsSharedAcrossClasses_InSameCollection
    Ch05.Lifecycle.Tests.OrderCreationTests.Create_NewOrder_StateIsCreated
```

共享范围的断言与 5.3 同款:`InstancesCreated == 1`、两个类的构造器登记的 `SeenIds` 只有一个 Id。而**串行保证**用并发计数证明:夹具的 `EnterAndAssertExclusive` 把在飞计数加一并断言它等于 1,测试体里故意 `Task.Delay(100)` 拉开时间窗——同一集合内的类不会并行跑,计数到不了 2:

```csharp
public void EnterAndAssertExclusive()
{
    var current = Interlocked.Increment(ref inFlight);
    Assert.True(current == 1,
        $"{current} tests were in flight at once; classes in one collection must not run in parallel");
}
```

这条串行保证不是集合夹具的私有规定,而是并行模型的规则:默认并行模式下"集合间并行、集合内串行"(运行 `dotnet run --project Ch05.Lifecycle -- -diagnostics` 时,报告头部会显示 `parallel mode = collections [N threads]` 与 seed)。并行配置、如何退出并行,第 6 章展开;本章只需要记住:**把类放进同一个集合,就同时得到了共享夹具和串行执行**。

**强类型集合**([`TypedCollectionFixtureTests.cs`](../code/Ch05.Lifecycle/TypedCollectionFixtureTests.cs)):字符串名字要求两边一字不差——拼错的名字会让该类挂进一个没有定义的新集合,夹具找不到。构造注入的写法分析器先给一条 xUnit1041 警告(`Fixture argument 'fixture' does not have a fixture source…`);真跑起来,失败是一条和 5.3 那条"未解析的构造参数"不同的运行期消息:`The following constructor parameters did not have matching fixture data: SomeFixture fixture`。v3 的替代写法是定义类用无参 `[CollectionDefinition]`,测试类用泛型特性直接指向定义类型:

```csharp
[CollectionDefinition]
public class InventoryReservationCollection : ICollectionFixture<ReservationLedgerFixture>
{
}

[Collection<InventoryReservationCollection>]
public class ReservationHoldTests { /* … */ }

[Collection(typeof(InventoryReservationCollection))]
public class ReservationReleaseTests { /* … */ }
```

`[Collection<TDef>]` 与 `[Collection(typeof(TDef))]` 等价,拼错在编译期就是错误;泛型特性要求 .NET 8+(.NET Framework 不支持,编译器不报错但运行时不可用——本教程是 net10.0,放心用)。注意只有引用侧是泛型:`CollectionDefinitionAttribute` 本身没有泛型版本,写成 `[CollectionDefinition<TDef>]` 编译器会拒绝:

```text
error CS0308: The non-generic type 'CollectionDefinitionAttribute' cannot be used with type arguments
```

两个类指向同一个定义类型,报告里就是一个集合(`total="4"`),夹具实例仍是一个——`SameTypedCollection_TwoWaysToReference_StillOneFixture` 用计数断言证明两种引用写法汇入同一集合。

集合定义必须与使用它的测试在同一个程序集里(夹具类型本身可以跨程序集,定义不行)。

## 5.5 程序集夹具:整个程序集共享一个实例

范围最大的一档:v3 新增。程序集级特性注册,实例在**任何测试之前**构造,在**全部测试结束后**释放:

```csharp
// AssemblyFixtures.cs(程序集级特性必须在命名空间声明之前,所以用完全限定名)
[assembly: AssemblyFixture(typeof(Ch05.Lifecycle.Tests.TestRunClock))]
[assembly: AssemblyFixture<Ch05.Lifecycle.Production.AuditSink>]
```

`typeof` 形式在所有支持的运行时可用;泛型形式是 4.0 补齐的,同样要求 .NET 8+。测试类取用它**不需要实现任何标记接口**——直接写构造参数即可:

```csharp
public sealed class RunClockSharingTests
{
    private readonly TestRunClock clock;

    public RunClockSharingTests(TestRunClock clock)
    {
        this.clock = clock;
        FixtureIdentity.Record(clock);
    }

    [Fact]
    public void Clock_ExistsBeforeAnyTest_AndIsBuiltOnce()
    {
        // 本测试没有构造过 TestRunClock:InstancesCreated==1 说明它先于一切测试被创建
        Assert.Equal(1, TestRunClock.InstancesCreated);
        Assert.True(clock.RunStartedAt <= DateTimeOffset.UtcNow);

        FixtureIdentity.AssertSingleInstanceOf<TestRunClock>();
    }

    // …第二个测试 AuditSink_SameInstanceAsInjectedInOtherClass 省略…
}
```

`FixtureIdentity` 是一张跨类登记表:每个测试类把"我看到的夹具实例"的身份记录进去,断言每个类型只出现一个身份。`AuditSinkSharingTests` 用构造注入、`RunClockSharingTests` 用 `GetFixture`(5.7),两边记录的身份相同——跨类共享成立,且"先于一切测试存在"由 `InstancesCreated == 1` 佐证。

构造约束比类夹具严格,而且是**编译期**检查。给程序集夹具写一个带 `int` 参数的构造器,分析器立刻停下:

```text
error xUnit3005: Type 'Ch05.Lifecycle.Tests.BadAssemblyCtor' must have a non-obsolete public constructor: public Ch05.Lifecycle.Tests.BadAssemblyCtor([ITestContextAccessor accessor], [ITestOutputHelper helper], [IMessageSink diagnosticMessageSink]) (https://xunit.net/xunit.analyzers/rules/xUnit3005)
```

也就是说:public、无过时构造器;可注入的参数只有 `ITestContextAccessor`、`ITestOutputHelper`、`IMessageSink` 三个(都是可选)。

最后一个关键差别,官方文档写得很直白:**程序集夹具不改变并行行为**。类夹具的宿主类在默认并行模式下串行,集合夹具把成员类串行化,而程序集夹具的实例可能被同时运行的多个测试触碰——它必须自己线程安全。`AuditSink` 用 `ConcurrentQueue` 实现,不是风格偏好,是这一条要求的直接后果。典型用途:数据库连接、测试容器(Testcontainers)、全局时钟这类"整个运行期都要、且本来就该并发安全"的资源。

## 5.6 用哪一档:范围、隔离性、代价

| 手段 | 实例创建时机 | 共享范围 | 状态隔离 | 代价与前提 |
| --- | --- | --- | --- | --- |
| 构造器 + `IDisposable` / `IAsyncLifetime` | 每个测试 | 无(只共享代码) | 完全隔离 | 初始化便宜时这是默认答案;异步初始化用 `IAsyncLifetime` |
| `IClassFixture<T>` | 类内第一个测试前 | 一个测试类 | 默认并行模式下类内串行 | 初始化昂贵且类内需要共享可变状态时 |
| `[CollectionDefinition]` + `ICollectionFixture<T>` | 集合内第一个测试前 | 集合内所有类 | 成员类之间串行 | 跨类共享;定义类须与测试同程序集 |
| `[assembly: AssemblyFixture]` | 全部测试前 | 整个程序集 | 无,可能并发访问 | 必须线程安全;失败波及全部测试(5.8) |

选择顺序应当是自下而上:先假设每个测试自己构造(5.1 的模型免费且干净);只有当初始化确实昂贵到影响运行时间,才升一档;再需要跨类,才升到集合;**程序集夹具是最后手段,不是最方便的默认**。反面的味道是这样的:把"每个测试都要用的业务对象"塞进程序集夹具,于是所有测试都在变更同一个对象,测试开始互相依赖,于是要排序、要重置、要在夹具里加防御代码——每一步都在为当初的共享决定付利息。5.1 的 `SharedRegistry` 反例是同一个教训的 `static` 版本:生命周期越长,耦合的半径越大。

判断标准很简单:**共享无状态或只读的昂贵资源(已加载的目录、连接、容器)是夹具的正确用法;共享可变业务状态,是给自己埋耦合。** `Catalog` 只读,类夹具安全;`OrderLedger` 可变,但它的集合夹具换来"成员类串行"的保证,变更是受控的;`AuditSink` 可变且并发,所以它必须线程安全。

## 5.7 不写构造参数:GetFixture 与管道通知

**`TestContext.Current.GetFixture<T>()`。** 构造注入不是取用夹具的唯一途径;不方便加构造参数(参数已经很多、工具类方法里)时:

```csharp
var fixture = (await TestContext.Current.GetFixture<ReservationLedgerFixture>())!;
```

它是异步的(`ValueTask<T>`),要 `await`。`TestContext.Current` 是"此刻"的快照,拿到就用,不要存字段。能解析的范围就是当前测试可见的夹具(程序集/集合/类);类夹具即使测试类没写构造参数也会被创建,`GetFixture` 照样能取到。

**管道通知接口(4.0)。** 夹具可以订阅执行流水的事件,按粒度分六级,同步/异步成对:

| 接口 | 可用于哪些夹具 |
| --- | --- |
| `INotifyTestAssemblyLifecycle(Async)` | 程序集夹具 |
| `INotifyTestCollectionLifecycle(Async)` | 程序集、集合夹具 |
| `INotifyTestClassLifecycle(Async)` | 程序集、集合、类夹具 |
| `INotifyTestMethodLifecycle(Async)` | 同上 |
| `INotifyTestCaseLifecycle(Async)` | 同上 |
| `INotifyTestLifecycle(Async)` | 同上 |

异步版签名是 `ValueTask OnTestStartingAsync(IXunitTest test)` / `ValueTask OnTestFinishedAsync(IXunitTest test)`;同步版去掉了 `Async` 后缀。5.3 的 `WarmCatalogFixture` 已经用 `OnTestFinished` 计数来守卫 Dispose 时机。最有代表性的用法是"**共享夹具 + 每测试重置**":夹具本身昂贵、跨测试共享,但它承载的可变状态在每个测试开始前被清干净——[`LifecycleNotificationTests.cs`](../code/Ch05.Lifecycle/LifecycleNotificationTests.cs):

```csharp
public sealed class PerTestResetFixture : INotifyTestLifecycleAsync
{
    public int Counter { get; set; }

    public ValueTask OnTestStartingAsync(IXunitTest test)
    {
        Counter = 0;
        TestContext.Current.TestOutputHelper!.WriteLine(
            $"OnTestStartingAsync: reset Counter before [{test.TestDisplayName}]");
        return ValueTask.CompletedTask;
    }

    public ValueTask OnTestFinishedAsync(IXunitTest test)
    {
        TestContext.Current.TestOutputHelper!.WriteLine(
            $"OnTestFinishedAsync: Counter={Counter}");
        return ValueTask.CompletedTask;
    }
}
```

两个测试分别把 `Counter` 改成 7 和 1,但每个测试的第一条断言都是 `Assert.Equal(0, fixture.Counter)`——不管执行顺序如何都成立,因为重置发生在每个测试开始前。报告里能看到事件与测试体的穿插(夹具通过 `TestContext.Current.TestOutputHelper` 写进了当前测试的输出):

```text
<test name="Ch05.Lifecycle.Tests.PerTestResetTests.SharedState_IsZero_BeforeEachTestStarts" result="Pass" …>
<output>OnTestStartingAsync: reset Counter before [Ch05.Lifecycle.Tests.PerTestResetTests.SharedState_IsZero_BeforeEachTestStarts]
OnTestFinishedAsync: Counter=7
</output>
```

测试级事件与 `[BeforeAfterTestAttribute]` 的时机相当,但通知接口支持异步,而且逻辑收在夹具自己身上,不用散落到特性里。

## 5.8 三个典型陷阱与失败的真实形态

**陷阱一:把线程不安全的对象共享给并行的类。** 集合夹具和程序集夹具都可能被并发访问(前者只串行化"同一集合内",后者完全不改变并行)。本章的 `OrderLedger`、`AuditSink` 全部用并发集合实现,不是防御性编程,是共享范围决定的硬要求。

**陷阱二:夹具里放可变业务状态。** 见 5.6 与 5.1 的 `SharedRegistry`——隔离被放弃后,测试开始依赖顺序,"偶发红"开始出现。

**陷阱三:分不清夹具失败的报告形态。** 初始化失败发生在测试体外,但它记在哪里,取决于夹具的层级和失败点。[`FixtureFailureShapeTests.cs`](../code/Ch05.Lifecycle/FixtureFailureShapeTests.cs) 把三种形态做成了可复现的演示:夹具默认健康(全绿),用环境变量注入失败。

## 动手练习

1. **异步的集合夹具。** 给 `SharedOrdersFixture` 实现 `IAsyncLifetime`:在 `InitializeAsync` 里预置一个订单,并加计数。给 `OrderCreationTests` 加一条断言:集合内第一个测试运行时,预置订单已可读、初始化计数为 1。验收:`dotnet test --project Ch05.Lifecycle` 全绿;你能说出 `InitializeAsync` 相对"集合内第一个测试"的发生时机。

## 本章小结

- xUnit 的默认模型:每个测试新建一个测试类实例,构造器是每测试的 setup,`Dispose` 是每测试的 teardown;计数断言(`ctorCount`/`disposeCount`/实例编号去重)能把它变成可证明的事实。
- 实例隔离不覆盖 `static` 状态;跨实例的可变状态就是测试耦合,表现为"偶发红"。
- `IAsyncLifetime`(`ValueTask InitializeAsync()` / 来自 `IAsyncDisposable` 的 `ValueTask DisposeAsync()`)补足构造器不能 await 的空隙;同时实现 `IDisposable` 时只有 `DisposeAsync` 被调用;v3 允许单独实现 `IAsyncDisposable`。
- 三档夹具按范围递增:`IClassFixture<T>`(一个类)、`[CollectionDefinition]` + `ICollectionFixture<T>`(多个类,附带集合内串行)、`[assembly: AssemblyFixture]`(整个程序集,不改变并行,必须线程安全)。集合定义须与测试同程序集;程序集夹具的构造签名受分析器(xUnit3005)编译期检查。
- 具名集合靠字符串配对,拼错在运行期报"没有匹配的夹具数据";强类型集合用无参 `[CollectionDefinition]` + `[Collection<TDef>]`(.NET 8+ 泛型特性)把拼写错误拦在编译期;`CollectionDefinitionAttribute` 本身没有泛型版本。
- 自下而上选型:构造器优先;共享只读的昂贵资源是夹具的正道,共享可变业务状态要配重置机制(管道通知)或别共享。
- `TestContext.Current.GetFixture<T>()` 免构造注入;`INotifyTestLifecycle(Async)` 等六级通知接口(4.0)让夹具感知测试开始/结束,可做"共享夹具 + 每测试重置"。
- 失败形态三种:类夹具构造失败记在测试头上;夹具清理失败是独立的 `[Test Class Cleanup Failure (…)]` 条目(测试本身仍 Pass);程序集夹具构造失败让全部测试连 Skip 一起红。类一旦启动,单个 `Skip`/`Explicit` 测试不豁免夹具的创建;整类都被跳过则类不启动。
