# 第 9 章 · 输出、诊断与调试

> 你将学会:
> - 用 `ITestOutputHelper` 的构造注入和四个写入重载,给测试写下属于它自己的输出
> - 说清默认的显示规则:通过的测试不显示输出、失败的测试输出跟在失败报告里;实时输出在原生 runner 里怎么打开,MTP 里为什么看不见
> - 用 `[assembly: CaptureConsole]` / `[assembly: CaptureTrace]` 把现有代码写进 `Console` / `Debug` / `Trace` 的日志搬进测试输出,并知道这两个开关的程序集级副作用与 Release 下的 `Debug` 边界
> - 用 `TestContext.Current` 的 `SendDiagnosticMessage`、`AddWarning`、`AddAttachment`、`KeyValueStorage` 分别做运行日志、软性告警、结果附件和跨管道阶段传值
> - 系统地读一份失败输出:结果行、断言或异常消息、堆栈、测试输出四块;太长时用 `--print-max-*`(全局)或 `Assert.OverrideMax*`(单条测试)调节篇幅
> - 用 `--stop-on-fail`、`-waitForDebugger`、`-wait` 这些开关缩短调试循环
> - 把大测试拆开定点调试:复制一份只做 Arrange 验前提、复制一份只留被测方法与最小输入、Theory 用条件断点、异步测试把"输入↔线程↔任务状态"记进输出

本章有两个工程。[`code/Ch09.Output`](../code/Ch09.Output) 是被测代码在 [`Production/`](../code/Ch09.Output/Production/) 的常规章节工程:`InvoiceRow`(发票行)、`InvoiceBook`(固定的对账样本)、`InvoiceReconciler`(把发票与台账逐行比对,可选地把过程日志写进 `Console` 和 `Trace`/`Debug`,并能生成一份文本差异报告)。[`code/Ch09.Output.Capture`](../code/Ch09.Output.Capture) 是一个只有四个测试的小工程,专门用来演示程序集级的输出捕获——把 `[assembly: CaptureConsole]` / `[assembly: CaptureTrace]` 关在这一个程序集里,它们不会影响本章其它测试类,也不会影响别的章。

下面所有输出片段都来自本机 .NET SDK 10.0.113(运行时 .NET 10.0.13)+ xUnit.net v3 4.0.2 的真实运行;绝对路径用 `...` 省略,runner 的横幅与无关汇总行偶尔省略,省略处用 `…` 或 `...` 标出,不影响被说明的行为;其余逐字保留。会失败的演示都挂着 `Skip`,去掉对应的 `Skip` 即可复现。

## 9.1 ITestOutputHelper:属于这个测试的输出

测试输出不是"打到控制台的东西",它是**绑定在某个测试上的一段文本**:跟着测试结果走,进报告文件,在并行执行时不会和别的测试混在一起。写它的唯一入口是 `ITestOutputHelper`,构造注入。

```csharp
// Ch09.Output/TestOutputBasicsTests.cs
public class TestOutputBasicsTests(ITestOutputHelper output)
{
    [Fact]
    public void WriteAndWriteLine_UsePlainAndFormattedOverloads()
    {
        output.Write("Write 不追加换行,");
        output.WriteLine("WriteLine 追加换行。");

        output.Write("格式化 Write:发票 {0} 行 / 台账 {1} 行", InvoiceBook.Invoices.Length, InvoiceBook.Ledger.Count);
        output.WriteLine("格式化 WriteLine:容差 {0:0.000} / 比例 {1:P1}", 0.005m, 0.0125m);

        var mismatched = InvoiceReconciler.FindMismatchedRows(InvoiceBook.Invoices, InvoiceBook.Ledger);
        output.WriteLine("对账差异 {0} 行:{1}", mismatched.Count, string.Join(", ", mismatched.Select(row => row.Id)));

        Assert.Equal(2, mismatched.Count);
    }
```

接口只有四个方法和一个只读的 `Output` 属性:`Write(string)`、`WriteLine(string)`、`Write(string format, params object[] args)`、`WriteLine(string format, params object[] args)`。格式化重载走的是 `string.Format` 那套占位符(`{0}`、`{0:0.00}`、`{1:P1}`),不是插值字符串——写成插值也行(`output.WriteLine($"...")`),那只会命中第一个重载。

输出器可以像普通参数一样往下传,辅助方法也能写同一份输出;不想传来传去时,任何地方都能通过 `TestContext.Current.TestOutputHelper` 拿到它(快照语义,见 9.5 的讨论)。

```csharp
// Ch09.Output/TestOutputBasicsTests.cs(同文件的另一条测试)
    [Fact]
    public void HelperMethod_ReceivesOutputHelper_WritesIntoSameBuffer()
    {
        DescribeRows(output, InvoiceBook.Invoices);

        Assert.Equal(3, InvoiceBook.Invoices.Length);
    }

    private static void DescribeRows(ITestOutputHelper output, IReadOnlyList<InvoiceRow> rows)
    {
        output.WriteLine($"共 {rows.Count} 行发票:");
        foreach (var row in rows)
            output.WriteLine($"  {row.Id} {row.Vendor} {row.Amount:0.00}");
    }
```

### 9.1.2 实时输出:两种 runner 的实测差别

想在测试还在跑的时候就看到输出,原生 runner 用 `-showLiveOutput`:

```text
$ ./bin/Debug/net10.0/Ch09.Output -class "Ch09.Output.Tests.TestOutputBasicsTests" -showLiveOutput

    Ch09.Output.Tests.TestOutputBasicsTests.WriteAndWriteLine_UsePlainAndFormattedOverloads [OUTPUT] Write 不追加换行,WriteLine 追加换行。
    Ch09.Output.Tests.TestOutputBasicsTests.WriteAndWriteLine_UsePlainAndFormattedOverloads [OUTPUT] 格式化 Write:发票 3 行 / 台账 3 行格式化 WriteLine:容差 0.005 / 比例 1.3%
    Ch09.Output.Tests.TestOutputBasicsTests.WriteAndWriteLine_UsePlainAndFormattedOverloads [OUTPUT] 对账差异 2 行:INV-1002, INV-1003
    Ch09.Output.Tests.TestOutputBasicsTests.HelperMethod_ReceivesOutputHelper_WritesIntoSameBuffer [OUTPUT] 共 3 行发票:
    Ch09.Output.Tests.TestOutputBasicsTests.HelperMethod_ReceivesOutputHelper_WritesIntoSameBuffer [OUTPUT]   INV-1001 Fabrikam 120.00
    Ch09.Output.Tests.TestOutputBasicsTests.HelperMethod_ReceivesOutputHelper_WritesIntoSameBuffer [OUTPUT]   INV-1002 Contoso 88.50
    Ch09.Output.Tests.TestOutputBasicsTests.HelperMethod_ReceivesOutputHelper_WritesIntoSameBuffer [OUTPUT]   INV-1003 Litware 42.00
```

注意第二行:`Write` 不带换行,所以后面 `WriteLine` 的内容接在同一行里——这是重载之间的真实差别,不是排版问题。

MTP 侧的开关 `--show-live-output on` 会被接受(不是未知选项),但在 4.0.2 + SDK 10.0.113 下,`dotnet test` 的控制台输出**没有任何变化**:通过的测试仍然一行输出都不打,失败的测试仍然只在失败块里打。实测过三种情形——通过的测试、失败的测试、`--report-xunit-xml` 报告——都看不到"实时"输出行。这台机器上没有可用的交互终端(工具环境里 pty 不可用),所以"接到真终端时是否不同"我没法验证;要实时输出,用原生 runner。

还有一条容易被当成"输出开关"的:原生 `-diagnostics` 会让**带输出的通过测试**补出结果行和 `Output:` 段(9.5 的探针输出里就有),而没有输出的通过测试连结果行都不打。它顺带打开了诊断消息,不是实时输出。

### 9.1.3 输出绑定到测试,不会串台

并行执行时,`output` 写到的是**这个测试**的缓冲区。[`ParallelOutputBindingTests.cs`](../code/Ch09.Output/ParallelOutputBindingTests.cs) 里有两个测试类,分属两个集合,默认并行模式下同时跑,各写各的标记行:

```csharp
// Ch09.Output/ParallelOutputBindingTests.cs(节选)
public class NightshiftReconcileTests(ITestOutputHelper output)
{
    [Fact]
    public async Task Reconcile_Nightshift_LogsEachStep()
    {
        output.WriteLine("[nightshift] 载入夜班发票");
        var mismatched = InvoiceReconciler.FindMismatchedRows(InvoiceBook.Invoices, InvoiceBook.Ledger);
        await Task.Delay(120, TestContext.Current.CancellationToken);
        output.WriteLine($"[nightshift] 第 1 步完成:差异 {mismatched.Count} 行");

        await Task.Delay(120, TestContext.Current.CancellationToken);
        output.WriteLine("[nightshift] 第 2 步完成:夜班结束");
    }
}
```

真实输出(两个测试的时间线交错,每一行都带着自己的测试名):

```text
$ ./bin/Debug/net10.0/Ch09.Output -class "Ch09.Output.Tests.NightshiftReconcileTests" -class "Ch09.Output.Tests.DayshiftReconcileTests" -showLiveOutput
    Ch09.Output.Tests.DayshiftReconcileTests.Reconcile_Dayshift_LogsEachStep [OUTPUT] [dayshift] 载入白班发票
    Ch09.Output.Tests.NightshiftReconcileTests.Reconcile_Nightshift_LogsEachStep [OUTPUT] [nightshift] 载入夜班发票
    Ch09.Output.Tests.DayshiftReconcileTests.Reconcile_Dayshift_LogsEachStep [OUTPUT] [dayshift] 第 1 步完成:差异 2 行
    Ch09.Output.Tests.NightshiftReconcileTests.Reconcile_Nightshift_LogsEachStep [OUTPUT] [nightshift] 第 1 步完成:差异 2 行
    Ch09.Output.Tests.DayshiftReconcileTests.Reconcile_Dayshift_LogsEachStep [OUTPUT] [dayshift] 第 2 步完成:白班结束
    Ch09.Output.Tests.NightshiftReconcileTests.Reconcile_Nightshift_LogsEachStep [OUTPUT] [nightshift] 第 2 步完成:夜班结束
```

结论只有一句:**不用担心串台,但也不要跨测试共享一个 `TextWriter`**。想让信息进报告,就写 `output`;想让信息进运行日志,那是 9.3 的诊断消息。

## 9.2 把现有代码的日志搬进测试输出

真实项目里的日志往往不经过测试:`Console.WriteLine`、`Trace.WriteLine`、某个第三方库内部的输出。v3 提供两个程序集级开关,把它们重定向成测试输出。

### 9.2.1 默认不捕获:日志去了哪里

[`Ch09.Output`](../code/Ch09.Output) 没有加任何捕获开关。[`OutputNotCapturedByDefaultTests.cs`](../code/Ch09.Output/OutputNotCapturedByDefaultTests.cs) 让生产代码"啰嗦"一次:

```csharp
// Ch09.Output/OutputNotCapturedByDefaultTests.cs
    [Fact(Skip = "演示:去掉 Skip 观察未捕获时 Console/Trace 输出的去向(见 9.2)")]
    public void VerboseReconciler_WritesConsoleAndTrace_NotInTestOutput()
    {
        output.WriteLine("这一行来自 ITestOutputHelper:属于测试输出");

        var mismatched = InvoiceReconciler.FindMismatchedRows(InvoiceBook.Invoices, InvoiceBook.Ledger, verboseLogging: true);
        output.WriteLine("这一行仍然来自 ITestOutputHelper;上面/reconciler 的日志不在这里");

        Assert.Equal(2, mismatched.Count);
    }
```

去掉 `Skip` 用原生 runner 跑(生产代码写的是 `Console.Out`、`Console.Error`、`Debug`、`Trace`):

```text
$ ./bin/Debug/net10.0/Ch09.Output -class "Ch09.Output.Tests.OutputNotCapturedByDefaultTests" -showLiveOutput
    Ch09.Output.Tests.OutputNotCapturedByDefaultTests.VerboseReconciler_WritesConsoleAndTrace_NotInTestOutput [OUTPUT] 这一行来自 ITestOutputHelper:属于测试输出
[reconciler] 开始对账:发票 3 行,台账 3 行
[reconciler] 差异 INV-1002:发票 88.50,台账 90.00
[reconciler] 差异 INV-1003:发票 42.00,台账 0.00
[reconciler] 对账结束:差异 2 行
    Ch09.Output.Tests.OutputNotCapturedByDefaultTests.VerboseReconciler_WritesConsoleAndTrace_NotInTestOutput [OUTPUT] 这一行仍然来自 ITestOutputHelper;上面/reconciler 的日志不在这里
```

三点都值得记住:

- `[OUTPUT]` 行属于测试;`[reconciler]` 行属于进程的标准输出/标准错误,不带测试名,失败报告里也不会有它。
- `Debug` / `Trace` 写的两行**根本没出现**:默认的输出监听器不会把它们写到控制台——别指望在终端里"顺便看到"。
- 标准输出和标准错误的行序不保证一致(上面 `差异 …` 是 stderr,排在了 stdout 的"对账结束"之前)。

### 9.2.3 `[assembly: CaptureTrace]` 与 Release 下的 `Debug` 边界

`CaptureTrace` 捕获 `Debug` 和 `Trace`。两者的差别不在框架,而在编译器:`Debug.*` 调用只在定义了 `DEBUG` 符号的编译里存在,Release 编译中被整体剔除。用同一个测试分别在 Debug 和 Release 下跑,边界就摆在眼前:

```text

    … [OUTPUT] [audit] 开始审计:2 行
    … [OUTPUT] [audit] 注意:标准错误也走 Console 捕获这条路
    … [OUTPUT] [audit] Debug 写入:Release 编译下这一行被编译器剔除
    … [OUTPUT] [audit] Trace 写入:任何编译配置下都存在
    … [OUTPUT] [audit] 审计结束:不平 1 行
    … [OUTPUT] [test] 这里直接写 Debug/Trace,不经过任何生产代码
    … [OUTPUT] [direct-debug] 测试里直接写的 Debug
    … [OUTPUT] [direct-trace] 测试里直接写的 Trace
```

(`…` 处是同一个测试的全名,逐字相同,只为排版省略。)

CI 里跑 Release 时,`Debug.WriteLine` 一条都不会有。想让日志在两种配置下都进报告,写 `Trace`;`Debug` 只适合本地调试。

### 9.2.4 程序集级:代价与隔离办法

这两个特性是**程序集级**的:一开就作用于该程序集里的每一个测试,没有类级或方法级的开关。[`Ch09.Output.Capture`](../code/Ch09.Output.Capture) 里另一个什么都没加的类也被捕获:

```csharp
// Ch09.Output.Capture/ConsoleCaptureTests.cs(第二个测试类)
public class ImplicitlyCapturedTests(ITestOutputHelper output)
{
    [Fact]
    public void NoAttributeOnThisClass_StillCaptured()
    {
        output.WriteLine("[test] 只有这一行是我主动写的");
        Console.WriteLine("[implicit] 这个类没加特性,Console 输出仍然进了测试输出");

        var rows = new[] { new AuditRow("B-01", 10m, 10m) };
        Assert.Empty(LegacyAuditWriter.FindUnbalancedRows(rows));
    }
}
```

还有一个更隐蔽的代价:捕获开着时,**测试之外**的 `Console` 写入会被吞掉——既不会归给任何测试,也不会打到控制台。我临时加了一个类夹具探针(跑完已从工程删掉),在 `InitializeAsync` 里同时写 `Console.WriteLine` 和一条诊断消息,用来证明夹具确实执行了:


夹具里那行写进 `Console` 的 `[outside-probe] …` 在输出里消失了,只剩带 `[D::…]` 前缀的那条诊断消息。所以启用捕获之前要清楚:你同时把"夹具、排序器、runner 启动代码里的 `Console` 输出"这条退路也关掉了。

- 需要捕获,就把带 `[assembly: CaptureConsole]` 的工程切出来(像本章这样),或者整个测试工程统一开、并把夹具里的诊断改用诊断消息(9.3)。

## 9.3 诊断消息:运行日志,不属于任何测试

诊断消息走的是另一条通道:它不属于某个测试,而是运行日志,用来回答"这次运行发生了什么、在哪一步"。任何地方都能发:

```csharp
// Ch09.Output/DiagnosticsTests.cs(节选)
    [Fact]
    public void Reconcile_SendsDiagnosticMessagesAroundTheWork()
    {
        TestContext.Current.SendDiagnosticMessage("对账开始:发票 {0} 行 / 台账 {1} 行", InvoiceBook.Invoices.Length, InvoiceBook.Ledger.Count);

        var mismatched = InvoiceReconciler.FindMismatchedRows(InvoiceBook.Invoices, InvoiceBook.Ledger);

        TestContext.Current.SendDiagnosticMessage("对账结束:差异 {0} 行;运行环境:{1}", mismatched.Count, environment.Snapshot);
        Assert.Equal(2, mismatched.Count);

```

`SendDiagnosticMessage` 有 `string` 和格式化重载(`arg0`…`arg2` 与 `params object[]`)。夹具和排序器里同样能发——[`DiagnosticsTests.cs`](../code/Ch09.Output/DiagnosticsTests.cs) 里的 `RunEnvironmentProbeFixture` 就在 `InitializeAsync` 里发了一条环境快照。

默认不显示,原生 runner 用 `-diagnostics` 打开:

诊断消息的典型用途:

- **定位卡死**:测试挂住时,最后一条诊断就是流水线当时所处的位置(9.5 的排序器探针就是这么设计的)。配合第 8 章的 `-longRunning <秒>` 用。
- **环境信息**:机器名、运行时、处理器数、文化、配置。CI 上复现"只在这台机器上失败"时,这些信息比截图可靠。
- **框架自身的诊断**:并行头部与 seed(上面那条 `Starting:`)。

实测边界,两条都要写进你的预期:

- MTP 下 `--xunit-diagnostics on`、`--xunit-internal-diagnostics on` 都被接受,但控制台里**一条诊断都不打**;把 `diagnosticMessages: true` 写进配置文件也一样,生成的 `--report-xunit-xml` 报告里也没有诊断条目。要看诊断,用原生 runner。
- 原生 `-internalDiagnostics`(框架内部诊断)在这些运行里没有增加任何输出行——它面向框架自身的问题排查,日常用 `-diagnostics` 就够。

## 9.5 KeyValueStorage:跨管道阶段传值

`TestContext.Current.KeyValueStorage` 是一个 `ConcurrentDictionary`,同一个运行里各管道阶段共享。它的定位是**传运行标记**,不是给测试用的共享状态容器。

[`Ch09.Output/KeyValueStorageTests.cs`](../code/Ch09.Output/KeyValueStorageTests.cs) 把三个阶段的读写拼成一个探针:`AssemblyInfo.cs` 注册一个程序集级类排序器(它原样返回输入,不改顺序),夹具在测试开始前写一个键,测试读旧键、写新键:

```csharp
// Ch09.Output/AssemblyInfo.cs(节选)
[assembly: TestClassOrdererAttribute<Ch09.Output.Tests.RunMarkerOrderer>]
```

```csharp
// Ch09.Output/KeyValueStorageTests.cs(节选)
public class RunMarkerOrderer : ITestClassOrderer
{
    public IReadOnlyCollection<TTestClass?> OrderTestClasses<TTestClass>(IReadOnlyCollection<TTestClass?> testClasses)
        where TTestClass : ITestClass
    {
        var storage = TestContext.Current.KeyValueStorage;

        TestContext.Current.SendDiagnosticMessage(
            "[kvs] 排序器被调用:阶段={0},此刻可见的键:{1}",
            TestContext.Current.PipelineStage,
            storage.Count == 0 ? "(无)" : string.Join(", ", storage.Keys.OrderBy(key => key)));

        storage.TryAdd("run.startedUtc", DateTimeOffset.UtcNow.ToString("O"));

        return testClasses;
    }
}

public class NightBatchContext : IAsyncLifetime
{
    public string BatchId { get; } = "nightly-2026-10-22";

    public ValueTask InitializeAsync()
    {
        TestContext.Current.KeyValueStorage["batch.id"] = BatchId;

        return ValueTask.CompletedTask;
    }

    public ValueTask DisposeAsync() => ValueTask.CompletedTask;
}
```

把两个测试类按顺序跑(顺序可控才能看清可见性):

```text
$ ./bin/Debug/net10.0/Ch09.Output :12345 -class "Ch09.Output.Tests.StorageWriterTests" -class "Ch09.Output.Tests.StorageReaderTests" -diagnostics -parallelMode none

    [D::Ch09.Output] [kvs] 排序器被调用:阶段=TestCollectionExecution,此刻可见的键:(无)
    Ch09.Output.Tests.StorageWriterTests.Reconcile_PublishesRunMarkersThroughStorage [PASS]
      Output:
        排序器写入的 run.startedUtc = 2026-10-23T04:01:19.8619679+00:00
        本测试写回 reconcile.mismatchCount = 2
    [D::Ch09.Output] [kvs] 排序器被调用:阶段=TestCollectionExecution,此刻可见的键:batch.id, reconcile.mismatchCount, run.startedUtc
    Ch09.Output.Tests.StorageReaderTests.Report_ReadsMarkersWrittenByEarlierStages [PASS]

        run.startedUtc = 2026-10-23T04:01:19.8619679+00:00
        storage[batch.id] = nightly-2026-10-22
```

实测出来的边界:

- **能看到什么**:排序器在 `TestCollectionExecution` 阶段被调用(每个测试集合前一次),能读能写;夹具在 `TestClassExecution` 阶段写的键,该类的测试能读到;测试写的键,后面的阶段(夹具的 `DisposeAsync`、下一个集合的排序器、另一个类的测试)都能读到——它作用域是整个测试程序集的运行,不是单个测试。
- **顺序不可靠**:上面用 `:12345` + `-parallelMode none` 才把顺序固定下来。默认并行 + 随机顺序下,另一个类写的键**可能还没写**。所以读的一方要么只依赖"更早阶段一定写过"的键(排序器、自己集合的夹具),要么把缺失当正常分支处理。
- **别用它替代夹具**:夹具是类型安全的构造注入(第 5 章),`KeyValueStorage` 是字符串键 + `object`。需要传依赖就用夹具;需要跨阶段传"运行标记"(开始时间、批次号、已经跑过某个前置步骤)才用它。
- 它是并发字典,并行写安全;但"检查再写"要自己用 `TryAdd`(上面的排序器就是这么写的)。

`TestContext.Current` 本身是"某一时刻的快照"(第 5、8 章都提到过):当下用,不要存起来跨阶段复用。

```text
  Assert.Contains() Failure: Sub-string not found
  String:    "nightly reconciliation diff\ngenerated: 2026-10-22T"···
  Not found: "Fabrikam Supply Co"
```

两个 runner 都有全局开关。原生侧:

```text
$ ./bin/Debug/net10.0/Ch09.Output -method "…NightlyDiff_ExpectingEmptyMismatchList_TruncatesCollectionPrint" -printMaxEnumerableLength 8

```

第一个例子里 `···` 恰好出现在第 8 个元素之后;第二个例子里字符串打满约 200 个字符才被截断。MTP 侧同名开关 `--print-max-enumerable-length 40` 的效果是把 40 个元素全部打出来,行尾是 `]` 而不是 `···`:

```text
…, InvoiceRow { Id = INV-0039, Vendor = Fabrikam, Amount = 390 }, InvoiceRow { Id = INV-0040, Vendor = Fabrikam, Amount = 400 }]
```

只想调这一条测试,用第 3 章讲过的 `Assert.OverrideMax*`(只影响当前测试):

```csharp
// Ch09.Output/DebugFieldGuideTests.cs
    [Fact(Skip = "演示:去掉 Skip 观察 OverrideMaxEnumerableLength 放宽打印(见 9.6)")]
    public void NightlyDiff_RaisingLimitInsideTest_PrintsMoreItems()

        var rows = Enumerable.Range(1, 40).Select(i => new InvoiceRow($"INV-{i:D4}", "Fabrikam", i * 10m)).ToList();

        Assert.OverrideMaxEnumerableLength(12);
        Assert.Empty(rows);

```

去掉 `Skip` 后,失败消息里恰好打 12 个元素再接 `···`:

```text

```

反过来,长字符串的差异输出会走"上下文窗口"形态,直接指出差异位置:

先读 `pos`,再去数据里定位那一段——比通读整份报告快。

### 9.6.4 断点与附加调试器

IDE 里调试测试就是常规操作:Visual Studio / VS Code 的测试视图里对单条测试选"调试",Rider 的 Unit Testing 视图同理。这时断点、单步、监视都是现成的;要记住一条:**检测到调试器附加时,`Timeout` 不参战**(第 8 章 8.6),否则你在断点上停两分钟测试就被判超时了。CI 里没有调试器,超时照常生效。

不带 IDE、只有一条命令行时,原生 runner 的四个开关把"附加调试器"这件事变得可行(`-?` 里的原文):

```text
  -debug             : launch the debugger to debug the tests
  -pause             : wait for input before running tests (ignored with -automated)
  -wait              : wait for input after completion (ignored with -automated)
  -waitForDebugger   : pauses execution until a debugger has been attached
```

`-waitForDebugger` 实测会停在测试开始之前:

```text
$ timeout 5 ./bin/Debug/net10.0/Ch09.Output -method "…Reconcile_AttachesBinaryArtifactWithMediaType" -waitForDebugger
xUnit.net v3 In-Process Runner v4.0.2+0c7aa4991f (64-bit .NET 10.0.13)
Waiting for debugger to be attached... (press Ctrl+C to abort)
```

命令是 `timeout 5 …`,没有调试器附加,5 秒后进程被 `timeout` 杀掉(退出码 124)。

这段时间里把调试器接上去:Linux 用 `gdb -p <pid>` 或 `lldb -p <pid>`(非 root 附加时可能被 `ptrace_scope` 挡住),Windows 用 `windbg -p <pid>`,或者用 IDE 的"Attach to Process"(`dotnet attach` 不是 .NET CLI 的命令,没有这个子命令)。接上之后断点就打得上了。`-wait` 是运行结束后挂住进程(便于看输出、附加上去看现场),它需要真正的控制台输入:

```text
$ ./bin/Debug/net10.0/Ch09.Output -method "…Reconcile_AttachesBinaryArtifactWithMediaType" -wait < /dev/null
…
Press any key to continue...error: Cannot read keys when either application does not have a console or when console input has been redirected. Try Console.Read.
```

进程退出码 4。

`-pause` 同理(`Press any key to start execution...`)。这两个开关在 CI、容器、管道里都会失败退出——它们是给交互终端用的。MTP 侧没有对应开关:`dotnet test` 调试走的是 IDE 的调试器,不是这几个参数。

### 9.6.5 把大测试拆开:复制、减法、条件断点

测试一大,"到处打日志 + 到处下断点"就不管用了。先把它**拆开**,再对拆出来的小块下断点——三条可复用的做法:

1. **复制一份,只做 Arrange**。把失败的测试复制一份,删掉 Act/Assert,只保留准备数据的段落,然后**对输入本身做断言**:夹具里到底有几行?那个键在不在字典里?期望的金额是多少?这一步就红,说明问题出在"前提不是我以为的那样",而不是被测方法——这类"前提漂移"是夹具共享(第 5 章)之后最常见的失败来源。
2. **复制一份,反过来做减法**。把夹具数据全删掉,只留被测方法和**能触发目标行为的最小输入**。如果最小输入下行为正确,问题在输入数据;如果最小输入下也能复现失败,你要调试的代码范围已经缩到最小,单步成本极低。
3. **Theory 用条件断点**。一条 Theory 每个数据行执行一次,在方法体里下断点会每行都停。IDE 的断点都支持**条件**:右键断点,条件写 `input == "error data"`(变量名就是参数名),断点只在你要的那一行数据上命中。

[`DebugDecomposeTests.cs`](../code/Ch09.Output/DebugDecomposeTests.cs) 把前两条做成了可运行的对照:同一个对账场景,一份只断言输入,一份只喂最小数据:

```csharp
// Ch09.Output/DebugDecomposeTests.cs(节选)
    [Fact]
    public void Decompose_ArrangeOnly_AssertsInputs()
    {
        // 原测试(9.4 的 Reconcile_...)的副本,只保留 Arrange 段,并断言输入本身。
        // 这一步就红 ⇒ 问题出在"前提不对",与被测方法无关。
        Assert.Equal(3, InvoiceBook.Invoices.Length);
        Assert.Equal(90.00m, InvoiceBook.Ledger["INV-1002"]);
        Assert.Contains("INV-1004", InvoiceBook.Ledger);
        Assert.DoesNotContain("INV-1003", InvoiceBook.Ledger);
    }
```

第三条技巧(异步测试的调试)的常见形态是:复制一份,**不关心业务结果,只观察被创建出来的任务**——每条输入对应哪个任务、跑在哪个线程、此刻什么状态,全部用 `ITestOutputHelper` 记下来。`AsyncObservation_LogsInputThreadAndTaskStatus` 就是这么写的,`-showLiveOutput` 下的真实输出:

```text
$ ./bin/Debug/net10.0/Ch09.Output -class "Ch09.Output.Tests.DebugDecomposeTests" -showLiveOutput
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT] 创建任务数=3,主线程=7
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT]   [task] input=boom thread=9 开始执行
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT]   [task] input=slow thread=4 开始执行
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT]   [task] input=fast thread=6 开始执行
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT] input=fast 创建后立刻状态=RanToCompletion
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT] input=slow 创建后立刻状态=Running
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT] input=boom 创建后立刻状态=Running
    …
    Ch09.Output.Tests.DebugDecomposeTests.AsyncObservation_LogsInputThreadAndTaskStatus [OUTPUT] input=boom 最终状态=Faulted
   Ch09.Output  Total: 3, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 0.142s
```

三个任务落在三个不同的线程池线程上;"创建后立刻状态"那一列把 `fast` 已经跑完、`slow`/`boom` 还在跑的区别直接摊开——偶发的"任务没跑完就断言"类问题,这种记录比猜要快得多。最后测试用 `Assert.Equal(["boom"], faulted)` 断言只有 `boom` 这条失败,证明观察本身没有掩盖行为。

还有一条与调试直接相关的经验:**本地全绿、流水线上偶发红**,多数不是测试逻辑问题,而是**前提不同**。把前提记进测试输出或诊断消息——OS、feature flag、环境变量、"某个期望存在的文件在不在"——流水线的失败报告里就有了对照现场(第 11 章 11.6 整节讲这条排查路径)。

## 9.7 排错清单

| 现象 | 先查什么 |
| --- | --- |
| 测试挂起、没有失败也没有结果 | 原生 runner:`-longRunning <秒>`(第 8 章)+ `-diagnostics`,看最后一条诊断停在哪个阶段(9.3、9.5 的探针就是干这个的);`Starting:` 行的并行模式与 seed 也在诊断里 |
| 明明写了输出,运行里看不到 | 默认只在失败时显示(9.1.1)。通过的测试要用原生 `-showLiveOutput`;MTP 的 `--show-live-output on` 在 4.0.2 下不改变控制台输出(9.1.2) |
| 生产代码的日志不在失败报告里 | 该工程没有 `[assembly: CaptureConsole]` / `[assembly: CaptureTrace]`(9.2.1);`Trace` 在没有捕获时根本不打到控制台 |
| Release 下少了 `Debug` 日志 | `Debug.*` 在非 `DEBUG` 编译里被剔除(9.2.3),要常驻就用 `Trace` |
| 警告在 MTP 控制台里没出现 | MTP 默认不打警告;它在报告文件里,或者用 `--fail-warns on` 让它拦人(9.4.1) |
| 附件"不见了" | MTP 把附件写成文件落在 `bin/<配置>/<框架>/TestResults/<测试用例 ID>/<附件名>`,运行摘要里会列出来;`--results-directory` 可改位置(9.4.2) |
| 报告里没有附件 | JUnit 报告不带附件;要下游能取到,用 xUnit 自己的 XML 报告(第 10 章) |
| 诊断消息一条都没有 | MTP 不显示 xUnit 诊断,连配置文件也不行;用原生 runner 的 `-diagnostics`(9.3) |
| 失败消息里集合只打几个元素 | 默认上限(实测 5 个元素、约 50 字符);整次运行用 `--print-max-*` / `-printMax*`,单条测试用 `Assert.OverrideMax*`(9.6.2) |
| 调试器里断点打不上 | 用原生 `-waitForDebugger` 先挂住进程再附加;`-wait` / `-pause` 需要交互控制台(9.6.4) |

## 本章小结

- `ITestOutputHelper` 构造注入,四个重载:`Write`/`WriteLine` × 纯文本/格式化;输出器可以当参数传,也可用 `TestContext.Current.TestOutputHelper`。**输出绑定到测试**:并行下不会串台,每条实时行都带测试名。
- 默认只有失败测试的输出会显示(MTP 在 `Standard output` 段,原生在 `Output:` 段)。实时输出用原生 `-showLiveOutput`;MTP 的 `--show-live-output on` 在 4.0.2 下不改变控制台输出。原生 `-diagnostics` 会顺带把通过测试的输出补出来,那不是实时输出。
- `[assembly: CaptureConsole]` / `[assembly: CaptureTrace]` 是程序集级、默认关闭:开了,`Console`(标准输出+标准错误)、`Debug`、`Trace` 都进该程序集每个测试的输出流;`CaptureOut` / `CaptureError` 可分别关。代价:测试之外(夹具等)的 `Console` 写入会被吞掉。`Debug.*` 在 Release 编译里被剔除,常驻日志用 `Trace`。
- `SendDiagnosticMessage` 是运行日志,不属于任何测试:用来定位卡死、记录环境、看框架自己的并行头部与 seed。原生 `-diagnostics` 可见;MTP 的 `--xunit-diagnostics` / `--xunit-internal-diagnostics` 在 4.0.2 下不显示任何诊断,报告里也没有。
- `AddWarning` 随通过的测试报告(原生直接打,MTP 只在报告里),`--fail-warns on` / `-failWarns` 把它升级成失败(`FAIL_WARN`)。`AddAttachment` 支持文本与 `byte[] + mediaType`;MTP 下附件落盘到 `TestResults/<测试用例 ID>/<附件名>`,xUnit XML 报告内联附件,JUnit 报告不带附件。
- `KeyValueStorage` 在整个运行内共享:排序器(`TestCollectionExecution`)、夹具(`TestClassExecution`)、测试体都能读写,跨类可见;但顺序不可靠,别用它替代类型安全的夹具,只传运行标记。
- 失败输出四块:结果行、断言/异常消息(`Expected`/`Actual` + `pos`)、堆栈(找你代码的第一帧)、测试输出。太长时全局用 `--print-max-*` / `-printMax*`,单条测试用 `Assert.OverrideMax*`;默认上限实测约 5 个元素 / 50 字符。
- `--stop-on-fail on` / `-stopOnFail` 用于本地快速收敛(`Cancelling due to test failure...`),别放 CI。调试:IDE 直接调试(调试器下超时不参战,见第 8 章),命令行用 `-waitForDebugger` 挂住进程再附加;`-wait` / `-pause` 需要交互控制台。
- 大测试拆开来调:复制一份只做 Arrange(验前提)、复制一份只留被测方法(最小输入)、Theory 用条件断点、异步测试记录输入↔线程↔任务状态;本地绿 CI 红先查前提差异(11.6)。
