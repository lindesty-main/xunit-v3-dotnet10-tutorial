# 第 10 章 · 配置、报告与覆盖率

> 你将学会:
> - 用 `xunit.runner.json` 与 `testconfig.json` 分别配置 xUnit.net 与 Microsoft Testing Platform(MTP),并分清哪个文件在哪些运行方式下生效
> - 复现"同一个选项写在命令行、配置文件、默认值三层时,谁生效"的真实过程
> - 用 `culture` 配置固定测试运行时的区域设置,并解释为什么依赖区域设置的断言必须固定 culture
> - 用 `methodDisplay`/`methodDisplayOptions` 把 `Class.Method(param)` 式的显示名变成人类可读的标题
> - 生成并阅读六种测试报告(xUnit XML/HTML、JUnit、NUnit、TRX、CTRF),按 CI 生态选型
> - 用 `Microsoft.Testing.Extensions.CodeCoverage` 收集代码覆盖率,解读 Cobertura 报告,并用 `.runsettings` 控制统计范围
> - 用 `--fail-skips`、`--ignore-exit-code` 等门禁选项和退出码表把测试运行接进 CI 的成败判定

## 10.1 两套配置文件:xunit.runner.json 与 testconfig.json

本章的工程是 [`code/Ch10.Reporting`](../code/Ch10.Reporting)。它自带 `xunit.runner.json` 与 `testconfig.json`,这两个文件不只是示例——本章每个"配置生效/不生效"的结论都是用它们跑出来的。xUnit.net v3 的两套配置文件各管一段:

| | `xunit.runner.json` | `testconfig.json` |
| --- | --- | --- |
| 属于 | xUnit.net 自身 | Microsoft Testing Platform(xUnit 键放在 `"xUnit"` 节里) |
| 生效场景 | 两种 runner 都读:原生命令行(`dotnet run`)和 MTP(`dotnet test`) | 仅 MTP 模式 |
| 读取位置 | 测试程序输出目录(所以要 `CopyToOutputDirectory`) | 工程根目录;构建时自动改名复制为 `<程序集名>.testconfig.json` |

### 10.1.1 xunit.runner.json:xUnit 自己的配置

把它放在测试工程根目录,并让构建把它复制到输出目录——这是本章工程 `.csproj` 的真实片段:

```xml
  <ItemGroup>
    <Content Include="xunit.runner.json" CopyToOutputDirectory="PreserveNewest" />
  </ItemGroup>
```

本章工程的 `xunit.runner.json` 原文:

```json
{
  "$schema": "https://xunit.net/schema/current/xunit.runner.schema.json",
  "methodDisplay": "classAndMethod",
  "methodDisplayOptions": "replaceUnderscoreWithSpace,useOperatorMonikers,useEscapeSequences",
  "assertEquivalentMaxDepth": 10,
  "shutdownForegroundThreadWaitSeconds": 5
}
```

`$schema` 让编辑器提供补全和校验;官方建议用 `current` 这个"永远跟随最新版"的 URL。常用键(完整清单见官方文档 Config with xunit.runner.json):

| 键 | 作用 | 默认值 |
| --- | --- | --- |
| `culture` | 所有测试运行时的区域设置(`"default"`/`"invariant"`/BCP 47 标签) | `"default"`(跟随操作系统) |
| `diagnosticMessages` | 发现/执行期间输出诊断信息。**MTP 下开了也没有任何控制台输出**(第 9 章实测);原生 runner 里这个键本身就足以打开诊断输出(等价于命令行加 `-diagnostics`) | `false` |
| `methodDisplay` / `methodDisplayOptions` | 显示名改写,见 10.3 | `"classAndMethod"` / `"none"` |
| `assertEquivalentMaxDepth` | `Assert.Equivalent` 比较对象的递归深度上限 | `50` |
| `shutdownForegroundThreadWaitSeconds` | 测试跑完后等待前台线程退出的秒数,超时则进程以失败退出(4.0 新增) | `10` |
| `parallelMode` / `maxParallelThreads` / `parallelAlgorithm` | 并行配置,优先级与语义见第 6 章 | `collections` / CPU 数 / `conservative` |
| `failSkips` / `failWarns` / `stopOnFail` | 门禁类开关,命令行等价物见 10.6 | `false` |
| `printMaxEnumerableLength` 等 | 断言失败消息里的打印截断(第 3 章提过默认值) | `5`/`3`/`5`/`50` |

两个坑:

- **文件名变体与优先级**:也可以用 `<程序集名>.xunit.runner.json`(如 `Ch10.Reporting.xunit.runner.json`)。带程序集名的文件优先于不带名字的,**两者之间不做键值合并**——只有一个是生效的。多个测试项目的产物混在同一个输出目录时才需要这种带名字的写法。
- **它是从输出目录读的**:所以 csproj 里的 `Content` 复制项不可省。MTP 下也可以用 `--xunit-config-filename <path>` 指向别处的配置文件。

`assertEquivalentMaxDepth` 不是摆设。本章的 [`EquivalentDepthTests.cs`](../code/Ch10.Reporting/EquivalentDepthTests.cs) 构造了一个第三层不一致的嵌套 record,断言"这里确实报了不匹配、且不匹配不是深度造成的":

```csharp
[Fact]
public void Equivalent_detects_mismatch_at_depth_three()
{
    var expected = new Chain("a", new Chain("b", new Chain("c", null)));
    var actual = new Chain("a", new Chain("b", new Chain("X", null)));

    var exception = Record.Exception(() => Assert.Equivalent(expected, actual));

    Assert.NotNull(exception);
    Assert.DoesNotContain("maximum depth", exception!.Message);
}
```

默认(深度 10)它是绿的。把上限压到 1 再跑:

```console
$ dotnet test --project Ch10.Reporting -- --filter-method "Ch10.Reporting.Tests.EquivalentDepthTests.Equivalent_detects_mismatch_at_depth_three" --assert-equivalent-max-depth 1
failed Ch10.Reporting.Tests.EquivalentDepthTests.Equivalent detects mismatch at depth three (14ms)
  Assert.DoesNotContain() Failure: Sub-string found
  String: ···"() Failure: Exceeded the maximum depth 1 with 'Nam"···
  Found:  "maximum depth"
```

深度不够时 `Assert.Equivalent` 不再比较深层节点,而是直接抛"超过最大深度"——真实的不匹配被深度限制盖住了。这个键的用意是给循环引用兜底,把它调到比较小会让深层结构的等价断言悄悄变味。

### 10.1.2 testconfig.json:只有 MTP 模式读

SDK 10 的 `dotnet test` 走 MTP(见第 1 章的 [`global.json`](../code/global.json)),MTP 有自己的配置文件 `testconfig.json`。放在**工程根目录**即可:构建系统会自动把它改名复制成输出目录里的 [`Ch10.Reporting.testconfig.json`](../code/Ch10.Reporting/bin/Debug/net10.0/Ch10.Reporting.testconfig.json)(实测构建后该文件确实出现),不需要手写 `Content` 项,也不建议手动复制一份以免双份漂移。

本章工程的 `testconfig.json` 原文:

```json
{
  "$schema": "https://xunit.net/schema/current/xunit.testconfig.schema.json",
  "xUnit": {
    "culture": "de-DE"
  }
}
```

xUnit.net 支持的键与 `xunit.runner.json` 同一套(`culture`、`methodDisplay`、`parallelMode`、`assertEquivalentMaxDepth`……),只是必须嵌在顶层 `"xUnit"` 对象里;`parallelizeTestCollections: false` 会被 4.0 自动映射为 `parallelMode: "none"`。除此之外,文件里还能配置 MTP 平台本身:

- `"platformOptions"`:如 `"resultDirectory"`(等价于 `--results-directory`);
- `"commandLineOptions"`:把命令行开关写进配置(MTP 2.3 起支持,键名去掉 `--`,例如 `"report-xunit-junit": true`);
- `"commandLineOptionDefaults"`:被动默认值(MTP 2.4 起);
- `"environmentVariables"`:启动测试进程前注入环境变量(MTP 2.3 起)。

这些平台节属于 MTP,细节见 Microsoft 的 MTP config options 文档。`--config-file <path>` 可以显式指定一个集中的 `testconfig.json`(配合 `Directory.Build.props` 里的 `TestingPlatformCommandLineArguments` 可以让整个仓库共用一份)。

### 10.1.3 谁生效:优先级链的实测

把同一个选项写在不同层,实测结果如下(选项是 `culture`,为了看得见效果,测试断言了当前区域设置本身):

1. **默认层**:什么都不配。区域设置跟随操作系统(这台机器是 `en-US`)。
2. **配置文件层**:`testconfig.json` 写了 `"culture": "de-DE"`。`dotnet test --project Ch10.Reporting` 全绿——断言 de-DE 的测试通过。
3. **命令行层**:`dotnet test --project Ch10.Reporting -- --culture en-US`,同一个测试立刻变红:

   ```console
   failed Ch10.Reporting.Tests.CultureContractTests.CurrentCulture IsPinnedByTestConfig (0ms)
     Assert.Equal() Failure: Strings differ
                ↓ (pos 0)
     Expected: "de-DE"
     Actual:   "en-US"
   ```

4. **两个文件冲突**:给 `xunit.runner.json` 也加 `"culture": "fr-FR"` 再跑 MTP——生效的仍是 `testconfig.json` 的 `de-DE`。MTP 模式下 `testconfig.json` 压过 `xunit.runner.json`。
5. **原生 runner 层**:`dotnet run --project Ch10.Reporting` 直接跑产物,`testconfig.json` 完全不被读取,区域设置回到操作系统的 `en-US`,断言 de-DE 的测试全部变红(10.2 展开)。

汇总成一条链(与官方文档一致,箭头右端优先):

```text
xUnit 特性/框架默认  <  xunit.runner.json  <  testconfig.json(xUnit 节)  <  环境变量(MTP)  <  命令行
```

并行选项的同类实验在第 6 章做过(命令行 > 特性/配置),结论一致:**配置文件适合放"这个项目恒定的行为",命令行放"这次运行的临时决定"**。

## 10.2 culture:把测试运行的区域设置钉死

本章的被测代码故意依赖区域设置([`Production/PriceTagPrinter.cs`](../code/Ch10.Reporting/Production/PriceTagPrinter.cs)):

```csharp
using System.Globalization;

namespace Ch10.Reporting.Production;

public class PriceTagPrinter
{
    // 依赖当前线程的 culture:同一个输入在不同 culture 下输出不同
    public string FormatPrice(double amount) =>
        amount.ToString("N2");

    public DateTime ParseValidUntil(string text) =>
        DateTime.Parse(text, CultureInfo.CurrentCulture);

    // 正确做法:显式传入固定 culture,结果与运行环境无关
    public string FormatPriceInvariant(double amount) =>
        amount.ToString("N2", CultureInfo.InvariantCulture);

    // 没有任何测试调用它:覆盖率报告里它的 line-rate 会是 0(见 10.5)
    public string FormatPricePlain(double amount) =>
        amount.ToString("N");
}
```

对应的测试([`CultureContractTests.cs`](../code/Ch10.Reporting/CultureContractTests.cs),节选)断言的是"工程被配置成 de-DE"这个前提本身:

```csharp
    [Fact]
    public void FormatPrice_UsesGermanNumberFormat()
    {
        var printer = new PriceTagPrinter();
        Assert.Equal("1.234,50", printer.FormatPrice(1234.5));
    }

    [Fact]
    public void ParseValidUntil_InterpretsDayFirst()
    {
        var printer = new PriceTagPrinter();
        Assert.Equal(new DateTime(2026, 2, 1), printer.ParseValidUntil("01.02.2026"));
    }
```

同一段代码在不同 culture 下的真实差异(都是本章实测输出,注意 fr-FR 的千位分隔符是不可见的窄空格):

| 调用 | de-DE | en-US | fr-FR | invariant |
| --- | --- | --- | --- | --- |
| `FormatPrice(1234.5)` | `1.234,50` | `1,234.50` | `1 234,50` | `1,234.50` |
| `ParseValidUntil("01.02.2026")` | 2026-02-01 | 2026-01-02 | 2026-02-01 | 01/02/2026 → 2026-01-02 |

用 `--culture en-US` 跑同一组测试,失败消息把差异钉死:

```console
failed Ch10.Reporting.Tests.CultureContractTests.ParseValidUntil InterpretsDayFirst (9ms)
  Assert.Equal() Failure: Values differ
  Expected: 2026-02-01T00:00:00.0000000
  Actual:   2026-01-02T00:00:00.0000000
failed Ch10.Reporting.Tests.DisplayNamesDemoTests.FormatPrice = german output(amount: 1234.5, expected: "1.234,50") (7ms)
  Assert.Equal() Failure: Strings differ
              ↓ (pos 1)
  Expected: "1.234,50"
  Actual:   "1,234.50"
```

而 `FormatPriceInvariant_IsStableAcrossCultures` 这条测试在 de-DE(MTP)和 en-US(原生 runner)下都是绿的——显式传 culture 的代码不受配置影响。

为什么必须固定 culture:开发机、CI 镜像、同事的笔记本的区域设置各不相同;货币符号、千位/小数分隔符、日期解析、大小写规则(土耳其语的 `i`)全都跟着变。不固定 culture 的测试等于把成败交给机器环境。固定手段按覆盖面排序:

1. `xunit.runner.json` 里 `"culture": "de-DE"`——两种 runner 都生效,覆盖面最好;
2. `testconfig.json` 里 `"xUnit": { "culture": "de-DE" }`——只在 MTP 生效(本章用的就是它,所以原生 runner 直接跑会红,见 10.1.3 第 5 条);
3. 命令行 `--culture de-DE`(MTP)/ `-culture de-DE`(原生),取值 `default`、`invariant` 或任意合法 BCP 47 标签;
4. 最稳妥的是根本不依赖线程 culture:像 `FormatPriceInvariant` 那样把 `CultureInfo` 显式传给生产代码。配置只是给"已经依赖线程 culture 的代码"兜底。

## 10.3 显示名:methodDisplay 与 methodDisplayOptions

xUnit 默认用"完全限定类名 + 方法名 + 参数"作显示名,出现在控制台、失败消息和所有报告文件里。本章的 [`DisplayNamesDemoTests.cs`](../code/Ch10.Reporting/DisplayNamesDemoTests.cs) 刻意用下划线、运算符别名和转义序列命名:

```csharp
    [Theory]
    [InlineData(1234.5, "1.234,50")]
    [InlineData(0.0, "0,00")]
    public void FormatPrice_eq_german_output(double amount, string expected)
    {
        var printer = new PriceTagPrinter();
        Assert.Equal(expected, printer.FormatPrice(amount));
    }

    [Fact]
    public void FormatPrice_U2212_negative_amount_keeps_minus()
```

`methodDisplay` 决定骨架:`"classAndMethod"`(默认,带命名空间限定)或 `"method"`(只留方法名)。`methodDisplayOptions` 是叠加的改写开关,可写 `all`、`none` 或逗号分隔的组合:

| 开关 | 效果 |
| --- | --- |
| `replaceUnderscoreWithSpace` | 下划线换成空格 |
| `useOperatorMonikers` | `eq`→`=`、`ne`→`!=`、`lt`→`<`、`le`→`<=`、`gt`→`>`、`ge`→`>=` |
| `useEscapeSequences` | `X2C`→`,`、`Unnnn`→对应 Unicode 字符(`U2212`→`−`) |
| `replacePeriodWithComma` | 句点换成逗号加空格(配合 `classAndMethod` 才有意义) |
| `removeAsyncSuffix` | 去掉方法名末尾的 `Async`(4.0 新增) |

三种配置下的真实报告内容(同一个测试在 xUnit XML 报告里的 `name` 属性):

```text
配置 methodDisplayOptions=none(命令行覆盖配置文件):
  name="Ch10.Reporting.Tests.DisplayNamesDemoTests.FormatPrice_eq_german_output(amount: 1234,5, expected: \"1.234,50\")"

本章 xunit.runner.json 生效时(默认骨架 + 三项改写):
  name="Ch10.Reporting.Tests.DisplayNamesDemoTests.FormatPrice = german output(amount: 1234,5, expected: \"1.234,50\")"
  name="Ch10.Reporting.Tests.DisplayNamesDemoTests.FormatPrice − negative amount keeps minus"
  name="Ch10.Reporting.Tests.DisplayNamesDemoTests.FormatPrice >= zero never uses −"

命令行 --method-display method(去掉类名骨架):
  name="FormatPrice = german output(amount: 1234,5, expected: \"1.234,50\")"
```

(参数 `1234.5` 在报告里印成 `1234,5`,是因为参数值也按测试 culture 格式化——又一个 culture 无孔不入的例子。)

命令行覆盖写法:MTP 用 `--method-display-options none` 或逐个值空格分隔(`--method-display-options replaceUnderscoreWithSpace useOperatorMonikers`);原生 runner 用 `-methodDisplayOptions replaceUnderscoreWithSpace,useOperatorMonikers`(逗号连接)。实测一个坑:`--method-display-options` 是多值选项,SDK 10 会把跟在后面的裸值当成多余的工程目录,写在命令行中间会撞上 `Specifying a directory for 'dotnet test' should be via '--project' or '--solution'.`——把它放到命令行的**最后**才稳。

两个注意事项:

- 改写只影响**显示名**,不影响过滤器:开了改写的工程里,`--filter-method "Ch10.Reporting.Tests.CultureContractTests.CurrentCulture_IsPinnedByTestConfig"`(真实方法名的完全限定形式)照样命中;按改写后的名字过滤要用 `--filter-display-name`(第 7 章)。
- 真实名在报告里另有去处:xUnit XML 的 `type`/`method` 属性、TRX 的 `<TestMethod name=...>` 始终印真实类名与方法名。给 Theory 数据行自定义显示名(第 4 章的 `TestDisplayName`)与这里的改写叠加时,最终显示名以数据行的为准。

## 10.4 六种报告文件

xUnit v3 内置六种报告,原生 runner 和 MTP 都能生成,只是开关名不同(4.0 把 MTP 的旧名统一加了 `xunit-` 前缀;旧名会被判成无效的命令行参数——测试模块以 exit 5 启动失败并打印 `Handshake failures`,10.6 展开):

| 报告 | 原生 runner | MTP | 用途与选型 |
| --- | --- | --- | --- |
| xUnit.net v2+ 兼容 XML | `-result-xml <file>` | `--report-xunit-xml` | xUnit 自家格式,字段最全:**唯一把警告文本和附件内容本身写进报告的格式**(其余格式只给计数、落盘路径,或干脆不提);留给 xUnit 生态的工具消费 |
| xUnit HTML | `-result-html <file>` | `--report-xunit-html` | 单文件自包含 HTML,人直接打开看,适合发附件、贴工单 |
| JUnit XML | `-result-junit <file>` | `--report-xunit-junit` | 事实标准;Jenkins、GitHub Actions 的测试报告器、IDE 插件大多只认它 |
| NUnit XML | `-result-nunit <file>` | `--report-xunit-nunit` | NUnit v3 的 XML 方言,给已接好 NUnit 格式的报表管线用 |
| TRX | `-result-trx <file>` | `--report-xunit-trx` | Visual Studio / Azure DevOps 的原生消费格式 |
| CTRF | `-result-ctrf <file>` | `--report-xunit-ctrf` | JSON 格式的通用测试报告(CTRF),给仪表盘/聚合平台 |

(还有 `-result-xmlV1`、`-result-markdown` / `--report-xunit-markdown` 两个次要格式。)

**输出位置与命名。** 原生 runner 把文件写在你给的路径上。MTP 不带 `-filename` 时自动生成名字:`<用户名>_<计算机名>_<日期>_<时间>`,扩展名按格式固定(`.junit.xml`、`.nunit.xml`、`.xunit.xml`、`.trx`、`.ctrf`、`.html`),目录默认是输出目录下的 `TestResults`,用 `--results-directory` 改目录。本章一次真实运行的产物清单:

```console
$ dotnet test --project Ch10.Reporting -- --report-xunit-xml --report-xunit-html --report-xunit-junit --report-xunit-nunit --report-xunit-trx --report-xunit-ctrf
  In process file artifacts produced:
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.ctrf
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.html
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.junit.xml
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.nunit.xml
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.trx
    - .../Ch10.Reporting/bin/Debug/net10.0/TestResults/lindesty_homearch_2026-10-23_04_28_21.062434.xunit.xml
```

`--report-xunit-junit-filename my.xml` 这类变体只接受**纯文件名**(不能带路径),用于把名字固定在自动化流水线上。多测试项目跑一次 `dotnet test` 时,让自动命名工作:每个项目都会得到自己的文件;如果所有项目都指定同一个固定文件名、又共用同一个 results 目录,后写的会覆盖先写的。覆盖率同理,官方明确警告不要对多项目用 `--coverage-output`(10.5)。

**各格式的关键结构**(都截自上面那次真实运行)。

JUnit(`.junit.xml`)——`testsuites` 汇总,每个程序集一个 `testsuite`,每条测试一个 `testcase`;跳过用 `<skipped>` 子元素:

```xml
<testsuites name="Test results" tests="11" failures="0" errors="0" disabled="0" ...>
  <testsuite name=".../Ch10.Reporting.dll" tests="11" failures="0" skipped="1" ...>
    <testcase name="Ch10.Reporting.Tests.CultureContractTests.ParseValidUntil InterpretsDayFirst"
              time="0.008000" classname="Ch10.Reporting.Tests.CultureContractTests" />
    <testcase name="Ch10.Reporting.Tests.ReportGateTests.Nightly regression placeholder" ...>
      <skipped>nightly environment not yet stable</skipped>
    </testcase>
```

TRX(`.trx`)——`TestDefinitions` 里每个测试一个 `UnitTest`(`TestMethod` 带真实类名/方法名),`Results` 里是结果;跳过的判 `outcome="NotExecuted"`,跳过原因在 `<StdOut>`:

```xml
<TestRun id="..." name="lindesty@unknown 2026-10-23T04:17:55..." runUser="lindesty" ...>
  <UnitTest name="Ch10.Reporting.Tests.CultureContractTests.ParseValidUntil InterpretsDayFirst" ...>
    <TestMethod codeBase=".../Ch10.Reporting.dll" className="Ch10.Reporting.Tests.CultureContractTests"
                name="ParseValidUntil_InterpretsDayFirst" ... />
  </UnitTest>
  <Results>
    <UnitTestResult testName="Ch10.Reporting.Tests.ReportGateTests.Nightly regression placeholder"
                    outcome="NotExecuted" ...>
      <Output><StdOut>nightly environment not yet stable</StdOut></Output>
    </UnitTestResult>
```

CTRF(`.ctrf`,JSON)——`results.summary` 是聚合计数,`results.tests[]` 逐条给状态、耗时、`suite`(四个元素的数组:程序集 ID、测试集合 ID、类名、方法名);**测试的 trait 会进 `labels`**(`ReportGateTests.PriceTag_is_printable` 带了 `[Trait("report", "demo")]`):

```json
{"reportFormat": "CTRF", "specVersion": "0.0.0", "reportId": "4124f395-...",
 "results": {
  "tool": {"name": "xUnit.net v3", "version": "4.0.2+0c7aa4991f"},
  "environment": {"osPlatform": "linux", "osRelease": "Arch Linux", "extra": {"user": "lindesty"}},
  "summary": {"tests": 11, "passed": 10, "failed": 0, "pending": 0, "skipped": 1, "other": 0, "suites": 1, "duration": 80},
  "tests": [
    {"name": "Ch10.Reporting.Tests.ReportGateTests.PriceTag is printable", "status": "passed",
     "filePath": ".../ReportGateTests.cs", "line": 10, "labels": {"report": "demo"}, ...},
    {"name": "Ch10.Reporting.Tests.ReportGateTests.Nightly regression placeholder", "status": "skipped",
     "message": "nightly environment not yet stable", ...}
  ]}}
```

NUnit(`.nunit.xml`)——NUnit v3 方言:`test-run` 根节点带全套计数(`passed/skipped/warnings/asserts`),下面按 `test-suite` 逐层嵌套。警告在这里只剩一个计数属性(文本没了);附件有 `<attachments><attachment filePath="..." description="..." />`,但只指向落盘文件,不含内容。

xUnit XML(`.xunit.xml`)——`assemblies/assembly/test` 层级,`test` 元素带 `result`、源码文件与行号、`type`/`method` 真实名;环境行里能看到本次运行的并行配置头部(`[collection-per-class, parallel (collections, 32 threads)]`)。警告与附件只有在这里是完整的:`<warnings><warning>原文</warning></warnings>` 是它独有的元素(NUnit 只给 `warnings="N"` 计数,JUnit 把警告文本混进测试的 `<system-out>`,TRX/CTRF/HTML 两者都不带),`<attachments><attachment name=... [media-type=...]>` 里直接内联附件内容(二进制是 base64)。这两个元素的由来见第 9 章。

HTML(`.html`)——自包含单文件(内嵌 CSS 与全部结果),浏览器直接打开,标题是 `xUnit.net Test Results`。

原生 runner 生成同样的报告用 `-result-*`,例如:

```console
$ dotnet run --project Ch10.Reporting -- -result-xml /tmp/native-reports/r.xunit.xml \
    -result-html /tmp/native-reports/r.html -result-junit /tmp/native-reports/r.junit.xml \
    -result-nunit /tmp/native-reports/r.nunit.xml -result-trx /tmp/native-reports/r.trx \
    -result-ctrf /tmp/native-reports/r.ctrf
$ ls /tmp/native-reports/
r.ctrf  r.html  r.junit.xml  r.nunit.xml  r.trx  r.xunit.xml
```

注意旧名 `-junit`、`-xml` 等在 4.0 里已弃用(会打警告,提示改用 `-result-*`)。

## 10.5 代码覆盖率

MTP 模式下微软官方提供的覆盖率扩展是 `Microsoft.Testing.Extensions.CodeCoverage`(闭源、免费使用;它同时是 Visual Studio 与 Azure DevOps 覆盖率的数据引擎)。安装:

```console
$ dotnet add Ch10.Reporting package Microsoft.Testing.Extensions.CodeCoverage
```

本章 `.csproj` 里即:

```xml
    <PackageReference Include="Microsoft.Testing.Extensions.CodeCoverage" Version="18.12.0" />
```

装好后命令行多出四个开关(边界:它们只在 MTP 模式存在;原生 runner 不认识 `--coverage`,`dotnet run -- --coverage` 会报 unknown option。Coverlet 走的是另一条路线,需要 `coverlet.MTP` 包,与这里互不影响):

| 开关 | 作用 |
| --- | --- |
| `--coverage` | 开启收集(必须的只有这一个) |
| `--coverage-output` | 指定输出文件名;默认 `TestResults/<guid>.coverage` |
| `--coverage-output-format` | `coverage`(二进制,默认)、`xml`、`cobertura` |
| `--coverage-settings` | 指定覆盖率设置文件(`.runsettings`/覆盖率 XML/JSON) |

第一次跑:

```console
$ dotnet test --project Ch10.Reporting -- --coverage --coverage-output-format cobertura
  In process file artifacts produced:
    - .../TestResults/5e321a86-84bb-468a-9b1b-64a02d5df153.cobertura.xml
```

打开文件却傻眼了——一个覆盖率数据都没有:

```xml
<coverage line-rate="1" branch-rate="1" complexity="1" version="1.9" timestamp="...">
  <packages />
</coverage>
```

原因在扩展的默认值:`IncludeTestAssembly` 在 MTP 扩展里默认 `false`(VSTest 时代默认 `true`),**测试程序集整体不参与统计**。本章的被测代码就在测试程序集里([`Production/`](../code/Ch10.Reporting/Production/) 目录),于是全部数据被排除。若被测代码在独立的类库工程里,默认值反而正确;放在测试程序集内的教程式工程必须自己打开它。

`--coverage-settings` 指向一个覆盖率设置文件。本章工程的 `coverage.runsettings`(开统计 + 只保留指定命名空间):

```xml
<?xml version="1.0" encoding="utf-8"?>
<Configuration>
  <!-- 本章的被测代码在测试程序集里(Production/ 目录),
       而 IncludeTestAssembly 默认是 false,不开启就没有任何数据 -->
  <IncludeTestAssembly>True</IncludeTestAssembly>
  <CodeCoverage>
    <!-- 只把指定命名空间的代码计入覆盖率:Function 匹配完全限定函数名,
         Include 非空时其余函数一律排除 -->
    <Functions>
      <Include>
        <Function>^Ch10\.Reporting\.Production\..*</Function>
      </Include>
    </Functions>
  </CodeCoverage>
</Configuration>
```

```console
$ dotnet test --project Ch10.Reporting -- --coverage --coverage-output-format cobertura \
    --coverage-settings "$PWD/Ch10.Reporting/coverage.runsettings"
  In process file artifacts produced:
    - .../TestResults/74f0176f-bc5b-45de-8fe7-d9998e7d390b.cobertura.xml
```

注意 `--coverage-settings` 实测只认**绝对路径**:相对路径(无论相对当前目录还是相对工程/输出目录)都会失败,而且症状不固定——有时是测试模块 exit 5 的 `Handshake failures`,有时是 SDK 抛出一句莫名其妙的 `KeyNotFoundException`(摘要只剩 `Zero tests ran`),两种都意味着没有任何测试跑起来。稳妥写法:传绝对路径,或 CI 里用 `${{ github.workspace }}` 拼出来。

现在的 Cobertura 报告(节选,真实输出):

```xml
<coverage line-rate="0.75" branch-rate="1" complexity="1" version="1.9" ... lines-covered="3" lines-valid="4">
  <packages>
    <package line-rate="0.75" ... name="Ch10.Reporting">
      <classes>
        <class line-rate="0.75" ... name="Ch10.Reporting.Production.PriceTagPrinter"
               filename=".../Production/PriceTagPrinter.cs">
          <methods>
            <method line-rate="1" ... name="FormatPrice" signature="(double)">
              <lines><line number="9" hits="1" branch="False" /></lines>
            </method>
            <method line-rate="0" ... name="FormatPricePlain" signature="(double)">
              <lines><line number="20" hits="0" branch="False" /></lines>
            </method>
          </methods>
          <lines>
            <line number="9" hits="1" branch="False" />
            ...
            <line number="20" hits="0" branch="False" />
          </lines>
        </class>
```

怎么读:`line-rate` 是被执行行占比(0.75 = 3/4,`lines-covered`/`lines-valid` 直接给出分子分母);`branch-rate` 是分支覆盖;`complexity` 是圈复杂度;`hits="0"` 就是没有任何测试执行到的行——正是 [`PriceTagPrinter.cs`](../code/Ch10.Reporting/Production/PriceTagPrinter.cs) 第 20 行那个没人调用的 `FormatPricePlain`。测试类本身被 `Functions/Include` 过滤掉了,报告里只剩被测代码——这正是"排除 Production 之外的代码"的做法;反过来用 `Functions/Exclude` 或 `ModulePaths`、`Attributes`、`Sources` 等清单也能配(它们默认与内置排除合并,想完全接管要在清单元素上写 `mergeDefaults="False"`)。

XML 不适合人看。要 HTML 就用 ReportGenerator:

```console
$ dotnet tool install --global dotnet-reportgenerator-globaltool
$ reportgenerator -reports:"**/*.cobertura.xml" -targetdir:CoverageReport
```

多测试项目时不要用 `--coverage-output` 固定名字——每个项目都会写同一个文件互相覆盖;让默认 GUID 命名生成,再用通配符收集。

## 10.6 退出码与门禁

**把跳过变成失败。** 本章有一条 `Skip` 的测试(见 [`ReportGateTests.cs`](../code/Ch10.Reporting/ReportGateTests.cs))。默认它算跳过、不拦人;`--fail-skips on`(原生 `-failSkips`)把它升级成失败:

```console
$ dotnet test --project Ch10.Reporting -- --fail-skips on
failed Ch10.Reporting.Tests.ReportGateTests.Nightly regression placeholder (0ms)
  Xunit.MicrosoftTestingPlatform.XunitException: FAIL_SKIP : nightly environment not yet stable
...
Exit code: 2
Test run summary: Failed!
  total: 11
  failed: 1
  succeeded: 10
  skipped: 0
```

**把警告变成失败。** `--fail-warns on` 让带 `AddWarning` 的通过测试判为 `FAIL_WARN`;警告在 MTP 控制台默认不可见、只进报告的机制在第 9 章实测过。两个开关也都能以 `failSkips`/`failWarns` 键写进任一配置文件;按第 8 章的约定,教程工程里用 `Skip` 标注的演示用例,去掉 `Skip` 即可复现对应输出。

**零命中与豁免。** 过滤器一条都没命中时,MTP 以退出码 8 结束(第 7 章实测):

```console
$ dotnet test --project Ch10.Reporting -- --filter-class "NoSuch*"
Test run completed with non-success exit code: 8 (see: https://aka.ms/testingplatform/exitcodes)
```

`--ignore-exit-code` 把指定退出码改写成 0(分号分隔多个,如 `--ignore-exit-code 8;9`;环境变量 `TESTINGPLATFORM_EXITCODE_IGNORE` 等价)。上面这条加 `--ignore-exit-code 8` 后正常返回 0——"这个过滤器在部分流水线里允许落空"就能这样表达。

**退出码表**(MTP;官方见 troubleshooting 文档的 Exit codes 一节,`https://aka.ms/testingplatform/exitcodes`):

| 码 | 含义 | 码 | 含义 |
| --- | --- | --- | --- |
| 0 | 成功 | 7 | 会话崩溃类失败 |
| 1 | 未知错误(兜底) | 8 | 没发现任何测试(或全被按零测试策略跳过) |
| 2 | 至少一条测试失败 | 9 | 少于 `--minimum-expected-tests` 要求的数量 |
| 3 | 会话被中止(如 Ctrl+C) | 10 | 基础设施故障(夹具创建失败等) |
| 4 | 扩展配置无效,会话无法运行 | 13 | 达到 `--maximum-failed-tests` 上限 |
| 5 | 命令行参数无效(10.4 的旧报告选项名就栽在这) | 14 | 覆盖率阈值评估失败(`--ignore-exit-code 14` 可豁免) |

这张表描述的是**测试模块**的退出码。参数写错时,`dotnet test` 的日志里会出现 `Handshake failures:` 和该模块的 `Exit code: 5`,而 SDK 包装层自己以 1 结束——CI 里 `echo $?` 看到的是 1,真正的 5 要往上翻日志才找得到(10.4 的旧报告选项名、10.5 的相对路径 `--coverage-settings` 都是这个形状)。

原生 runner 没有这套细分退出码:实测成功时返回 0,过滤器一条都没命中也返回 0(摘要里 `Total: 0`,不报错);有失败时返回 1,失败 7 条和失败 2 条都是 1;命令行参数写错(未知选项、缺参数、取值非法)一律返回 3——和 MTP 的 3(会话被中止)、5(参数无效)含义完全不同。MTP 的 8/9/14 等语义只存在于 MTP 侧,两套别混用。

## 10.7 哪些进版本库,哪些留在 CI 命令行

本章工程里三个文件都应当进版本库,因为它们定义的是"这个项目恒定的行为":

| 进版本库 | 内容 | 理由 |
| --- | --- | --- |
| `xunit.runner.json` | culture、显示名规则、`assertEquivalentMaxDepth` 等 xUnit 行为 | 让本地、任何 runner、CI 得到同一套行为;IDE 里点"运行"也一致 |
| `testconfig.json` | MTP 侧的 xUnit 键、平台选项 | 同上,且保证本地 `dotnet test` 与 CI 流水线同配置 |
| `coverage.runsettings` | 统计范围(包含/排除) | 覆盖率口径必须全团队一致,否则数字没有可比性 |

留在 CI 命令行的,是"与这次运行有关、与项目无关"的开关:

- 报告:开哪几种(`--report-xunit-junit --report-xunit-trx`)、放哪(`--results-directory`),由流水线的产物收集方式决定;
- 覆盖率:开不开(`--coverage`),慢不慢由流水线决定;
- 门禁:`--fail-skips on`、`--fail-warns on`、`--ignore-exit-code`、`--minimum-expected-tests`——不同分支/流水线的严格程度可以不同;
- 过滤:`--filter-trait` 之类(第 7 章)。

一条经验:同一个键尽量只写在一层。本章把 `culture` 放在 `testconfig.json` 而不是两处都放,就是为了"改一处、处处生效";两处都写时 MTP 下 `testconfig.json` 赢(10.1.3 实测),但读代码的人未必知道这条规则。

## 动手练习

1. **换一种 culture,预测再验证。** 把 `testconfig.json` 的 culture 改成 `fr-FR`,先预测哪些测试会红、失败消息长什么样,再跑 `dotnet test --project Ch10.Reporting` 验证。验收:恰好三条红——`CurrentCulture_IsPinnedByTestConfig`(Actual: `"fr-FR"`)、`FormatPrice_UsesGermanNumberFormat`(Actual 是 `1`、窄空格、`234,50`)、以及 `DisplayNamesDemoTests` 里数据行 `amount: 1234.5` 那条(同 Theory 的 `0.0` 行仍绿:`0,00` 两种 culture 下相同);`ParseValidUntil` 仍绿(法语同样是日前月后)。改回 `de-DE` 后恢复全绿。
2. **三种报告进自定义目录。** 跑 `dotnet test --project Ch10.Reporting -- --report-xunit-junit --report-xunit-trx --report-xunit-ctrf --results-directory /tmp/ch10-reports`。验收:`/tmp/ch10-reports` 里出现三个自动命名的文件;在 JUnit 里找到 `Nightly regression placeholder` 的 `<testcase>` 与 `<skipped>`,在 TRX 里找到它的 `outcome="NotExecuted"`,在 CTRF 里找到 `PriceTag is printable` 的 `"labels": {"report": "demo"}`。
3. **补上覆盖率缺口。** 当前 cobertura 里 `FormatPricePlain` 是 `hits="0"`(整体 `line-rate 0.75`)。写一条调用它的测试,重跑 10.5 的带 `--coverage-settings` 命令。验收:新的 `.cobertura.xml` 顶层属性变成 `lines-covered="4" lines-valid="4"`、`line-rate="1"`,`FormatPricePlain` 的 `line-rate="1"`。

## 本章小结

- `xunit.runner.json` 归 xUnit,两种 runner 都读(从输出目录,所以 csproj 要 `CopyToOutputDirectory`);`testconfig.json` 归 MTP,只在 MTP 模式生效,放工程根目录、构建自动改名成 `<程序集名>.testconfig.json`。
- 优先级:`特性/默认 < xunit.runner.json < testconfig.json < 环境变量 < 命令行`;两个文件键冲突时 `testconfig.json` 赢(实测);原生 runner 完全不读 `testconfig.json`,用它跑 MTP 专属配置钉住的行为会得到另一套结果。
- 依赖区域设置的代码必须固定 culture(配置文件或命令行),或者在生产代码里显式传 `CultureInfo`。
- `methodDisplayOptions` 把 `FormatPrice_eq_german_output` 变成 `FormatPrice = german output`;它只改显示名,过滤器仍按真实方法名匹配。
- 六种报告各服务一个生态:JUnit 给 CI 通用、TRX 给 VS/Azure DevOps、CTRF 给 JSON 仪表盘、xUnit XML 字段最全(警告原文与附件内容只有它内联,NUnit 只给计数和落盘路径)、HTML 给人看、NUnit 兼容既有管线。多项目时信任自动命名,别固定文件名。
- 覆盖率:`--coverage` 起步,`cobertura` 是通用交换格式;`IncludeTestAssembly` 默认 `false`,被测代码在测试程序集内时必须用 `.runsettings` 打开;`line-rate`/`hits` 直接指出没被调用的方法。`--coverage-settings` 用绝对路径。
- 门禁与退出码:`--fail-skips on`/`--fail-warns on` 把跳过和警告升级成失败(exit 2);零命中 exit 8,`--ignore-exit-code` 豁免;完整退出码表在 `https://aka.ms/testingplatform/exitcodes`。
- 进版本库的是项目行为(两个配置文件、覆盖率口径),留在命令行的是每次运行的决定(报告、覆盖率开关、门禁、过滤)。
