# 第 2 章 · 测试结构与命名

> 你将学会:
>
> - 把测试主体组织成 AAA 三段结构,并分清注释什么时候是帮助、什么时候是噪音
> - 在三种常见命名风格(三段式 / 可读句子 / Given-When-Then)之间做选择,让测试名自己携带行为契约
> - 用 `DisplayName` 属性让 runner 打印人类可读的描述
> - 判断一个测试该写成 `Fact` 还是 `Theory`,避开复制粘贴与过度参数化两个极端
> - 正确组织测试工程与测试类:一个被测类型对应一个测试类,不滥用继承
> - 用命名与数据表达行为契约;一个测试只验证一个行为,`Assert.Multiple` 的适用尺度

本章回答一个问题:测试怎样写,才能让半年后打开它的人不用先读实现就能看懂。本章的工程是 [`code/Ch02.TestStructure`](../code/Ch02.TestStructure),被测对象是两个带规则分支的策略校验器(用户名与密码)。所有输出片段都来自本机 .NET SDK 10.0.113 + xUnit.net v3 4.0.2 的真实运行;片段里过长的绝对路径与栈帧用 `...` 省略,其余逐字保留。

评估测试时可以看它是否能快速给出反馈、独立稳定地运行、聚焦于明确行为,并且让团队成员无需先读生产实现就能理解。代码应当直接易读,这些是整体质量目标,不是要求每个测试都套用同一模板;本章的 AAA、命名和行为范围规则能帮助落实这些目标。

## 2.1 本章的被测对象:带规则分支的策略校验器

被测代码在 [`Production/`](../code/Ch02.TestStructure/Production/) 目录,命名空间 `Ch02.TestStructure.Production`。先是违规记录:

```csharp
namespace Ch02.TestStructure.Production;

/// <summary>策略校验器可能违反的规则种类。</summary>
public enum PolicyRule
{
    UsernameRequired,
    UsernameTooShort,
    UsernameTooLong,
    UsernameMustStartWithLetter,
    UsernameHasInvalidCharacter,
    PasswordTooShort,
    PasswordMissingLowercase,
    PasswordMissingUppercase,
    PasswordMissingDigit,
    PasswordContainsUsername,
}

/// <summary>一条违规:违反了哪条规则,以及给人看的说明文字。</summary>
public sealed record PolicyViolation(PolicyRule Rule, string Message);
```

用户名策略,[`Production/UsernamePolicy.cs`](../code/Ch02.TestStructure/Production/UsernamePolicy.cs):

```csharp
namespace Ch02.TestStructure.Production;

/// <summary>
/// 本章的被测对象之一:用户名策略。规则:
/// 长度 3-20;必须以 ASCII 字母开头;只允许 ASCII 字母、数字和下划线。
/// Validate 返回所有被违反的规则(空列表表示合法),而不是遇到第一条就停下。
/// </summary>
public class UsernamePolicy
{
    public const int MinLength = 3;
    public const int MaxLength = 20;

    public IReadOnlyList<PolicyViolation> Validate(string? username)
    {
        var violations = new List<PolicyViolation>();

        if (string.IsNullOrWhiteSpace(username))
        {
            violations.Add(new PolicyViolation(PolicyRule.UsernameRequired, "用户名不能为空。"));
            return violations;
        }

        if (username.Length < MinLength)
            violations.Add(new PolicyViolation(PolicyRule.UsernameTooShort, $"用户名至少需要 {MinLength} 个字符。"));
        if (username.Length > MaxLength)
            violations.Add(new PolicyViolation(PolicyRule.UsernameTooLong, $"用户名最多允许 {MaxLength} 个字符。"));
        if (!IsAsciiLetter(username[0]))
            violations.Add(new PolicyViolation(PolicyRule.UsernameMustStartWithLetter, "用户名必须以字母开头。"));

        var invalidChars = username.Where(c => !IsAllowedCharacter(c)).Distinct().ToArray();
        if (invalidChars.Length > 0)
            violations.Add(new PolicyViolation(
                PolicyRule.UsernameHasInvalidCharacter,
                $"用户名只能包含字母、数字和下划线,出现非法字符:{string.Join(" ", invalidChars)}。"));

        return violations;
    }

    private static bool IsAsciiLetter(char c) => c is >= 'a' and <= 'z' or >= 'A' and <= 'Z';

    private static bool IsAllowedCharacter(char c) => IsAsciiLetter(c) || char.IsAsciiDigit(c) || c == '_';
}
```

密码策略,[`Production/PasswordPolicy.cs`](../code/Ch02.TestStructure/Production/PasswordPolicy.cs):

```csharp
namespace Ch02.TestStructure.Production;

/// <summary>
/// 本章的被测对象之二:密码策略。规则:
/// 长度至少 8;必须同时包含小写字母、大写字母和数字;不得包含用户名(忽略大小写)。
/// Validate 返回所有被违反的规则(空列表表示合法),而不是遇到第一条就停下。
/// </summary>
public class PasswordPolicy
{
    public const int MinLength = 8;

    public IReadOnlyList<PolicyViolation> Validate(string password, string username)
    {
        var violations = new List<PolicyViolation>();

        if (password.Length < MinLength)
            violations.Add(new PolicyViolation(PolicyRule.PasswordTooShort, $"密码至少需要 {MinLength} 个字符。"));
        if (!password.Any(char.IsLower))
            violations.Add(new PolicyViolation(PolicyRule.PasswordMissingLowercase, "密码必须包含小写字母。"));
        if (!password.Any(char.IsUpper))
            violations.Add(new PolicyViolation(PolicyRule.PasswordMissingUppercase, "密码必须包含大写字母。"));
        if (!password.Any(char.IsDigit))
            violations.Add(new PolicyViolation(PolicyRule.PasswordMissingDigit, "密码必须包含数字。"));
        if (username.Length > 0 && password.Contains(username, StringComparison.OrdinalIgnoreCase))
            violations.Add(new PolicyViolation(PolicyRule.PasswordContainsUsername, "密码不能包含用户名。"));

        return violations;
    }
}
```

两个设计选择直接决定了后面的测试怎么写得清楚:

- `Validate` 返回**全部**被违反的规则,而不是返回 `bool`。布尔值只说"结果不对",十条规则里违反了哪条、说明文字写得对不对,全都丢了;规则列表让每个测试都能断言"违反了哪条规则"。
- 规则边界是 `public const`(`MinLength`/`MaxLength`)。测试用常量构造边界数据(比如 `MaxLength + 1`),改规则时边界测试自动跟着走,不用满工程找硬编码。

## 2.2 AAA:三段结构

测试主体通常可以按三段组织:**Arrange**(准备输入和环境)、**Act**(调用被测方法,通常一次)、**Assert**(验证结果)。三段之间用空行隔开,让读者能快速找到每一步。

先看反例。[`TestStructureAntiPatternTests.cs`](../code/Ch02.TestStructure/TestStructureAntiPatternTests.cs) 是本章专门存放反例的文件:这些测试**本身是通过的**,但写法故意不好,注释标明对应的小节。下面就是 2.2 的反例:

```csharp
[Fact]
public void TestValidate_Empty()
{
    var p = new UsernamePolicy(); var v = p.Validate(""); Assert.True(v.Count > 0);
}
```

三个毛病:名字没有信息(见 2.3);三段挤在一行,读的时候要在脑内自己分段;`Assert.True(v.Count > 0)` 把信息全丢了——失败时你只知道"数量不大于 0",不知道到底返回了什么。

重构后的版本在 [`UsernamePolicyTests.cs`](../code/Ch02.TestStructure/UsernamePolicyTests.cs):

```csharp
[Theory]
[InlineData(null)]
[InlineData("")]
[InlineData("   ")]
public void Validate_UsernameBlank_ReportsRequiredViolation(string? username)
{
    var violations = policy.Validate(username);

    var violation = Assert.Single(violations);
    Assert.Equal(PolicyRule.UsernameRequired, violation.Rule);
}
```

结构建议:

- 空行把三段分开;Act 只包含对被测方法的调用。如果 Act 段出现多次调用,多半是两个行为挤在了一个测试里。
- Arrange 的数据一眼能看懂就不写注释;当准备的意图不明显时才写注释,而且写的是"为什么"。合适的例子在 [`PasswordPolicyTests.cs`](../code/Ch02.TestStructure/PasswordPolicyTests.cs):

```csharp
// Arrange 里的讲究:用户名是全小写的 alice,密码里写成 Alice,
// 就是为了钉死"忽略大小写"这个行为。
var violations = policy.Validate("HiAlice2024", "alice");
```

- `// Arrange`、`// Act`、`// Assert` 这类注释不要写:空行本身就是分隔,注释只是噪音。团队刚开始推行 AAA、需要临时脚手架时可以短期用,落地后删掉。

AAA 是帮助组织测试的惯例,不是硬性语法规则。像只检查一个调用是否抛出异常的测试,可以没有明显的 Arrange 段;不必为了凑齐三段添加空变量或空注释。若团队使用 `// Arrange` 一类标记,注释风格保持一致即可。

## 2.3 命名:测试名是第一行文档

测试名比测试体被读到的次数多得多:失败报告、CI 通知、IDE 测试资源管理器里,露面的只有名字。好名字回答三个问题:**测什么、在什么条件下、期望什么行为**。名字写对了,一条失败邮件不需要点开代码就能复现场景。

### 三种常见风格

三段式:`被测方法_条件_期望行为`。本章的 [`UsernamePolicyTests.cs`](../code/Ch02.TestStructure/UsernamePolicyTests.cs) 整体用这种风格:

```csharp
public void Validate_UsernameShorterThanMinimum_ReportsTooShortViolation()
public void Validate_UsernameNotStartingWithLetter_ReportsMustStartWithLetterViolation(string username)
```

可读句子式:把行为写成一个英文句子,名字里不出现被测方法名。[`PasswordPolicyTests.cs`](../code/Ch02.TestStructure/PasswordPolicyTests.cs) 整体用这种风格:

```csharp
public void Password_without_digit_is_rejected()
public void Password_containing_the_username_is_rejected_regardless_of_letter_case()
```

第三种常见约定是 Given-When-Then,例如 `GivenInvalidInput_WhenValidated_ThenReportsViolation`;它把前置条件、动作和结果写进名称,适合希望让名称对应行为场景的团队。

几种风格的取舍:

| 维度 | 三段式 | 可读句子式 | Given-When-Then |
| --- | --- | --- |
| IDE 里按字母排序 | 同一被测方法自然聚在一起 | 散开,靠类名组织 | 同一 Given/When 前缀可聚在一起 |
| 按方法名过滤(`--filter-method`) | 前缀一勾就是一组 | 只能按句子匹配 | 可按 Given/When 前缀匹配 |
| 读作文档 | 稍生硬,但信息密度高 | 读起来顺,容易写啰嗦 | 条件与结果分段清楚,也可能显得冗长 |
| 对重命名的韧性 | 名字含方法名,方法改名测试要跟着改名 | 名字与实现解耦 | 名字与实现解耦 |

选一种,整个工程保持一致。本章工程故意两种并列展示(两个测试类各用一种),真实工程里混用比任选一种都差。

顺带一提:`xunit.runner.json` 里的 `methodDisplay`/`methodDisplayOptions` 能在**显示时**把方法名里的下划线换成空格(`replaceUnderscoreWithSpace`),还能把 `eq`、`lt`、`ge` 这类名字替换成 `=`、`<`、`>=`(`useOperatorMonikers`)。那是显示层的整形,源码里的名字不变,别指望它替你解决命名问题;配置细节在第 10 章。

### 要避免的名字

[`TestStructureAntiPatternTests.cs`](../code/Ch02.TestStructure/TestStructureAntiPatternTests.cs) 里存着真实反例:

```csharp
public void TestValidate_Empty()
public void ValidateUsername_Case1_ReturnsTrue()
```

`Test`、`Case1`、`ReturnsTrue` 都是实现细节式命名:它们记录的是"这个测试戳了哪个分支",不是"验证了什么行为"。这类测试失败时,必须打开测试体才知道坏了什么;`ReturnsTrue` 甚至没有回答"什么条件下为真"。名字里出现 `Test1`、`Case2`、`OK`、`Works` 这类词,就是重命名的信号。

### DisplayName:描述里有中文或空格时

方法名受 C# 标识符约束,句子只能靠下划线拼。`DisplayName` 属性(`FactAttribute`/`TheoryAttribute` 都有)把 runner 打印的名字整个替换成任意字符串。[`UsernamePolicyTests.cs`](../code/Ch02.TestStructure/UsernamePolicyTests.cs):

```csharp
[Fact(DisplayName = "用户名长度恰好等于上限 20 时应视为合法")]
public void Validate_UsernameAtMaxLength_ReportsNoViolations()
```

[`PasswordPolicyTests.cs`](../code/Ch02.TestStructure/PasswordPolicyTests.cs) 里那个带 `Skip` 的演示测试(2.6 会用到)也配了 `DisplayName`。`dotnet test`(MTP)打印它的跳过记录时,名字就是这句话:

```text
skipped 过短密码的提示里应写明最小长度 (0ms)
  演示用:故意写错的断言,去掉 Skip 参数即可复现
  from .../Ch02.TestStructure/bin/Debug/net10.0/Ch02.TestStructure.dll (net10.0|x64)
```

原生命令行(`dotnet run --project Ch02.TestStructure`)打印同一个名字:

```text
    过短密码的提示里应写明最小长度 [SKIP]
      演示用:故意写错的断言,去掉 Skip 参数即可复现
```

MTP 还能按显示名过滤:

```shell
$ dotnet test --project Ch02.TestStructure -- --filter-display-name "*恰好等于上限*"
...
Test run summary: Passed!
  total: 1
  failed: 0
  succeeded: 1
  skipped: 0
```

适用场景:团队希望失败报告和测试报告用中文或自然语言;描述需要空格、标点等进不了标识符的内容。

不适用场景:不要给每个测试都配。方法名仍然是代码里、栈帧里、`--filter-method` 里的名字,`DisplayName` 只改变显示;给所有测试都配,等于维护两套名字。默认显示仍是方法名,所以 2.3 前半节的命名风格才是根基。

## 2.4 Fact 还是 Theory

`[Fact]` 是一个无参数事实的测试:`用户名 21 个字符时报 TooLong`,一条。`[Theory]` 加数据行是**同一段测试逻辑对多组输入各跑一遍**:每一行数据是一个独立测试,计数、过滤、失败定位都按行算(本章工程的 29 个测试里,一半以上是数据行展开出来的)。

判定标准一句话:**这是一条事实,还是同一逻辑的多组输入?**

| 情况 | 写法 |
| --- | --- |
| 单一具体场景("恰好 21 个字符") | `Fact` |
| 同一分支、同一期望,只是输入不同(空格、连字符、点都是非法字符) | `Theory` + `InlineData` |
| 同类场景但期望不同(3 个字符合法,2 个字符太短) | 拆成多个测试,别塞进同一个 Theory |
| 测试体需要按参数 if/switch | 行为不同,拆 |
| 参数里有布尔开关 | 几乎总是该拆 |

好的 Theory,[`UsernamePolicyTests.cs`](../code/Ch02.TestStructure/UsernamePolicyTests.cs)——三组输入走的是同一个分支,断言一字不变:

```csharp
[Theory]
[InlineData("li-si")]
[InlineData("li si")]
[InlineData("li.si")]
public void Validate_UsernameContainsInvalidCharacter_ReportsInvalidCharacterViolation(string username)
{
    var violations = policy.Validate(username);

    Assert.Contains(violations, v => v.Rule == PolicyRule.UsernameHasInvalidCharacter);
}
```

数据行本身就是规格:哪些字符算非法,不用读测试体就能看到;哪一行失败,runner 单独报那一行。

Fact 误用的代价是重复:同一个测试体复制三遍只改数据,逻辑一变要改三处,很快就出现"三个副本改漏了一个"。

Theory 误用的代价是过度参数化。[`TestStructureAntiPatternTests.cs`](../code/Ch02.TestStructure/TestStructureAntiPatternTests.cs) 存了真实反例:

```csharp
[Theory]
[InlineData("alice", "Str0ngPass", true)]
[InlineData("ab", "Str0ngPass", false)]
[InlineData("alice", "weak", false)]
public void Validate_UsernameAndPassword_ReturnsExpectedFlag(string username, string password, bool expected)
{
    var usernameOk = new UsernamePolicy().Validate(username).Count == 0;
    var passwordOk = new PasswordPolicy().Validate(password, username).Count == 0;

    Assert.Equal(expected, usernameOk && passwordOk);
}
```

它"覆盖"了三种输入,但把行为契约压成了一个布尔:失败时只知道"预期 True 没来",不知道是用户名太短还是密码缺数字;用户名校验和密码校验两套逻辑挤进同一个测试;数据行离开测试体毫无意义。这就是 2.3 说的"命名即文档"的反面——名字和数据都在,但读不出任何行为。

判定流程:

1. 测试需要参数吗?不需要 → `Fact`。需要 → 继续。
2. 参数化之后,测试体完全相同、只有数据在变吗?是 → 一个 `Theory`。
3. 测试体要按数据分支,或者期望的形状在变?→ 拆成多个测试。
4. 拿不准?→ 先写 `Fact`,出现第三个副本时再合并成 `Theory`。

## 2.5 工程组织

### 测试工程放在哪里

本教程把被测代码和测试放在同一个工程里([`Production/`](../code/Ch02.TestStructure/Production/) 目录加 `Production` 命名空间,这是第 1 章定下的简化),为的是把注意力留给测试本身。真实解决方案里,两者通常是**分开的工程**,常见布局:

```text
src/
  MyApp/                 # classlib:生产代码
  MyApp.Core/
tests/
  MyApp.Tests/           # 测试工程
```

测试工程用项目引用指向要测的工程,例如:

```xml
<ItemGroup>
  <ProjectReference Include="../../src/MyApp/MyApp.csproj" />
</ItemGroup>
```

(这段不在本章工程里,是真实工程的示意。)要点:

- 生产工程不引用任何测试相关的东西;依赖方向只有 tests → src。
- v3 的测试工程是独立可执行程序(第 1 章讲过),在这个布局里不变:它仍然是 `OutputType Exe`,能直接运行。
- 一个生产工程配一个测试工程是常见默认;不要按命名空间再拆出更多测试工程。

### 一个被测类型,一个测试类

`UsernamePolicy` 对应 `UsernamePolicyTests`,`PasswordPolicy` 对应 `PasswordPolicyTests`,文件名一一对应。好处很实际:在 IDE 里按类名搜索,就能找到这个类型的全部测试;改 `UsernamePolicy` 时,该跑的测试一目了然。

觉得某个测试类太大,通常说明被测类型太大,而不是测试文件需要拆——先拆类型,测试类自然跟着拆。

### 测试文件按功能或命名空间组织

按"被测类型"切分文件是默认做法(本章就是这么做的)。跨类型的功能测试(比如"注册流程"要同时用两个策略类)可以按功能命名,如 `UserRegistrationTests`。团队里选一种组织方式(按被测类型,或按功能/命名空间镜像 src 结构),和工程形状一致即可,别混着用。

### 测试类不是继承层次

xUnit.net 为每个测试新建一个测试类实例(第 1 章),测试类不是一种"带行为的基类";复用靠构造函数、辅助方法和夹具(第 5 章),不靠继承。把 `[Fact]` 放进基类的后果,[`TestStructureAntiPatternTests.cs`](../code/Ch02.TestStructure/TestStructureAntiPatternTests.cs) 里有真实演示:

```csharp
public abstract class PolicyTestsBase
{
    [Fact]
    public void BaseClassFact_RunsInEveryDerivedTestClass()
    {
        Assert.True(true);
    }
}

public class DerivedFromBaseA : PolicyTestsBase
{
}
```

抽象基类自己不产生测试,但每个具体派生类都会继承并重跑这条测试。过滤到派生类跑一次:

```shell
$ ./Ch02.TestStructure -class "*.DerivedFromBaseA"
xUnit.net v3 In-Process Runner v4.0.2+0c7aa4991f (64-bit .NET 10.0.13)
  ...(Discovering/Starting 行省略)
=== TEST EXECUTION SUMMARY ===
   Ch02.TestStructure  Total: 1, Errors: 0, Failed: 0, Skipped: 0, Not Run: 0, Time: 0.077s
```

`Total: 1` 就是基类里那条 `[Fact]`。再加一个派生类,它就跑两遍,而且没人会注意。基类里的 `[Fact]` 把"公共行为"复制进每个子类,基类里的字段把隐藏状态耦合进每个子类——看到测试基类,先问它是不是应该改成夹具或辅助方法。

## 2.6 测试作为文档

测试是唯一不会腐烂的文档:它每天被 CI 执行,过期就变红。但前提是测试表达的是**行为**,不是实现。

### 命名 + 数据 = 行为契约

把名字和数据行放在一起读,就是一份规格:

```csharp
[Theory]
[InlineData("bob")]          // 恰好是最小长度 3
[InlineData("alice_99")]
[InlineData("ZhangSan")]
public void Validate_ValidUsername_ReportsNoViolations(string username)
```

它在说:`bob`、`alice_99`、`ZhangSan` 这类用户名合法,而且"恰好等于下限"也算合法。谁改动 `UsernamePolicy` 的实现,这份规格都还在原地等着被运行。这就是为什么本章花一整节讲命名:名字不是装饰,是契约的正文。

### 测公开行为,不测私有实现

`UsernamePolicy` 里的 `IsAsciiLetter`、`IsAllowedCharacter` 是私有辅助方法,本章没有任何测试直接调用它们——所有测试都走公开入口 `Validate`。效果:辅助方法内部怎么重新拆分,测试一行不改;如果测试贴着私有方法写,重构就被迫重写测试,测试作为安全网的意义就没了。

判断标准:测试引用的每个成员,应该是调用方也能用到的公开 API。反过来,如果某个私有辅助复杂到"单独测它"很诱人,那是被测类型该拆分的信号,不是用反射去测私有方法的理由。

### 一个测试只验证一个行为

一个测试描述一个行为。注意"一个行为"不等于"一条断言"——2.2 的重构版里有两条断言:

```csharp
var violation = Assert.Single(violations);
Assert.Equal(PolicyRule.UsernameRequired, violation.Rule);
```

`Single` 说"违规有且只有一条",`Equal` 说"它是 Required 那条",合起来就是"空用户名被报为唯一一条 Required 违规"这一个契约。

当一个行为的证据是一组事实时,用 `Assert.Multiple`。[`PasswordPolicyTests.cs`](../code/Ch02.TestStructure/PasswordPolicyTests.cs):

```csharp
[Fact]
public void Weak_password_lists_every_missing_requirement_at_once()
{
    var violations = policy.Validate("abcdef", "alice");
    var rules = violations.Select(v => v.Rule).ToArray();

    // 这个测试验证的行为是"一次性列出所有缺失项",它的证据就是三条规则。
    // Assert.Multiple 会把三条断言全部跑完,失败时一起报告。
    Assert.Multiple(
        () => Assert.Contains(PolicyRule.PasswordTooShort, rules),
        () => Assert.Contains(PolicyRule.PasswordMissingUppercase, rules),
        () => Assert.Contains(PolicyRule.PasswordMissingDigit, rules));
}
```

它和普通断言序列的区别:普通序列在第一条失败断言处终止测试,输出里只看到第一个失败;`Multiple` 把所有检查跑完,失败一起报告。本章工程里有一个故意失败的测试(带 `Skip`,去掉即可复现),去掉 `Skip` 后用原生命令行(`dotnet run --project Ch02.TestStructure`)运行,真实输出(MTP 版的排版不同,但同样会列出两段 `Not found`):


1. **重构反例。** 把 [`TestStructureAntiPatternTests.cs`](../code/Ch02.TestStructure/TestStructureAntiPatternTests.cs) 里的 `TestValidate_Empty` 和 `ValidateUsername_Case1_ReturnsTrue` 按三段式命名重写,AAA 用空行分隔,断言换成有信息的写法,并删掉反例注释。

## 本章小结

- 测试通常按 AAA 组织:空行帮助分隔,Act 通常只有一次调用;AAA 是惯例而非必须凑齐的模板,注释只在能解释意图时保留。
- 命名回答"测什么 + 什么条件 + 期望什么行为":三段式(`方法_条件_期望`)、可读句子式与 Given-When-Then 都可行,选一种保持一致;`Test1`、`Case1`、`ReturnsTrue` 式实现细节名不合格。
- `DisplayName` 把两种 runner 打印的名字整个替换成任意描述,适合中文或自然语言报告;方法名仍是代码、栈帧和 `--filter-method` 用的名字,`DisplayName` 宜少不宜多。
- `Fact` 是一条事实;`Theory` 是同一逻辑的多组输入,每行数据是独立测试。测试体按数据分支、或参数里有布尔开关,就是该拆的信号;拿不准先写 `Fact`,出现第三个副本再合并。
- 真实项目把测试工程与生产代码分开(`src/` + `tests/` + `ProjectReference`);本教程简化为同工程 [`Production/`](../code/Ch02.TestStructure/Production/) 目录。一个被测类型对应一个测试类;测试文件按类型或功能组织,选一种。
- 测试类不是继承层次:`[Fact]` 写进基类会被每个派生类重跑一遍;复用交给构造函数与夹具(第 5 章)。
- 测试用命名与数据表达行为契约;只测公开行为;一个测试只验证一个行为——多条断言可以描述同一个契约,`Assert.Multiple` 只用于同一行为的多条证据,失败时一次报告全部。
